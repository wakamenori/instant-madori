# 検証12：日差しの計算方式と結果の形

実施日：2026-11-26。Issue #203。床・壁・天井に届く直射光の求め方を五つ試作し、答えの分かる例での誤差、細い光が消えないか、2階建ての家一軒での時間とメモリ、結果の大きさを比べた。採った方式は次のとおりで、計画の4.8に書いた。

- 光を調べる点を取らない。受ける面ごとに、遮る三角形を太陽の向きに面の平面へ投影して面から引き、光の届く範囲を凸な多角形の集まりとして正確に求める（方式E）。
- 遮る物は表示メッシュで判定する。平面の面では、表示メッシュへの光線とB-repへの光線の答えが一つも違わなかった。
- 計算は、ブラウザのビューアのWasmで、表示中の案の表示データから行う。Containerは計算しない。家一軒の最も遅い時刻で、wasm32の計算は約3 msだった。
- 結果は表示データに載せず、ビューアのメモリの中だけに持つ。表示データには、計算の入力として地域と方位、光を受ける範囲を足す。

反対役の試しで、方式Eに五つの誤りが見つかった。直した後の方式（E2）で測り直した値を、この記録の判断に使った。

## 対象と測り方

試作は使い捨てのコードとして `crates/modeling` のテスト専用のモジュールに置いた。コードは [prototype.patch](evidence/verification-12/prototype.patch) に残し、このブランチには含めない。課題、比べる方式、固定例、許容差は、試作のコードより前に [task.md](evidence/verification-12/design/task.md) に書いてコミットした（`ed7fa99bb`）。計算する場所を決める閾値も、家一軒の時間を測る前に同じファイルの末尾に足した。

固定例は、SolidCraftのスケッチの押し出しとブール演算で直接作り、住宅データの操作には依存しない。座標は+Xが東、+Yが北、+Zが上で、単位はmmである。光を受ける面は、部屋の空気の箱へ向く平面の面（床、壁の室内側、天井）とした。

| 方式 | 求め方 |
| --- | --- |
| G | 受ける面ごとの均一な格子（200、100、50、25、10 mm）。セルの中心から太陽へ、表示メッシュに光線を当てる |
| A | 開口の8隅を太陽の向きに受ける面へ投影した矩形の中だけを、5〜25 mmの格子で調べる。外は暗いとする（検証2の方式） |
| Q | 200 mmのセルから、四隅と中心の判定がそろわないセルだけを細かくする |
| E | 点を取らない。遮る三角形のうち受ける面より太陽の側にある部分を、太陽の向きに面の平面へ投影して面から引く。差は、凸な片の切り取りを自前で書いたものと、SolidCraftの `kernel::planar_regions_boolean` の二通りで求めた |
| B | Gと同じ点を、平面のB-repへの光線で調べ、Gと答えが違う点を数える |

精度は、macOSでSolidCraftのdevのビルドを使って測った。家一軒の時間は、SolidCraftのreleaseのビルドがこのマシンのディスクに入らなかったので、別の方法で測った。dev の試作で固定例の表示メッシュを表示データと同じf32にして書き出し、std だけに依存する小さなcrateでG・A・Q・Eを動かした。光線の判定は、そのcrateの中にWoopらの水密な交差判定とBVHを書いた。このcrateの答えは、devの試作と、格子の方式で明るいセルの数が全件一致し、Eの面積が全件1e-6 m²以内で一致した（120行、役割ごとの面積360個）。同じcrateを、macOSのarm64のrelease、Node.jsのwasm32、ContainerのイメージのLinux amd64（`rust:1.99.1-bookworm` でビルドし、`debian:bookworm-slim` で実行）で動かした。このマシンはApple M4 Proで、Dockerはarm64なので、amd64はエミュレーションで動いた。

×は許容差の外である。どの方式でも、水平な天井の面積はどの太陽でも0だった。光が届かない面（床の例の天井と壁、壁の例と勾配天井の例の床）も、計算できた方式ではすべて0だった。勾配天井の例の北の壁（解析解0.671832 m²）は、Gの10 mmとA、Q、E、E2だけが許容差に入った。

格子の誤差は間隔を細かくしても単調に減らない。固定例の寸法が格子の間隔の倍数なので、光の境界がセルの中心の列にちょうど重なることがあり、水密な判定は辺を通る光線を遮られたと数える。境界の一列が丸ごと暗くなるか明るくなるかで、誤差が跳ぶ。QはGを200 mmから二分するので、指定した最小の10 mmと5 mmは、実際には6.25 mmと3.125 mmになった。

kernel版のEは、床の例でも `solidcore failed (status 1001)` で止まった。失敗した最初の呼び出しは、四角形から投影した四角形を一つ引くもので、影の側に長さ約1.56e-7 mmの辺があり、受ける面の辺と影の辺が一部で重なっていた（[kernel-cut.txt](evidence/verification-12/raw/kernel-cut.txt)）。この短い辺は、試作が受ける面の手前を1e-7 mmの幅で切ったときにできたもので、kernelの許容差と同じ桁である。直接の原因は特定していない。kernelはビューアのWasmに入れられないので、それ以上は調べていない。

## 表示メッシュとB-repの光線

GとBは、同じ3,469,300点で答えが一つも違わなかった。平面の面は表示メッシュに三角形で正確に分けられ、SolidCraftの水密な交差判定は二つの三角形が共有する辺を通る光線をすり抜けさせない。曲面の家具などでは、表示メッシュは面からテッセレーションの誤差の分だけ離れるが、画面に描くのは表示メッシュなので、光の範囲は描いた形に合う。Bの時間は、比べるためにGの光線も同じ点で当てたので、Bだけの時間は分けられなかった。この比較は、SolidCraftのf64の表示メッシュで行った。表示データのf32の位置で起きる誤りは、反対役の試しで見つかった（後の節）。

## 反対役の試しで見つかった誤り

二人の反対役（Opus、effort high）が、記録と計画とパッチを読み、試作のcrateで場面を変えて方式Eを壊そうとした。見つかった誤りは、どれも再現のコマンドを打ち直して確かめた。再現のスクリプトは [interrogate/](evidence/verification-12/interrogate/) にある。

1. **軸に沿わない面で、Eが光を消した。** 受ける面自身のf32の三角形が遮る物に入っていた。f32の丸めで頂点が面の平面より最大約1e-4 mm手前に出ると、手前を切る幅（1e-7 mm）を越え、面が自分を引いた。30°と60°回した壁、勾配を変えた勾配天井（反対役の計測では16.7°〜31.0°の四つすべて、再計測では21.8°と26.6°）、0.1 mm上げた勾配天井で、面積が0になった。事前の固定例は、丸めがたまたま後ろ側に出たので通っていた。
2. **上限が仕事を抑えなかった。** Eは受ける面ごとにすべての遮る三角形を切って投影するので、仕事は受ける面の数と遮る三角形の数の積に比例する。地面の下に三角形を10万個足すと、計画の三つの回数（候補、切り取り、片）は同じまま、家一軒の12月15時が約3 msから約85 msになった（ネイティブ）。計画の「数百ms以内」という上限の書き方も、事前に決めた閾値（50 msを超えたらWeb Worker）と食い違っていた。
3. **受ける面が部屋の外まで含んでいた。** 片流れの屋根に600 mmの軒を付け、下面を一つの面にすると、屋外の軒天まで天井として光った（勾配天井1.086707 m²が3.857988 m²）。試作は、重心から10 mm先が部屋の空気の箱に入る面を丸ごと受ける面にしていた。同じ理由で、勾配天井の固定例では屋根の上面が床として受ける面に入っていた（報告した値には影響しない）。計画が床と天井を「面の役割（3.5）」で選ぶとしたことも誤りで、3.5の面の役割は壁と屋根にしかない。
4. **太陽にほぼ平行な面で、投影が崩れた。** s·nが1e-10をわずかに超える面で、投影した影が面の外へ大きく伸び、方位1e-8°で西の壁に1.091697 m²の光が出た。正しくは0である。
5. **描き方の前提が違った。** viewport-gpuのプレビューの枠は、不透明な面と線だけを描き、透ける面（`pv.glass`、`pv.trans`）を描かない。光の片は不透明でしか描けない。また、上階を隠しても光の片をそのまま描くと、2階の床の片（3月21日12時の床の光0.676 m²のうち0.647 m²）が、描かれていない床の1 mm上に浮く。

ほかに、計画が新しいcrateとその依存の規則を書きながら、4.2の表と `scripts/check/boundaries.ts` に行が無いこと、`raw/environment.txt` が中断した最初の計測の記録のままだったこと、幅5 mmのスリットの期待値の桁の誤りが見つかった。

直した方式E2は、次の点がEと違う。

- 受ける面自身の三角形を、面の番号で遮る物から外す。
- 面の平面との距離の絶対値が0.01 mm以下の頂点を、面の上にあるとみなす。太陽の側の頂点を一つも持たない三角形は捨て、持つ三角形は面の上までを影として引く。手前を切る位置を一律に0.01 mmずらす形も試したが、壁と天井の継ぎ目に光が残り、勾配天井が1.086864 m²になった。
- s·n ≤ 0.01（太陽と面のなす角が約0.57°以下）の面は、調べずに暗いとする。
- 受ける範囲を、面の三角形を部屋の範囲（底面の多角形を鉛直に押し出した柱と、zの範囲）で切ったものにする。
- 遮る三角形を、時刻ごとに太陽の向きに垂直な平面へ投影して、1辺1,000 mmの一様な格子に入れる。受ける範囲ごとに、その投影の外接矩形と重なるセルの三角形だけを候補にする。

E2は、全固定例と反対役の変形（鉛直軸のまわりに0°〜90°を5°ごとに回した床・壁・勾配天井・スリット・隙間20の例、面の平面をB-repから取る場合と最初のf32の三角形から取る場合、四つの勾配、12通りのずらし、軒、ほぼ平行な面、屋根の上面）の解析解のある値で、誤差が最大8.5e-7 m²だった。Eは同じ値のうち80個で許容差を外れていた。隣家を除いて30°回した家一軒では、光が届く面のE2とG 25 mmの差は最大0.92%だった。全部の値は [e2-cases.md](evidence/verification-12/raw/e2-cases.md) にある。

## 家一軒の時間とメモリ

家一軒は、2階建てで階ごとに4室、窓10か所とスリット窓1か所、外へのドア、室内のドア、2階の床と1階の天井の階段の穴、軒の出600 mmの陸屋根、部屋ごとの家具の箱、南に3 m離れて高さ6,500 mmの隣家2棟（50 mmの隙間あり）である。表示メッシュは1,148個の三角形で、遮る三角形が1,016個、光を受ける面が48面ある。太陽は東京相当の12月21日の9時・12時・15時、3月21日と6月21日の12時と、地平線より下の時刻とした。12月の3時刻は、隣家がすべての窓を遮り、どの面にも光が届かなかった。

各方式の、昼の5時刻のうち最も遅い時刻の計算時間（5回の中央値、ms）と最大メモリを示す。時間に、メッシュの読み込みとWasmの読み込みと描画は含まない。E2は、ディスクの空きが足りずLinux amd64では測れなかった。

家具が増えたときと、遮る三角形が多いときを見るため、各部屋に円柱（半径200 mm、高さ700 mm、蓋を含めて256三角形）をN個ずつ足した場合と、地面の下に光に関係しない三角形を足した場合を、E2で測った。表は昼の5時刻のうち最も遅い時刻のwasm32の中央値である。

E2の時間は三つの仕事で決まる。格子に入れる三角形の数、候補の組の数、影と凸な片を比べる回数である。地面の下に40万個を足した12月15時は、候補の組が10,279のまま時間が2.96 msから15.11 msに増えた。この差は格子に入れる仕事で、三角形一つあたり約30 nsになる。円柱64個の12月15時は、切り取りの回数が円柱なしと同じまま、候補の組が931,470になり、51.39 msだった。格子の分を除くと、候補の組一つあたり約50 nsになる。円柱32個と64個の6月21日12時が遅いのは、窓からの光の中に円柱が並び、光の届く範囲が細い片に分かれる（片のピーク337）ためである。円柱32個では影と片の比較が6,765,653回あり、比較一回あたり約35 nsになる。片が細かく分かれるのは、円柱の側面の細い三角形を一つずつ引き、引くたびに片を辺の直線で分けるからである。ボディの影の輪郭をまとめてから引けば比較は減ると推定するが、試していない。

Linux amd64の値はエミュレーションで動かした値なので、Cloudflare上のContainerの時間とは違う。計算をブラウザで行うことにしたので、Containerの時間は判断に使っていない。

結果を表示データと同じ考え方で数えた（Eは面ごとに8バイトと、凸な片の頂点ごとにf32の2D座標で8バイト。格子は面ごとの原点と間隔、行ごとの連続区間）。値はEを直す前に測った。

## 判断

**方式はE2とする。** 許容差をすべて満たしたのはAの5 mmとE（直した後はE2）だけだった。E2は解析解との差が1e-6 m²以下で、家一軒ではAの5 mmより約1,000倍速かった（直す前のEで、macOSの2.85 msと2,812.99 ms）。Aは、光が届く範囲が開口の投影の中にあるという前提に立ち、開口の一覧に漏れがあると黙って光を失う。Gは光の幅が間隔に近づくと誤差が跳び、10 mmでも正面の50 mmの光で許容差を超えた。Qは細い光を作りの上で見落とす。

**遮る物は表示メッシュで判定する。** 平面の面では、表示メッシュとB-repの答えは同じだった。B-repを使うにはsolidcore-opsへの直接の依存が要り、ビューアのWasmでは使えない。表示データの位置はf32なので、受ける面自身を外し、面の平面から0.01 mm以内を面の上とみなす。

**計算はブラウザのビューアのWasmで行う。** 家一軒の最も遅い時刻のwasm32の中央値は、直す前で2.81 ms、直した後で2.96 msで、事前に決めた閾値（50 ms以下なら画面の処理の中で同期的に計算する）を下回った。時刻を変えたときにネットワークの往復もContainerの起動も無く、別の案や条件の遅れた結果が届くこともない。対象の選択も、すでにブラウザで表示メッシュを使っている。Containerで計算すると、結果の形式、内部と公開のルート、R2のキャッシュ、遅れた結果を捨てる仕組みが要る。

**仕事の量に上限を置き、超えたら計算しない。** 格子に入れる三角形の数、候補の組の数、影と片を比べる回数を数え、上の単価（約30 ns、50 ns、35 ns）から求めた時間の合計が50 msを超えない値を上限にする。円柱を部屋ごとに32個以上置いた場面の一部の時刻（32個の3月21日と6月21日の12時、64個の12月15時など）は、この上限を超えるので「計算できない」になる。上限を超えた案を粗く計算すると、細い光が消えるかどうかが端末と案によって変わるので、粗くしない。

**受ける範囲は、modelingが部屋の範囲で切って書く。** どの面のどこが部屋の中かは、部屋の輪郭と面の役割を知っているmodelingにしか分からない。表示データには、受ける範囲を三角形で書き、ボディの番号、面の番号、床・壁・天井の別、部屋の住宅要素IDを付ける。

**結果はビューアのメモリの中だけに持つ。** 結果を運ばないので、結果のバイナリ形式は要らない。表示データには入力として、地域と方位、光を受ける範囲（と、ガラスのボディができたときに光を通すボディの区別）を任意セクションで足す。

**描画はviewport-gpuに任せる。** 検証11のとおり、ビューアが自前のパイプラインで後から重ねる描き方は、透けるボディがあると深度を失う。光の片は、viewport-gpuのプレビューの枠（`pv_slot`）にシーンとして置き、モデルと同じ深度のある描画で描く。この枠は透ける面を描かないので、片は不透明で、下の柄を隠す。隠したボディの受ける範囲の片は描かない。この描き方は試作していない。柄を見せたいときは、受ける面の三角形を光の片で置き換えてシェーダーに日差しのフラグを足す描き方（[candidate-1.md](evidence/verification-12/design/candidate-1.md)）が次の候補になる。

**GPUの影の地図は使わない。** 4096²の影の地図で敷地と隣家を含む約40 mを覆うと、1画素が約10 mmになり、5 mmの光は1画素に届かない。結果がGPUに依存し、CIで面積を確かめられない。

## 分かっていないこと

- 家一軒は、箱を組んだ固定例である。AIが作る一般の住宅では、受ける面の数と遮る三角形の数がもっと多い。円柱の家具を部屋ごとに32個置くと上限を超えた。家具の多い案で上限を超える頻度は分かっていない。
- 時間はApple M4 Proの値である。商談で使う端末での時間は測っていない。
- E2のLinux amd64の時間は、ディスクの空きが足りず測っていない。
- kernel版のEが失敗した直接の原因は特定していない。
- 描き方（プレビューの枠に片を置く）は試作していない。Wasmの大きさの増え方も測っていない。

## 再実行と証拠

証拠は [evidence/verification-12/](evidence/verification-12/) にある。

- `design/` に、計測の前に書いた課題と許容差（`task.md`）、読んだ資料の要約（`grounding.md`）、二つの設計の候補と合成の記録がある。
- `prototype.patch` は、E2を含む試作のコードの差分である（`6e8aa2e03` に当てる）。
- `raw/dev.jsonl` は、SolidCraftのdevのビルドで測った解析解と細い日差しの例の全行である。
- `raw/scenes/` は、書き出した固定例の表示メッシュである。`raw/scenes2/` は、それに部屋の範囲を足したものである。
- `raw/macos.jsonl`、`raw/wasm.jsonl`、`raw/linux.jsonl` は、依存なしのcrateで直す前の方式を測った全行で、`raw/summary.md` が表にしている。`raw/reproduce.md` に、場面の形式、時間の内訳、ディスクの推移がある。
- `raw/e2-cases.md`、`raw/e2-timing.md`、`raw/e2-wasm.jsonl` は、E2の照合と時間である。手順は `raw/e2-reproduce.md` にある。
- `interrogate/` に、反対役の再現のスクリプトがある。パスは反対役の作業ツリーのものなので、使うときは直す。

再実行するときは、基準のコミットのworktreeを作り、差分を当てる。

```sh
git worktree add --detach ../v12-rerun 6e8aa2e03
cd ../v12-rerun
git checkout origin/main -- docs/verification/evidence/verification-12
git apply docs/verification/evidence/verification-12/prototype.patch
mise exec -- pnpm install --frozen-lockfile
mise exec -- pnpm setup
bash crates/modeling/src/model/sun_probe/bench/dev.sh
```

`dev.sh` は `raw/dev.jsonl` を作る。場面の書き出しと、依存なしのcrateでのmacOS・wasm32・Linux amd64の計測は `raw/reproduce.md` の手順で、E2の照合と計測は `raw/e2-reproduce.md` の手順で行う。書き出しの後は、コミットした場面だけで計測できる。
