# 検証2：壁の分割・削除、ブラウザ接続、直射日光

実施日：2026-11-08。[検証1](verification-01.md)を拡張し、壁の構成が変わる編集、ブラウザでの表示とサーバーでの変更、季節・時刻・隣家による直射光の変化まで実行した。本文は実施時点の記録であり、現在の仕様と実装順は[実装計画](../plan.md)を参照する。

片付け（2026-11-08）：検証サーバーを停止し、試作コードと `target/` の生成物を削除した。この文書と[記録フォルダ](evidence/verification-02/)の証拠は残している。以下は実施時の記録であり、記載のコマンドは現在のリポジトリではそのまま実行できない。

## この結果からの設計判断

**SolidCraftをサーバー側の形状処理に使い、描画部分だけをブラウザへ組み込む構成で進められる。住宅側には、壁と開口の関係、分割後の外観の引き継ぎ、削除時の関連物の処理を持たせる必要がある。**

この責務の分担は、コードを読んだ見込みから、限定した例で動作を確認した段階に進んだ。既存のSolidCraftのクレートの変更は不要だった。

日差しについても、床に直射光が届く範囲を、月・時刻・隣家に応じてブラウザの3Dに表示できた。今回の方法は床のサンプリングによる表示であり、室内の明るさや写実的な照明の完成を示すものではない。

## 1. 壁の分割と削除

### 試した条件

検証1の共有壁をX=4500へ動かした二部屋を使用した。窓のある壁の全体を赤茶色、室内側の面を緑色にし、窓の中心X=2250を通る平面で壁を二つに分割した。窓の開口は二つの壁片にまたがる。

続いて共有壁を消して二部屋を統合し、その後、窓のある壁をガラスとともに削除した。各段階で保存・再読込し、以前の案からの再編集と、重複した削除の失敗時に元の案が保たれることも確認した。

### 見つかった問題と修正

SolidCraftの `solid.split_body` だけで分割すると、元の名前を保つ `wall.north` の色は残ったが、新しい `wall.north (1)` にはボディの色も面の色もなかった。**SolidCraftの面追跡だけで、住宅として期待する引き継ぎが全部済むわけではない。** [修正前後の実測](evidence/verification-02/topology-report.json)に、色指定が空だった状態も残した。

利用側で、論理的な壁 `north-1` が二つのCADボディに対応するようにした。分割元の外観を読み取り、子のボディと室内側の面へ引き継ぐ。窓の対応先も二つの壁片とガラスへ更新した。室内側はこの直線壁のY=5000の面として識別している。

削除では、共有壁の削除を部屋の統合に反映した。窓のある壁の削除では、関連するガラス・対応表・残った色指定も処理した。これは今回の操作の意味として実装したもので、あらゆる部屋削除時に家具まで消すという製品仕様を決めたものではない。

### 確認できたこと

| 操作 | 結果 |
| --- | --- |
| 窓をまたぐ壁の分割 | 窓の空洞と壁の合計体積が維持され、両方の壁片の室内側が緑色になった |
| 共有壁の削除 | 2Dと3Dから共有壁が消え、二部屋が40.00 m²の一室になった |
| 窓のある壁の削除 | 壁片・ガラス・関連する対応が消え、家具の加工と色が残った |
| 保存・再読込 | 3段階ともデータが一致し、形状・対応・色の検査が通過した |
| 前の案へ戻して再編集 | 分割前の案を復元し、再び分割できた |
| 失敗した削除 | 採用済みの案を変更しなかった |

壁の体積と空洞はB-repで確認した。共有壁を消した後の40 m²は既存の矩形の床領域を統合した値。外壁まで消した段階では「閉じた室」を検出しているわけではなく、同じ床領域を保持する。この点は画面でも「床領域の広さ」と表示する。

## 2. ブラウザとサーバーの接続

### 実装した構成

`apps/madori-verify` にローカル検証用のHTTPサーバーを追加した。住宅情報、SolidCraftの編集データ、形状評価と保存をサーバーで扱う。ブラウザには表示メッシュ・色・対象の対応・2D図・面積を送る。

`apps/madori-viewer` は専用のHTML/JavaScript画面と、SolidCraftの `geom`・`render`・`gpu` を使うWasmビューアである。ブラウザ側の通常依存には `engine`・`doc`・`kernel`・`ui-egui` を含めていない。WebGPUで描画し、カメラ操作はSolidCraftのCameraを利用する。

画面の操作ボタンは検証用であり、製品の編集をAI経由で行う要件を変更するものではない。AIや会話機能はまだ接続していない。

### ブラウザで実際に確認したこと

- 壁の分割・部屋の統合・窓のある壁の削除・初期状態への復帰をクリックし、サーバーでの形状変更が3D・2D・広さに反映された。
- テーブルをクリックすると、サーバーが `table.top` と論理的な家具 `furniture-1` を返した。選択は描画メッシュから確定せず、この平面だけの例ではサーバーでB-repの面と視線を交差させて判定した。
- 回転・拡大縮小・表示切替でビューが変わり、視点操作による追加のHTTP要求は発生しなかった。
- サーバーを終了・再起動した後、案の番号、住宅情報、形状、色、対応表を復元できた。ブラウザを再読込して編集を続けられた。
- 古い案の番号からの変更、二度目の分割、存在しない操作を拒否し、表示用のデータ全体が変更前と一致した。

[ブラウザで観測した値](evidence/verification-02/browser-observations.json)、[拒否した操作](evidence/verification-02/madori-browser-errors.json)、[再起動の照合](evidence/verification-02/madori-browser-restart.json)を保存した。

### サイズと時間

Wasmは **1,043,049バイト**。同じファイルをgzip圧縮すると300,303バイトだった。既存の `ci` プロファイルでビルドし、wasm-optは使っていない。サーバーは未圧縮で配信したため、圧縮後の値は実際の転送量ではない。[サイズの記録](evidence/verification-02/viewer-size.json)

住宅モデルのJSONは今回約74〜102 KB。壁の分割からブラウザの描画指示まで126.5 ms、部屋の統合136.9 ms、窓のある壁の削除133.0 ms、初期状態への復帰154.2 msだった。これはローカルでの各1回の観測であり、GPUの描画完了時刻、実ネットワーク、AIの応答時間、家一軒の性能を測った値ではない。

ブラウザはこの環境のT3プレビュー（Chromium 152 / Electron 44、1280×800、WebGPU）。一般のPC・ブラウザ間の互換性は未検証。

## 3. 季節・時刻・隣家による直射光

### 計算と表示の範囲

同じ二部屋の形を日差し用の固定例として使い、方位を設定して窓を南向きにした（+X=西、+Y=南、+Z=上）。東京の緯度35.68°、経度139.76°、2026年の各月21日、日本標準時を使う。太陽の方向は[NOAAの太陽位置の近似式](https://gml.noaa.gov/grad/solcalc/solareqns.PDF)から求めた。

壁、家具、屋根と、必要な場合は南側の隣家について、床から太陽への線がB-repの面に当たるかを調べる。隣家は窓側の外壁から1000 mm離れた高さ6500 mmの箱。ガラスは光を通すものとする。

**屋根は遮蔽計算に含め、室内を見るため表示だけ省略した。** 屋根をなくして日差しを計算したものではない。黄色は床に直射光が届く範囲であり、壁や天井を含む写実的な明暗表現ではない。拡散光、反射、照度、ガラスの光学特性、天候は計算しない。

この表示は固定例を再生成する検証モードであり、編集した任意の案へ日照機能を統合したものではない。今回、太陽位置と遮蔽の処理は利用側に追加した。SolidCraftの既存の照明設定だけで同じ体験を実現できるかは、今回の結果からは判断しない。

### 粗い計算で見落とした光

最初の200 mm間隔のサンプリングでは、夏の細い日だまりを見落とし、ゼロと表示した。窓の開口の8隅を床へ投影して候補範囲を絞り、その範囲を25 mm間隔で判定する方式へ変更した。表示用メッシュは隣り合うセルをまとめ、計算点を増やしても転送データが過大にならないようにした。

独立に答えを出せる「真南・高度30°」で、窓幅1.2 m、開口高さ1.1 m、壁厚0.2 mから投影面積を計算した。期待値は `1.2 × (1.1 / tan(30°) − 0.2) = 2.046307… m²`。25 mmサンプリングの結果は2.04 m²で、事前に設定した許容差0.05 m²以内だった。窓を通る点、窓より上の壁に遮られる点、隣家に遮られる点も確認した。

### 実測した範囲

| 条件 | 床に直射光が届く面積の概算 |
| --- | ---: |
| 12月21日12時、隣家なし | 1.94625 m² |
| 6月21日12時、隣家なし | 0.028125 m² |
| 12月21日9時、隣家なし | 1.614375 m² |
| 12月21日15時、隣家なし | 0.001875 m² |
| 12月21日12時、隣家あり | 0 m² |
| 12月21日0時 | 0 m² |

値はこの窓の寸法・壁厚・向き・周辺物体に対するもの。一般に夏の採光がなくなるという意味ではない。25 mm間隔より細い変化の見落としや境界の誤差は残る。

[計算結果](evidence/verification-02/sunlight-report.json)を保存した。サーバー計算は約0.08〜2.36秒。ブラウザでは冬の昼が約1.17秒、夏の昼が約0.23秒、隣家ありの冬の昼が約1.31秒だった。値を変えて結果を見る体験は確認できたが、連続した時刻変更に毎フレーム追従する性能は確認していない。

## 実施時の手順（試作コードは片付け済み）

リポジトリのルートで、形状と日差しの検査を実行した。

```sh
cargo run --locked --profile ci -p madori-verify -j 4 -- --topology target/madori-topology
cargo run --locked --profile ci -p madori-verify -j 4 -- --sunlight
```

`apps/madori-viewer` でブラウザ用のファイルをビルドした。

```sh
trunk build --cargo-profile ci --dist ../../target/madori-web --filehash false
```

ルートへ戻り、ローカルサーバーを起動した。

```sh
cargo run --locked --profile ci -p madori-verify -j 4 -- --serve
```

`http://127.0.0.1:8797/` を開いて確認した。案件の代わりに一つの検証用データを扱い、変更のたびに `target/madori-web-state.json` へ保存する構成だった。再起動すると最後の状態から再開し、「初期状態に戻す」で二部屋の例へ戻れた。サーバーはloopbackに限定した同期処理の検証用HTTP実装であり、片付け後は停止している。製品用の認証・DB・API基盤は、検証実施時点では未選定だった。

## 残った設計上の仕事

検証1の5段階も追加変更後に再実行して通過した。追加したRustのネイティブ側とWasm側は、それぞれ `cargo clippy --no-deps -- -D warnings` を通過した。ブラウザ用JavaScriptの構文確認、Rustのフォーマット確認、文書のローカルリンク確認も通過した。SolidCraft全体のCIや、製品としての負荷・互換性試験を実行したという意味ではない。

住宅の要素に識別子を持たせ、対応するCADの形と面の役割を追う方針に進む。今回の対応表はボディ名と、この例の「室内側の平面」を使ったものなので、任意の名称変更、曲面、壁の合流、複雑な面の分割まで保証する方式ではない。

直射光のサンプリング精度と速度、壁・天井への表示、任意の敷地と周辺形状への対応は本体実装で確認・改善する。今回の床への黄色い表示を、そのまま製品の最終的な見せ方と決めたわけではない。

検証後の合意により、事前の技術検証はいったん完了とし、住宅情報・操作を一般の間取りへ広げ、AI・画面・保存をつなぐ本体実装に進む。今回の成功は、その操作と表示を受け止める土台についての結果であり、AIによるプランの品質は未検証である。生成品質の証明を実装開始の条件にはせず、作りながら改善する。
