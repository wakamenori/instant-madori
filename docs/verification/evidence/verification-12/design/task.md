# 日差しの試作の課題と、計測の前に決めた許容差

Issue #203。この文書は計測の前に書き、試作のコードより先にコミットする。後から変えたときは、変えた理由と日付を末尾に足す。

## 決めること

1. 光を調べる点の取り方。
2. 遮蔽の判定（表示メッシュへの光線か、平面のB-repへの光線か）。表示メッシュとB-repで答えが違うとき、どちらを正にするか。
3. 結果の形（面ごとの多角形、セルの集まり、表示メッシュの頂点ごとの値）と、その運び方（案の表示データの任意セクションか、別のバイト列か）。
4. 計算する場所（Containerの `crates/modeling` を保つか）。
5. 壁・天井への表示方法と、太陽が地平線より下のときの扱い。

## 比べる方式

座標は住宅の座標系で、+Xが東、+Yが北、+Zが上、単位はmmとする。太陽の方向 `s` は、点から太陽へ向かう単位ベクトルである。

| 記号 | 点の取り方・求め方 | 遮蔽の判定 |
| --- | --- | --- |
| G | 受ける面ごとの均一な格子。間隔200、100、50、25、10 mm。セルの中心を調べ、明るいセルの数×間隔²を面積とする | 表示メッシュへの光線（`MeshIndex::raycast`） |
| A | 開口（窓・ドアの穴の室内側と屋外側の輪郭）を `s` に沿って受ける面へ投影した範囲の外接矩形の中だけを、間隔25、10、5 mmの格子で調べる。範囲の外は暗いとする（検証2の方式） | 表示メッシュへの光線 |
| Q | 面ごとに200 mmの粗い格子から始め、四隅と中心の判定がそろわないセルだけを4分割し、最小の間隔25、10、5 mmまで細かくする | 表示メッシュへの光線 |
| E | 点を取らない。受ける面の多角形から、遮る三角形（ガラスを除く）を受ける面より太陽の側の部分に切ってから `s` に沿って受ける面の平面へ投影した多角形の和を引き、明るい多角形を求める | 表示メッシュの三角形の投影 |
| B | Gと同じ点を、平面のB-repへの光線で調べる（検証2の方式）。表示メッシュへの光線との答えの違いを数える | 平面の面の多角形への光線 |

Eの多角形の差は、SolidCraftの `kernel::planar_regions_boolean` か、試作の中で書いた凸な多角形の切り取りで求める。どちらで求めたかを結果に書く。

## 固定例

固定例は、SolidCraftの操作（スケッチの押し出しとブール演算）で直接作る。住宅データの操作には依存しない。ガラスは開口の中の薄いボディとし、遮る物から除く。

### 処理時間とメモリを測る例

2階建ての家一軒と隣家2棟。外形はおよそ10 m × 8 m、階ごとに4室以上、外壁の窓を合わせて10か所程度（スリット窓を1か所含む）、外へのドアと室内のドア、2階の床の階段の穴、軒の出600 mmの屋根、家具の箱8個程度、隣家の箱2棟（隙間あり）。光を受ける面は、部屋の空気の箱へ向く面（床、壁の室内側、天井）とする。太陽は12月21日の9時・12時・15時、3月21日12時、6月21日12時（東京相当、検証2の方向を座標系に合わせて使う）と、地平線より下の時刻。

時間は、表示メッシュとBVHを作る前処理と、条件ごとの計算に分けて測る。メモリは最大常駐量を測る。ContainerのイメージのLinux amd64（`apps/geometry/Dockerfile` と同じ `rust:1.99.1-bookworm` でビルドし、`debian:bookworm-slim` で動かす）の中で測る。このマシンはApple M4 ProでDockerはarm64なので、amd64はエミュレーションで動く。macOSのarm64でも同じ計測を行い、両方を載せる。

## 計測の前に決めた許容差

- 床・壁・勾配天井の3例は、面積の誤差が解析解の1%以内で合格とする（床 ±0.020463 m²、壁 ±0.012326 m²、勾配天井 ±0.010867 m²）。1.2 m幅の光の範囲で、境界が平均3〜4 mmずれた量に当たる。3Dの画面で部屋を見る距離では1画素がおよそ5 mm以上になり、見分けられない。
- 同じ3例で、光が届かない面（床の例の天井と壁、壁の例の床、勾配天井の例の床）の面積は0.0001 m²（1 cm²）以下とする。
- 水平な天井は、どの太陽でも面積が0（1e-9 m²以下）で合格とする。
- 細い日差しは、面積が0より大きく、解析解との差が解析解の20%以内で「消えない」とする。
- 採る方式は、上のすべてを満たすこと。満たさない方式は採らない。

## 追記（2026-11-26）：計算する場所の判定

設計の二つの候補が、どちらもブラウザのWasmで表示データから計算する案になった。そこで、試作の計測の結果を読む前に、計算する場所を決める計測と閾値をここに足す。

- 方式Eの凸な片の実装を、SolidCraftに依存しない小さなクレートに写す。家一軒の固定例の表示メッシュ（f32の位置と三角形）、受ける面、遮る物の区別をファイルに書き出して入力にする。同じクレートを、macOSのarm64のreleaseと、wasm32（Node.jsで実行）で動かす。条件ごとに5回測り、中央値と範囲を出す。答えがContainerの試作と一致することも確かめる。
- 判定は、家一軒の5つの太陽の条件のうち最も遅い条件のwasm32の中央値で行う。
  - 50 ms以下なら、ブラウザのWasmで、画面の処理の中で同期的に計算する。
  - 50 msを超え300 ms以下なら、ブラウザのWasmで、Web Workerの中で計算する。
  - 300 msを超えるか、wasm32の最大のメモリが200 MBを超えるなら、Containerで計算する。
- 閾値の根拠。商談で使うノートPCは、このマシン（Apple M4 Pro）の3〜5倍遅いと見込む。50 msは5倍しても時刻の操作の直後に描き終わる量で、300 msは5倍しても1.5秒で、Containerへの往復と計算と同じ程度になる。
