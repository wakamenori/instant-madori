# 二つの設計候補の比べ方と合成

Issue #203。pstack の architect の手順で、二つの担当（どちらも Opus、effort medium）に、同じ課題と同じ資料（`task.md`、`grounding.md`）から本番の日差しの流れを一つずつ設計させた。候補は [candidate-1.md](candidate-1.md) と [candidate-2.md](candidate-2.md) にある。二人とも試作の計測を見ずに書いた。

## 判定の基準

1. 正しさ。幅50 mm以下の光が消えない。解析解の例が許容差に入る。水平な天井が作りの上で0になる。
2. 既存の境界に合う。`crates/display` は依存を持たない。ビューアはCADカーネルを含まない。modelingはSolidCraftを受け持つ。
3. 利用者の体験。商談中に時刻を変えたとき、待たずに描ける。
4. 上限。大きさと仕事の量に上限があり、超えたら粗くせずに失敗にする。
5. 描画。床・壁・天井に描け、屋根を隠しても変わらず、ガラスがあっても壊れない。
6. 公開する型と関数が小さい。

## 二つの候補が一致したこと

二つの候補は、計算の場所、方式、入力の運び方で同じ結論になった。

- 計算は、ブラウザのビューアのWasmで、表示中の案の表示データから行う。Containerのルート、結果の形式、R2のキャッシュは要らなくなる。
- 方式はE（点を取らない正確な投影）。太陽に背を向ける面は調べずに暗いとする。
- 計算はSolidCraftに依存しない新しいcrateに置き、表示データだけに依存させる。modelingは試験でだけ使う。
- 表示データに、地域と方位、光を受ける面の任意セクションを足す。屋根を隠しても、計算は表示の状態を見ない。

同じモデルの二つの担当なので、一致は独立した二つの判断より弱い証拠として扱った。そのため、計算の場所は候補の意見では決めず、試作の結果を見る前に `task.md` の追記に書いた閾値（wasm32で50 ms）で決めた。

## 合成

候補2を土台にした。候補2は、凸な片の切り取りを自前で書き、第三者のcrateに依存しない。試作で全許容差を満たしたのも同じ書き方だった。仕事の量の上限を時間でなく操作の回数で数え、受ける面に部屋の住宅要素IDを持たせる。

候補1から取り込んだもの、取り込まなかったもの。

- 取り込んだ。光を通すボディ（開口のガラス）は、色の透明度や名前でなく住宅要素の種類で決め、表示データに書く。候補2は、ガラスのボディができるときにその区別を足すとしており、合わせて計画には規則だけを書いた。
- 取り込まなかった。平行な面で投影を使い回す工夫。家一軒で2.8 msなので、今は要らない。
- 取り込まなかった。頂点を1/64 mmの整数の格子に丸め、ネイティブとwasm32でビット単位に同じ答えにする仕組み。結果をキャッシュしないので、端末をまたいで同じビット列である必要がない。
- 取り込まなかった。受ける面の三角形を光の片で置き換え、シェーダーに日差しのフラグを足す描き方。上流のシェーダーの変更が要る。候補2の、viewport-gpuのプレビューの枠に片を置く描き方は上流を変えずに済むので、こちらを初めの設計にした。片が下の柄を隠すことが問題になれば、候補1の描き方が次の候補になる。後の反対役の試しで、プレビューの枠は透ける面を描かないと分かったので、この描き方では片は必ず不透明になり、下の柄を隠す。

## 判定役

arenaの判定役は、親（Claude）と別の系統のモデルから選ぶ決まりである。設定の `arena cross-judge pool` は `opus xhigh` と `inherit-parent` で、どちらも親と同じ系統なので、判定役は立てず、上の基準で親が選んだ。
