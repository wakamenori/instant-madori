# 検証6：住宅からの形状生成・壁接合・要求ごとの再構築

実施日：2026-11-15。Issue #69 の三つの設計判断を、家一軒の試作と反対役の追加検証から決めた。住宅データからCADを再生成し、住宅側で決めた壁ごとの輪郭を押し出し、完了した要求の間ではCADのSessionを保持しない。要求内の再生成には評価キャッシュを引き継ぐ。現在の仕様は[実装計画](../plan.md)の3.1・3.5・3.6・4.3・4.6・4.7に反映した。

## 対象と測り方

[住宅入力](evidence/verification-06/house.json)は12,000×8,000 mmの6室の平屋である。外壁200 mm、内壁120 mm、高さ2,400 mm、床150 mm、室内ドア5個、窓3個を持つ。X=4,000の共有壁を4,500へ動かす。長さはmm、体積はmm³。輪郭方式は壁9ボディと床1ボディ、箱の和は壁1ボディと床1ボディになる。この住宅入力と寸法は#103でも再利用できる。性能確認用の固定例であり、一般の住宅スキーマではない。

Mac16,11、macOS 27.2.1、論理CPU12、メモリ24 GiB、mise固定のRust 1.99.1を使った。`CARGO_INCREMENTAL=0`、既存のreleaseプロファイル、thin LTO、ビルド並列数4である。最初に `pnpm install --frozen-lockfile` と `pnpm setup` を完了した。最初の比較のベースは `bbd8460920d8fb19334b3004d8424dd400f9bb44`、追加検証と文書のベースは `0bb6fa02c`。その間の更新はRustの形状処理を変更していない。

作成、壁変更、表示のバイナリ出力、CAD文書の読込と再評価、保存用シリアライズを別々に測った。ビルド、期待値との照合、プロファイルは比較の時間に含めない。表示の出力は `madori_modeling::display::export` と共有形式のencodeを使い、実際のバイト列をdecodeして消費した。AI、HTTP、実Container、Cloudflare、ブラウザ描画を含まない。ローカルの数値からContainerの種類や商談全体の待ち時間は決めない。

共有Macの負荷が高く、最初の計測前後のload平均は31.06と25.58だった。各方式を順序反転して7回ずつ実行し、同じ手順をもう7回行った。遅い試行も捨てずに14回の中央値と全範囲を示す。[全56試行](evidence/verification-06/baseline-runs.json)に個々の時間、色の面上の点・法線、体積、サイズを残した。

数値の合格条件は実行前に決めた。座標0.01 mm、法線成分0.000001、体積100 mm³以内とする。体積はメッシュから推定せず、SMLibのB-rep積分値で照合した。表示のdecode、ボディが閉じていること、フィーチャー評価エラーがないことも調べた。ただし、それだけでは正しい接合を証明できないため、後述の住宅側の検査を加えた。

### 開口に覆われない点と部屋側の検査

反対役と指揮役は、固定の色の点Y=2,500・Z=1,200を覆うドアを足すと、全再生成が `appearance.assign` の `no face at ...` で失敗することを確かめた。保持Sessionの面の色は残った。SolidCraftはボディの大きさの5%以内の近傍面を選ぶため、点が開口内でも別の面へ割当たる場合がある。固定した点を近傍探索に任せる方式を採らない。

試作を修正した。住宅の壁面の範囲を、開口の左右端と上下端で区切り、開口を含まない区画の内点を選ぶ。辺からの余裕が最大の区画を、同じ入力で同じ順に選ぶ。壁の留めでは実際の側面の輪郭内であることも必要になる。割当て可能な領域がなければ明示的に失敗させる。この試作の矩形面の区画分けを、任意の壁面へ一般化する作業は#80が受け持つ。

[追加した外観の検査](evidence/verification-06/appearance.json)ではY=2,200〜3,100・高さ2,050のドアを足し、元の点を覆った後も青と緑が正しい面に残った。色付き面積は両側とも5,526,000 mm²、X=3,940と4,060、法線はそれぞれ-Xと+Xだった。`v1-r0` はY=100〜3,940にあるr1/r2間の壁、`v1-r1` はY=4,060〜7,900にあるr4/r5間の壁という独立したfixtureの対応を使う。色の検査はボディID、部屋側に対応する向き、面上の位置、全法線成分、開口を引いた面積、色の件数を照合する。

r4/r5側の `v1-r1` に色を付ける変異は `wrongBodyPaint.ok=false`、部屋側の期待する対応を上側へ変える変異は `wrongRoomExpectation.ok=false` になった。正常例だけが `doorAddedAcrossOldPoint.ok=true` である。

### 採用判断と一括の費用

全再生成を採る。住宅データと外観の役割を正とすれば、壁の追加・削除・分割でCADの依存関係と孤立した色指定を差分同期する仕組みを減らせる。反対役と指揮役の再実行では、保持Sessionで壁を消す際、開口の切欠きも同時に消さないと評価に失敗し、削除した壁の色も孤立して残った。パラメータ更新による壁移動は27フィーチャー中16を再評価し、変更箇所だけの更新にはならなかった。

これは全再生成の速度優位を示す判断ではない。初回の壁移動の時間は範囲が重なり、固定の短縮率は主張しない。反対役が試したドア追加・壁追加では、表示データの書き出しを含め、保持Sessionが6室の家で8〜19倍、24室の大きい家で25〜47倍速かった。住宅操作と一括の種類ごとに費用が違うため、壁移動だけで方式全体の速さを決めない。

指揮役の再実行では、6室5操作のプレビュー込みで保持84 ms、全再生成394 ms、キャッシュ引継ぎ176 msだった。反対役の24室21操作では保持0.43〜0.54秒、全再生成8.4〜10.2秒、キャッシュ引継ぎ0.93〜3.9秒だった。新しい要素を最後に足す順序なら0.93秒だった。これらは独立の反対役の観測であり、次の担当側の追加計測とは区別する。

## 壁の接合と住宅側の拒否条件

最初の[角90度・45度・Tの比較](evidence/verification-06/baseline-joins.json)は両方式で評価エラー0、体積誤差0.000002 mm³未満だった。長さ2,000・厚さ200・高さ2,400の2壁の留めの期待値は2×2,000×200×2,400=1,920,000,000 mm³。Tは(4,000×200+1,900×120)×2,400=2,467,200,000 mm³。中心線端で突き付けた箱の和は留めと異なり、45度では外側が9,941,125.497 mm³欠ける。箱和の期待値は `(2Lt-(t/2)^2 tan(θ/2))H` として別に計算した。箱和が斜め接合に使えないという証拠ではなく、延長・クリップまで含む別実装は比較していない。

この試作の箱の和は採らない。すべての壁が一つのボディになり、壁と面の役割の対応を別に作る必要がある。6室の初期作成の中央値は輪郭62.215 msに対して箱和239.057 msで、約3.8倍遅かった。また、試した45度の突き付けでは材料が欠けた。これらは今回の組み立て方の比較であり、箱の延長・クリップで留めを作る別実装を否定するものではない。

採用する輪郭方式も、無条件に側面の交点を使うだけでは破綻した。[追加接合の全結果](evidence/verification-06/decided-joins.json)には、以前の規則の結果と、決めた規則での作成または拒否を並べた。

| ケース | 以前の規則 | 決めた規則の結果 |
| --- | --- | --- |
| 200と120の一直線 | 無限大・NaNの輪郭 | 二等分線で切り、体積1,536,000,000 mm³、誤差0.000001未満 |
| 厚さ違い、ずれ0.3・1度 | 自己交差。1度で体積が14,248,362 mm³過大 | 二等分線で切り、各1,536,000,000 mm³、誤差0.000001未満 |
| 厚さ違い、ずれ2・3・5度 | この長さでは正しい | 3度以内は二等分線、5度は向かい合う側面の交点。いずれも誤差0.000001未満 |
| 内角15度、壁長2,000 | 正しい | 成功。体積1,920,000,000 mm³ |
| 内角15度、壁長700 | 閉じたまま自己交差し、2,242,872 mm³過大 | 留めに必要な約759.6 mmを下回るため生成前に拒否 |
| 外側面をそろえるための40 mmの接続壁 | 接続壁が三角形に退化。和は1ボディ・すき間なしで、体積が11,520,000 mm³過大 | 短い接続壁を拒否し、境界の側面オフセット200/0・120/0で表すと成功 |
| Y字30度、厚さ120と200 | 通し壁がなく規則未定義 | 隣接する向かい合う側面の交点で生成。いずれも体積誤差0.000001未満 |
| 扇形、3壁の間が30度 | 規則未定義 | 同じ隣接面の規則で生成、体積誤差0.000001未満 |
| 両側に50 mmずれて付いたT | 隣接面の規則だけなら480,000 mm³の重なり | 通し壁を優先し、合計体積と和の体積が一致 |
| 角を5 mmまたぐドア | ホスト壁のみの切欠きでは隣壁25,625 mm³が残る | 壁の輪郭をはみ出す開口として生成前に拒否 |
| 留めの手前のドア、余裕0〜10 mm | 正しい | 0・0.001・0.01・0.1・1・10 mmで成功 |
| 四方向交差・斜めT15/30度 | 成立する条件もある | 通し壁を優先し、合計体積と和の体積が一致 |
| 交差した輪郭を与える変異 | CADが受け取る場合がある | 自己交差の検査で拒否 |
| 全高の開口で壁を二つに切る | 評価エラー0で2ボディになる | 1壁1ボディの検査で拒否 |

一直線からのずれの幅は3度以下とした。0.3・1度で無条件の交点が破綻し、2・3・5度ではこの長さの例が成立したため、3度を近平行として扱う余裕を取った。任意の厚さ・長さで3度が十分という証明ではない。留めの長さ・自己交差・非有限値は角度と独立に検査し、短い形を拒む。完全な一直線では境界に垂直、近い場合は境界方向を二等分する線で切る。通し壁がない節点では角度順に隣接した側面を接続し、通し壁があるTでは枝をその側面で止める。

通過した30ケースはフィーチャー評価エラー0で、期待体積との最大誤差0.000001 mm³未満だった。個々のボディの合計とBoolean和の体積も照合し、重なりを見つける。外側面をそろえた例では、同じ境界上の側面オフセットで接続し、短い接続壁とすき間を作らない。体積だけで全てのすき間を検出できるとは扱わない。任意の多分岐、曲面、あらゆる近平行のTを受け入れる一般実装は#80の範囲である。

## 要求の形と費用

要求は入力住宅スナップショットと操作の一括を受け、要求内でCADを構築して、検査済みの住宅スナップショットと表示を返す。読込・操作・検査・保存を別々の状態保持APIにはしない。色だけの一括でも作り直す。表示だけならR2に保存した表示を読み、Containerへ送らない。確定前の検査・保存用出力も、この一要求の形で行う。

要求種別の参照試作も担当が実行した。[要求別の5回の値と範囲](evidence/verification-06/requests.json)、[8要求のジョブの5回の合計](evidence/verification-06/jobs.json)を残す。参照試作の入力は同じ6室・家具なしで、住宅JSONは1,077バイト、再生成したCAD JSONは25,495バイト、表示は35,976バイトだった。要求の機能の費用を比較するローカルの呼出しであり、公開HTTPの計測ではない。参照試作は診断用のCAD JSONもシリアライズしているが、採用する保存仕様では家のCADを保存しない。

6.2が送る要求を、8要求の参照ジョブのms中央値で分ける。右列は家の形が変わるときだけ再生成し、それ以外は保持Sessionを使う比較対象である。

最初の14回ずつの輪郭・パラメータ方式では、CAD文書の読込と新規Sessionでの再評価が中央値60.788 ms [55.286, 81.772]、その後の壁変更が48.465 ms [42.863, 72.659]だった。文書のパラメータを先に変えて一度だけ評価した出力・保存までの合計は62.568 ms [56.680, 72.252]、保持Sessionの変更・出力・保存は48.974 ms [45.280, 113.326]だった。二重評価の費用を、要求ごとの構築に必須の費用とは扱わない。採用する住宅からの全再生成・表示・保存用出力の合計は62.316 ms [59.094, 72.424]だった。このCAD文書読込の比較は方式検討用であり、家のCADをmanifestへ保存する提案ではない。

保持Sessionなら、job ID・実行世代別のSession表、同一Sessionの排他、重複した操作IDの抑止、停止token、容量と期限による破棄、メモリを失ったときのsnapshotと操作からの再構築が要る。要求ごとに作り直す方式でも、job ID・操作ID・実行世代・入力snapshotは必須である。途中の要求の取消し情報は扱うが、完了した要求のCADグラフを次の要求の前提にしない。停止・失効した世代の遅着結果は確定しない。
