# 住宅相談サービス 実装計画

更新日：2026-11-20

初回提供までの仕様と設計、実装の段階と各段階の完了条件をまとめる。作業の単位と進み具合はGitHubのmilestoneとIssueで管理し、この文書には書かない。生成品質・性能・一般の住宅への対応は、各段階で確認・改善する。合意した要件に加え、API、モジュール名、保存形式などは実装に向けた初期設計を記す。

## 1. 目的と初回提供の範囲

### 1.1 目指す体験と到達点

施主の断片的な希望をその場で間取りと3Dにし、営業と一緒に見ながら住まいのイメージを具体化する。家の形だけでなく、家具の配置、素材、敷地や隣家との関係、窓からの日差しも相談できるようにする。

初回提供の到達点は、招待された営業が自分の案件で案を作り、変更・比較し、保存して次の商談から再開できること。6章の全段階を初回提供の範囲とする。最初の一往復が動いた時点は、途中の実装到達点である。

### 1.2 利用者・利用場面・利用環境

- 注文住宅の初回相談で、営業が操作し、施主と同じ画面を見る。
- PCのブラウザを対象にする。住宅を変更するためのCAD操作は要求しない。
- 招待制とし、メール認証コードでログインする。案件は個々のユーザーに所属する。
- AIは運営側で用意し、費用を負担する。営業によるAPIキーの登録は不要。
- 対応ブラウザの確認は6.1と6.6で行う。WebGPUの利用可否を判定し、利用できない場合に理由を表示する。

### 1.3 対応する住宅と機能、初期の対象外

| 対象         | 初回提供で扱う範囲                                                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 階・部屋・壁 | 平屋と2階建て。各階の床は同一高さ。直線の壁、斜めの壁、L字などの部屋。LDKは一室として扱う。アーチ形の入口や斜めの切り欠きなど、壁への形の加工 |
| 屋根         | 陸屋根・片流れ・切妻・寄棟。複数の屋根の組み合わせ、勾配・軒の出の変更                                                                        |
| 階段         | 直階段・L字・折り返し。踊り場と回り段。段板・手すりなどの形と見た目の変更                                                                     |
| 窓・ドア     | 取り付け先の壁、位置、幅・高さを持ち、間取りと3Dで同じ配置を表す                                                                              |
| 家具・素材   | 言葉や参考画像から特徴を取り入れた家具の作成・配置・変更。色と、木目・タイルなどの柄の表示                                                    |
| 敷地・周辺   | 敷地の形・寸法・方位・道路、隣家の配置・高さ・形。画像と会話で入力し、不明な条件は仮置きする                                                  |
| 日差し       | 地域・方位・月・時刻に応じた直射日光と遮蔽。家の配置・窓・屋根・隣家の影響を反映する                                                          |
| 相談の継続   | 案件、複数パターン、会話、案の履歴、過去案からの再開、複製、間取り画像の保存                                                                  |

初期の対象外は、3階以上、地下室、スキップフロア、平面形が曲線の壁（アーチ形の入口など、加工でできる曲面は扱う）、螺旋・自由曲線の階段、曲面屋根、壁のない用途別領域の面積表示、住所からの周辺建物の自動取得とする。画像の完全再現、写実的な反射、反射光を含む室内照度の定量予測も要求しない。

タブレット、会社・チームでの共同編集、一般向けの自己登録、課金機能、案を横に並べる比較、図書一式の出力、CAD連携、法規・構造の適合判定は初回提供に含めない。

## 2. 利用の流れと画面の仕様

### 2.1 案件の作成とパターンの管理

案件一覧から案件を作り、一つ目のパターンを開始する。案件名とパターン名には初期名を入れ、後から画面で変更できる。敷地が未定でも始められる。案件名などの管理情報の変更と、住宅内容の編集は区別する。

一つの案件に、別の土地での検討と、同じ土地での別案を持てる。パターンを切り替えると、住宅・敷地・会話・履歴・実行状態も切り替わる。別パターンで進行中の処理は継続する。

案件画面は、間取り・3Dの表示領域と、会話・履歴・指示欄で構成する。現在のパターン、表示中の案、編集中か確定済みかを分かるようにする。

### 2.2 AIへの指示・画像添付・対象選択・聞き返し

住宅・家具・素材・敷地・隣家の変更は、テキストと画像によるAIへの指示で行う。画面から壁や家具などを選択し、指示の対象として添えられる。初期設計では選択対象を最後の確定案に限定し、作業途中の形を確定した対象として送らない。

希望が全部揃うまで入力を要求せず、未指定の部分を仮置きして案を作る。画像では、気に入った特徴を取り入れることを目指す。読めない寸法や見えない部分を推定した場合は、その条件を会話で伝える。

AIは必要に応じて質問や選択肢を出せる。聞き返す基準は運用中に調整する。質問だけの応答では案を増やさない。初期設計では、未確定の編集の途中で質問する場合、その作業用コピーを破棄し、回答を受けて最後の確定案から編集を始める。

生成中も追加指示を送れる。指示には受付順と、選択時の案・対象IDを記録する。実行時には直前までの確定結果を使い、選択対象が消えていたら勝手に別の対象へ置き換えず、会話で確認する。

### 2.3 間取り・3D・日差しの表示と操作

| 表示   | 操作と内容                                                                                                   |
| ------ | ------------------------------------------------------------------------------------------------------------ |
| 間取り | 階の切り替え、拡大・移動。部屋名・広さ・方位、壁・窓・ドア・階段・家具の配置を表示する                       |
| 寸法   | 初期設計では建物の外形寸法と選択した部屋・壁の主要寸法を表示する。複雑な部屋を一つの幅・奥行きだけで表さない |
| 3D     | 回転・拡大、室内を見るための視点移動、視点リセット。室内を見やすくする屋根・上階の表示切り替えを用意する     |
| 日差し | 月と30分刻みの時刻を選択する。各月21日を代表日とし、実際に計算する年・日付・時刻を表示する                   |

視点や表示、日差しの月・時刻は画面で直接変更し、案の履歴を増やさない。地域と方位は住宅・敷地の条件として案に保存し、変更はAIへの指示で行う。未指定なら仮の条件を表示する。初期値は東京相当の位置・日本標準時・画面上方向を北とし、計算年は利用時の年を使う。

間取り・3D・面積は同じ案を表示する。別の時点の表示データを混ぜない。屋根などを見やすさのため非表示にしても、日差しの遮蔽物からは除かない。

### 2.4 生成途中・待機・停止・失敗時の表示

| 状態                 | 画面と次の処理                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| 実行中               | 作業の区切りでプレビューを更新し、最後の確定案と区別する。追加指示は待機列に入れる                   |
| 質問待ち             | 質問を会話に残し、確定案を維持する。質問への回答を先に扱えるよう、待機列の自動進行を保留する         |
| 完了                 | 新しい案へ切り替え、変更内容と残る使い勝手の懸念を説明する。次の待機指示を実行する                   |
| 停止・失敗・上限到達 | 未確定の変更を採用せず、最後の確定案へ戻す。待機指示があれば保留し、再開・取り消しを選べるようにする |
| 接続断・画面を閉じた | サーバーで処理を継続する。開き直したときに進行状況と結果を読み直す                                   |

利用者は、実行中の指示も待機中の指示も、同じ停止の操作で止められる。待機中に止めた指示は実行されない。停止の受理後に届いた結果は採用しない。確定のほうが先に完了していた場合は、停止はその完了と確定した案を返し、停止によって完成済みの案を取り消さない。画面は停止の応答で、止めた（cancelled）か、確定が先だった（completedと確定した案）かを分け、確定が先なら新しい案へ切り替える。開き直した画面は、stateの最後に終わった指示から同じ区別を読む。最後に終わった指示は実行した指示に限り、待機中に止めた指示と取り消した指示を含めない。この区別は実行した指示にだけあるためである。保留中なら、保留の原因になった指示とその終わり方をstateの保留から読む。過去案への復帰は別の操作で行う。

実行中の指示が停止・失敗で終わったとき、待機中の指示があれば、パターンの待機列を保留する。止めた理由や失敗の原因が後の指示にも当てはまる場合に、意図しない編集を続けないためである。保留中は待機中の指示を実行しない。保留中に届いた指示も受け付けて待機列の最後に加え、保留が解けるまで実行しない。画面は、保留の原因になった指示とその終わり方（停止か失敗か）と、待機中の指示を示す。利用者は再開か取り消しを選ぶ。再開すると、待機列を受付順に進める。取り消すと、保留中に届いた指示も含めて待機中の指示をすべて取り消し、保留を解く。どちらの操作も、画面が示した保留の原因の指示を添えて送る。その後に保留が解けていた場合や、別の指示の失敗で保留し直していた場合は適用しない。画面は状態を読み直し、利用者に選び直してもらう。

待機中の指示がなければ保留しないので、停止や失敗を見てから送った指示はすぐに実行する。待機中の指示を止めても保留しない。その指示には採用しない未確定の変更がなく、後の指示も一つずつ止められるためである。保留中に待機中の指示を一つずつ止めて待機列が空になったら、保留も解ける。

プレビューの更新間隔は実測で調整する。負荷が大きければ更新頻度を下げ、完了時だけの更新にも切り替えられる構成にする。一指示の処理時間には上限を置かず、所要時間を記録して改善する（5.3）。実行中の指示を止める手段は、利用者の停止と、5.2の費用・AIの往復の回数などの上限である。

### 2.5 履歴の閲覧・復帰・パターンの複製

AIが編集をまとめて案を提示するたびに履歴を一件追加する。案には変更内容から名前を付ける。内部コマンドや会話一件ごとに案を増やさない。

過去案は閲覧専用とし、プレビュー中の編集入力を無効にする。「この案から続ける」でその内容を新しい履歴項目として末尾へ追加する。後の案と会話は消さず、どの案へ戻ったかを記録する。AIは希望や参考画像を参照しつつ、取り消された操作を再適用しない。

パターンの複製では、起点となる確定案と、そこまでの案の履歴・会話を引き継ぐ。最新案からの複製は、その時点までに完了した会話も含める。質問だけで終わった往復も対象とする。過去案からの複製は、その案を提示した時点で会話を区切る。未実行の指示と進行中のジョブは複製先へ持ち込まない。複製後の変更は独立する。

初期設計では、実行中のパターンを復帰させる操作は、完了または停止を待って行う。待機指示があれば保留する。複製は確定済みの案から行えるため、複製元の処理を止める必要はない。

### 2.6 保存・再開・間取り画像の出力

確定案と会話はサーバーに保存し、手動保存を要求しない。再開時には最後の確定案と、待機・実行中・保留の状態を復元する。

間取り画像は表示中の階をPNGで保存する。部屋名、面積、方位、表示中の寸法を含め、案件・パターン・案・階が分かる名前にする。対象は確定済みの案とし、プレビュー中の過去案も出力できる。生成途中の形は出力対象にしない。

## 3. 住宅データと編集のルール

### 3.1 階・部屋・共有境界・壁の表現

住宅の編集データは、要素の種類ごとの一覧で持つ。各要素には名前とは別の安定したIDを与える。IDは家全体で重複させず、表示データの `ElementId` と同じく、64バイト以下の英数字と `._:-` に収める。関係は片方向だけを保存し、逆向きの関係は住宅データを作るときに求める。

| 要素 | 保存する情報                                                                     | 求める情報                             |
| ---- | -------------------------------------------------------------------------------- | -------------------------------------- |
| 階   | 基準高さ、階高。床領域と階段の床開口は6.3で加える                                | なし                                   |
| 頂点 | 属する階、平面上の座標                                                           | 接する境界                             |
| 境界 | 始点と終点の頂点、その上に立つ壁                                                 | 左右に接する部屋                       |
| 壁   | 境界の中に一つだけ持ち、境界のIDで指す。境界から左右の側面までのオフセット、高さ | 厚さ、側ごとの面の役割、取り付いた開口 |
| 部屋 | 名前、用途、向きを持った境界の列                                                 | 輪郭、属する階                         |

部屋の境界の列は、上から見て反時計回りとする。境界を始点から終点へたどる部屋は境界の左側に、逆にたどる部屋は右側に接する。一つの境界の各側に接する部屋は一つまでとする。壁の面の役割は、その側に部屋があればその部屋、なければ外側とする。壁の幅は境界から左右の側面までのオフセット（どちらも0以上）で持ち、厚さはその和として求める。一直線に続く壁のまとまりは保存せず、それを動かす操作が求める。座標と長さはmmの浮動小数で持ち、境界の共有は座標の一致ではなく頂点のIDで表す。各一覧は追加順を保ち、その順を要求の始めのCADの生成順とする。要求の中の操作が足した要素は、生成する側が自分の生成順の末尾に足す（3.5）。

住宅データを作るとき（保存したJSONを読むときを含む）、次のものを要素IDと理由を付けてまとめて返し、住宅データを作らない。自己交差、開口のはみ出し、重なりなどの形の検査は3.6で行う。

- IDの文字・長さの違反と、IDの重複
- 存在しない階・頂点・境界・壁への参照
- 両端が同じ頂点の境界、長さ0の境界、二つの階をまたぐ境界、同じ二つの頂点を結ぶ二つ目の境界
- 閉じていない、同じ頂点を二度通る、または反時計回りでない部屋の境界の列と、同じ境界を二度含む列
- 三つ以上の部屋、または同じ側の二つの部屋に接する境界。どの部屋にも接しない境界と、どの境界にも使われない頂点
- 壁の色のうち、その壁にない面の役割を指す行と、同じ面を指す二つ目の行（3.5）
- 有限でない数と、絶対値が10 km（10⁷ mm）を超える数
- 負のオフセット・開口の位置・床からの高さと、0以下の厚さ・高さ・幅・階高

住宅データは `{"version": 1, "house": {…}}` の形のJSONで読み書きする。読むときは版を確かめ、知らない版と未知の欄を拒んでから、上の検査を行う。後から足す欄は、無ければ空として読み、空なら書かない。欄の名前や意味を変えるときは版を上げ、古い版を読むときに今の形へ移す（5.4）。

隣室との境界を一つのデータで共有し、変更時に両側の部屋と壁を更新する。部屋の輪郭と壁座標を独立に書き換えて後から合わせる方式は採らない。壁厚を反映した室内側の輪郭から、面積と2D表示を生成する。部屋の輪郭を変える加工がある部屋は、3.4のとおり3Dから求める。LDK内部の用途は設備・家具の配置で表し、用途別の面積境界を追加しない。

壁の追加・分割・統合では、境界と部屋の関係も同じ操作内で更新する。部屋IDを残すか統合先へ移すかを操作結果に含め、参照先が変わったことをAIへ返す。

壁を動かす操作は、壁ID、動かす向きにある面の役割（その側の部屋か外側）、距離（mmの正の数）を受け取り、壁をその面の向きへ垂直に動かす。距離はマス目へ丸めない（3.4）。選んだ壁と、頂点を共有して同じ直線上（直線から0.001 mm以内）に続く壁を一直線のまとまりとし、まとまりの頂点を同じだけ動かす。T字の先へ壁が一直線に続くとき、一つの境界だけを動かすと部屋が長方形でなくなるので、まとまりで動かす。まとまりの頂点に接するほかの境界は、遠い側の頂点を動かさずに伸び縮みする。この境界がまとまりに垂直でなければ拒む。斜めの壁は6.3で扱う。頂点・境界・部屋・開口のIDと関係、壁の色は変わらない。次の移動は、要素IDと理由を付けて拒む。

- まとまりに接する境界が、長さ0以下まで縮む移動。その先へ動かすには壁の分割が要る（6.3）。
- 動かない壁の中心線が、まとまりの通る範囲（動かす前と後の位置の間）に触れる移動。動かした壁の実体が、動かない壁の実体と重なる移動。実体は境界の中心線を左右のオフセットだけ広げた長方形とし、面が接するだけなら重なりとしない。動かす前から重なっていた組は数えない。接合部の形まで含めた重なりは、確定前に検査する（3.6）。
- 動かす向きにある部屋の幅が、その階で最も厚い壁の厚さ（1 mm未満なら1 mm）以下になる移動。幅は、動かした壁の中心線から、同じ部屋の向かい合う辺までの最も短い距離とする。部屋の配置の操作と同じ下限である。
- 収まらなくなった開口が、3.2の調整でも収まらない移動。

結果には、動いた壁、まとまりの境界を辺に持つ部屋の動かす前と後の内法面積、調整した開口を含める。動かす前に内法の輪郭を求められなかった部屋は、前の面積を空にする。

壁の平面形は、境界と左右側面のオフセットから住宅側で決め、壁ごとに押し出す。平面形は部屋の内法の輪郭と同じ節点の計算から求め、有限でない値、自己交差、時計回りの輪郭を、壁のIDと理由を付けて拒む。接合の形は保存せず、頂点の座標・オフセット・要素IDから求める。外側の面をそろえた厚さ違いも、一つの共有頂点と側ごとのオフセットで表す。中心線を40 mmずらすためだけの短い接続壁を足さない。

節点では入射する壁を角度順に並べ、次の優先順位で輪郭の端を決める。一直線からのずれが3度以下の組を通し壁の候補とし、候補が複数ならずれの小さい組を優先し、同じなら安定した要素IDで決める。この角度幅は[検証6](verification/verification-06.md)の0.3・1・2・3・5度の比較に基づく。

1. 一直線になる組があればそれを通し、ほかの壁は通し壁の側面で止める。
2. 通し壁がない節点では、隣どうしの壁の向かい合う側面の交点で出会わせる。
3. 平行またはほぼ平行で厚さの違う壁は、側面の交点を遠方へ延ばさず、境界の向きを二等分する線で切る。完全な一直線では境界に垂直な線とする。

通し壁がなく3本以上の壁が集まる節点と、通し壁の同じ側の2本の壁が通し壁の側面より手前で出会う節点では、壁の端の形を6.3で決める。それまでは、壁の平面形がこれらの節点を、節点のIDと理由を付けて拒む。部屋の内法の輪郭は、これらの節点でも規則2で求める。

角度幅だけで形の成立を保証しない。短い留め、自己交差、開口のはみ出しなどは3.6で拒む。

AIが平屋を作るときは、部屋の配置だけを渡し、境界・頂点・壁はサービスが作る（6.2では、パターンの住宅を置き換える操作とする）。入力は、部屋ごとの名前・用途・壁の中心線上の対角の二点（`min` と `max`）と、外壁の厚さ・内壁の厚さ・壁の高さである。隣の部屋と共有する座標は同じ数で書き、隣接は座標の完全一致で判定する。許容差は使わない。長方形でない部屋はこの入力では表せず、頂点の列などの欄は未知の欄として拒む。斜めの壁とL字の部屋は6.3で加える。

サービスは、部屋の各辺を、その線上にあるすべての部屋の角で分け、分けた区間ごとに境界を一つ作る。両側に部屋がある境界には内壁、片側だけの境界には外壁を立て、壁は境界から両側へ厚さの半分ずつの幅を持つ。境界の左には、その区間に接する部屋のうち要求で先に書いた部屋を置く。したがって外周の境界は、左が部屋、右が外になる。階は一つで、基準高さを0、階高を壁の高さとする。各一覧の順は、要求の順に各部屋を `min` の角から反時計回りにたどり、初めて出会った順とする。

次のものは、要求の何番目の部屋かと部屋名を付けて返し、住宅データを作らない。検査は、数と部屋の幅、部屋の重なり、壁の実体の三つの段階で順に行う。ある段階で見つかったものは、その段階の分をまとめて返し、次の段階は調べない。重なった部屋の壁を調べても、直す先は分からないためである。

- 数と部屋の幅の段階。有限でない数、絶対値が10 kmを超える数、0以下の厚さと高さ、半分にすると0になる厚さ。部屋が一つもないこと。どちらかの軸の幅が、最も厚い壁の厚さ（1 mm未満なら1 mm）以下の部屋
- 部屋の重なりの段階。重なる二部屋。重なった長方形を付ける
- 壁の実体の段階。外周の壁が4本集まる頂点。角だけで接し、残りの二つの象限を埋める部屋がない二部屋である
- 壁の実体の段階。実体が重なる二枚の壁。頂点を共有せず、同じ線上にもない組を調べる。壁の実体は、境界から両側へ厚さの半分ずつ広げた箱とし、端の長さは節点の形で決める。同じ線上に壁が続く端は延ばさない。L字の角では、相手の壁の厚さの半分だけ延ばす（上の規則2）。T字の足では、通し壁のうち薄いほうの厚さの半分だけ縮める（上の規則1）。面が接するだけなら重なりとしないので、外壁の厚さちょうどの段差と隙間は作れる。二枚の壁に接する部屋と、二枚の中心線の間に中心線が収まる壁に接する部屋を付ける。Z字に接する二部屋では、一部屋の二枚の壁が、その間の短い共有の壁を挟んで重なるので、この規則で相手の部屋も付く。付ける部屋の組が同じものは一件にまとめ、隙間が最も狭い組の値を返す

これらに当たらなければ、離れた部屋、コの字、中庭も作る。この検査を通った住宅データを住宅データの検査が拒んだら、サービスの不具合として扱い、AIへは返さない。

この操作が作るIDは、操作IDのバイト列に対するFNV-1a（64 bit）の上位40 bitを10桁の小文字の16進にしたものを前に付け、`<前置き>:s1`（階）、`<前置き>:r<n>`（要求のn番目の部屋）、`<前置き>:w<n>`（境界と壁）、`<前置き>:v<n>`（頂点）とする。どの操作IDでも32バイト以下に収まる。同じ操作IDと入力からは同じ住宅データを作るので、Workflowの再試行は同じ結果に収束する（4.6）。別の操作からは別のIDになり、置き換えた後の住宅で、古い壁のIDが別の壁を指さない。40 bitの値が衝突して同じ住宅でIDが重なった場合は、住宅データの検査が `DuplicateId` で拒む。前置きの計算を変えると再試行中の操作のIDが変わるので、計算を変えるときは操作の版を分ける。

### 3.2 窓・ドア・屋根・階段の表現

開口は、取り付け先の壁ID、壁上の位置、幅、高さ、床からの高さ、種別、見た目を持つ。開口の形状やドアの開き方など、表示に必要な情報を別に持つ。

壁の移動（3.1）では、開口は基準の端からの距離を保つ。動いた壁は長さが変わらないので、その開口は収まったままである。伸び縮みした壁の開口がすべて元の位置で収まれば、どれも変えない。収まらない開口があれば、位置を、次に幅を変える。ずらすときは、動いた端に近い開口をできるだけ元の位置に残し、ほかの開口を動かない端の側へ押す。押す先が足りなければ、動いた端に近い開口も動いた端の側へ寄せる。全幅ではどう並べても収まらないときだけ幅を縮める。このときは、動いた端に近い開口を動いた端の側へ詰め、動かない端に近い開口から縮める。開口は、移動後に基準の端からの距離を保った位置の順に並べ、調整で互いを越えず、基準の端も変えない。床からの高さの範囲が重ならない開口（ドアの上の欄間の窓など）は、互いを押さない。幅の下限は、ドアが600 mm、窓が300 mmとし、元の幅がそれより狭ければ元の幅とする。下限でも収まらない開口があれば、開口を削除せず、開口ID、壁ID、使える長さ、下限を付けて移動を拒む。結果には、調整した開口ごとに、距離と幅の前後を含める。

開口は住宅用の操作で付け、変え、外す。付ける操作は、取り付け先の壁、位置を測る基準の端（始点か終点）、その端から近い側の枠までの壁に沿った距離、幅、高さ、床からの高さ、種別（窓か、吊り元と開く側を持つドア）を受け取り、開口を一覧の末尾に足す。開口のIDは3.1の部屋の配置の操作と同じ前置きを使い、`<前置き>:o1` とする。変える操作は、開口のIDと同じ欄を受け取り、取り付け先の壁を含めてすべての値を置き換え、IDと一覧の中の順を保つ。外す操作は開口のIDを受け取る。壁に付いた開口は住宅データから求めるので、外した開口は壁からも消える。知らない開口のIDは、そのIDと理由を付けて拒む。どの操作も、拒んだときは元の住宅データを変えない。

付ける操作と変える操作は、その開口が壁に収まり、同じ壁のほかの開口と重ならないことを確かめ、開口のID、壁のID、理由を付けて拒む。壁の長さは境界の両端の頂点の間の長さとし、基準の端からの距離と幅の和がこれを超える開口を拒む。床からの高さと高さの和が壁の高さを超える開口も拒む。重なりは、壁に沿った範囲と床からの高さの範囲でできる立面の長方形で判定し、両方の範囲が正の長さで重なるときだけ拒む。ドアの上の欄間の窓と、枠どうしや壁の端に接するだけの開口は許す。比べる値はどちらも座標と寸法から計算した値なので、3.4の許容差（0.001 mm）を拒まない側に使う。例えば、小数の座標から求めた長さは端にちょうど届く開口の和よりわずかに短くなることがあり、終点から測った開口を始点からの範囲に直すと、接するだけの二つの開口に丸めの重なりが出る。壁の端やほかの開口との間に最小の間隔は設けない。構造の適合判定は初回提供の対象外（1.3）で、接合部の留めにかかる開口は確定前の検査（3.6）で拒む。住宅データを作るときにはこの検査を行わないので、収まらない開口を含む保存した住宅も読める。確定前の検査と壁の移動は、同じ規則で開口を確かめる。壁の移動は、伸び縮みした壁で、この規則のうち壁に沿った範囲（端と重なり）を確かめる。

ドアは、取り付け先の壁の両側に部屋があればその二部屋をつなぎ、片側だけならその部屋の外への出入口になる。窓はつながりを作らない。

屋根は、覆う領域、形式、基準高さ、勾配、軒の出、素材を持つ。複数の屋根の接合も更新対象に含める。建物の外形変更で屋根だけが元の大きさのまま残らないようにする。

階段は、接続する階、昇り口・降り口、経路、幅、段の構成、踊り場・回り段、床開口を持つ。段板の意匠は、段板ごとの座標系で書いた加工（3.5）として持つ。手すりは別の部品として関連付ける。経路や寸法の変更時は、段板ごとに加工を当て直し、手すりを引き継ぐ。CADの一つの立体へ置き換えて、上下階の接続情報を失う扱いにはしない。

### 3.3 家具・素材・敷地・隣家の表現

家具・造作などの物体は、物体自身の座標系で書いた形、置き場所、素材、参考画像への参照を持つ。基準寸法は欄に持たず、足し合わせる立体の範囲として形から求める。形は3.5の自前の型で持ち、物体の座標系の軸に平行な平面（xy・xz・yz）に書いた輪郭を、残る軸の正の向きへ押し出した立体の列とする。立体は先頭から順に足し合わせるか切り取り、先頭は足し合わせとする。物体の座標系は、置き場所の点を原点とし、+zを上、+yを正面とする。置き場所は、部屋に置くなら階・平面上の位置・向き（平面のx軸から物体のx軸への反時計回りの角度）、壁に付けるなら壁ID・基準の端・面の役割・基準の端からの距離・床からの高さとする。壁に付けた物体は正面をその面の外へ向け、形の範囲が壁の長さと高さに収まらなければ、住宅データを作るときに拒む。所属する部屋は改訂ごとに位置から求め直し、固定の値として持たない。部屋に置いた物体は、同じ階で置き場所の点を内法の輪郭（輪郭の上を含む）に含む部屋に属し、どの部屋にも入らなければそのことを返す。壁に付けた物体は、その面の部屋に属する。物体は住宅のボディに触れずに組み立て、置き場所へ動かす。部屋の広さが変わっただけで家具を拡大しない。2Dの外形は、置いた後の3Dから生成する。

素材は、色、柄の画像または生成パラメータ、実寸の柄の大きさ、向き、適用する部品・面の役割を持つ。壁の伸縮で木目やタイルの大きさまで伸びない初期設計とする。参考画像と、実際に表示に使う素材データを区別する。

敷地は境界、寸法、地域・方位、道路を持つ。隣家は配置、形、高さを持ち、室内の間取り情報を要求しない。入力には画像と会話を使い、確認済みの寸法と推定値を区別して保存する。形・配置は後から変更できる。

### 3.4 寸法・面積の計算と表示基準

長さはmm、面積はm²で表す。面積は座標からmm²で求めて持ち、表示するときにm²と畳へ直す。軸に平行で座標が整数mmの輪郭なら、面積は誤差なく求まる。寸法を固定のマス目へ丸めず、任意の値を指定できるようにする。AIが生成時に目安となる寸法を使うことは許容する。

部屋面積は壁の内側の床領域で求める。部屋の各境界を、その部屋の側の壁の側面まで内側へずらした線を、3.1の節点の規則でつないで内法の輪郭とする。一直線から3度以内で続く二本は境界の向きを二等分する線で切り、部屋の側のオフセットが違えば切り口に段ができる（規則3）。それより角度のある二本は、側面の交点で出会う（規則2）。通し壁で止まる壁の側面は、通し壁の側面か、厚さの変わる通し壁の切り口で止まる（規則1）。ほかの壁に隠れて床に面さない側面は除き、その前後の側面を交点で出会わせる。同じ向きに出る二本の壁、部屋の角の内側に入る壁、床が残らない部屋は、要素IDと理由を付けて返し、面積を出さない。開口は輪郭を変えないので、ドアの敷居部分はどの部屋の面積にも入らず、重複加算しない。床のない階段開口などを除く処理は6.3で加える。参考畳数は内法面積を1.62 m²で割って表示し、換算基準を明記する。丸めは表示時だけ行う。

3Dとの照合では、すべての壁のボディを床の高さへ投影し、部屋の内点を含む領域の面積と比べる。壁を部屋側へ広げる加工のように、部屋の輪郭を変える加工がある部屋は、面積と2Dの輪郭をこの投影から求める。部屋のIDと境界は住宅データのまま保つ。

建物全体は各階の参考面積を別に算出する。外周壁は、片側だけに部屋がある境界の壁とする。その中心線は、境界から部屋の側へ（部屋の側のオフセット−外側のオフセット）÷2の位置にある。初期設計では、外周壁の中心線を規則2と規則3でつないでたどった輪で囲む領域から床のない部分を除き、階ごとの値と合計を表示する。中庭のように囲まれた外は含めず、内壁は参考面積を変えない。内法の部屋面積の単純合計とは区別する。この計算を法定床面積の判定へ広げない。

幾何計算の許容差は長さ0.001 mmとする。同じ形を別の方法で求めた二つの結果は、一方のどの点も他方から0.001 mm以内にあれば一致とみなす。面積では、輪郭の周長に0.001 mmを掛けた値以内の差を一致とする。この値は、SolidCraftが同じ点とみなす距離（10⁻⁶ mm）より3桁大きく、人が指定する寸法の単位（1 mm）より3桁小さい。座標の上限の10⁷ mmでもf64の刻みは約2×10⁻⁹ mmで、この許容差より十分小さい。試験の期待値との比較と3Dとの照合は、どちらもこの判定を使う。輪郭の計算そのものは許容差を使わず、入力の値だけで分岐する。

面積はm²の小数第2位まで、参考畳数は小数第1位まで表示する。どちらも求めた値の下の桁を切り捨てる。表示は求めた値を超えないので、部屋を実際より広く見せず、表示した畳数に1.62 m²を掛けた値は内法面積を超えない。参考畳数は、丸めた面積ではなく求めた面積から直接出す。例えば内法4,410×4,500 mmの部屋は19.845 m²・12.25畳なので、19.84 m²・12.2畳と表示する。許容差と表示桁は、特定の例を通すために変更しない。畳換算の出典は付録Cに記す。

### 3.5 SolidCraftの形状との対応、変更・削除時の引き継ぎ

住宅データを正とし、住宅が生成するSolidCraftのフィーチャーと対応表は変更ごとに作り直す。住宅の値とCADパラメータを別々に更新して同期する方式は採らない。対応表には住宅要素ID、要求内で生成したCAD要素の識別子、壁のどの部屋側か・外側かを示す面の役割を記録する。壁一つの押し出し結果は一つのボディとし、分割する操作では住宅側でも壁IDを分ける。CADの面名・面番号や表示名を永続的な識別に使わない。

住宅の平面の座標は、xを東、yを北、zを上とする右手系とし、そのままSolidCraftの座標に置く。3.1の「上から見て反時計回り」は、この座標で符号付き面積が正の向きである。壁は、住宅側が決めた平面形を階の基準高さから壁の高さまで押し出し、ボディ名を境界のIDとする。床は部屋ごとに、境界の列がつくる多角形を基準高さから下へ150 mm押し出し、ボディ名を部屋のIDとする。この厚さは、6.3で床領域を加えるまでの表示上の値である。開口は、壁に沿った範囲と床からの高さの範囲を、取り付け先の壁のボディだけから切り取る。窓のガラスやドアの板のボディは作らない。対応表は、開口には切り取りのフィーチャーを記録し、ボディは名前で要素に結び付ける。切り取りや分割で分かれたボディは、分かれる前のボディの要素に結び付ける。二つ以上のボディに分かれた壁と、ボディが残らない壁・床は、3.6の検査のために報告する。表示データのボディは、住宅データの一覧の順に壁、床と並べる。

AIが壁や段板に加えた加工と、家具・造作などの物体も住宅データに含め、SolidCraftの文書は保存しない。住宅データは加工と物体の形を、CADに依存しない自前の型（スケッチの線・円弧、押し出し、切り取りと足し合わせなど）で持ち、`crates/modeling` がSolidCraftのコマンドへ変える。加工の形は取り付け先のボディに含め、物体は物体ごとのボディとして対応表に記録する。

同じ要求の一括内では、前の評価キャッシュを新しいSessionへ引き継ぐ。SolidCraftの公開フィールド `Model.cache` の共有が可能であり、住宅の再生成でも利用する。入力が同じフィーチャーを再利用できるよう、要求の始めは住宅データの各一覧の順に、壁、開口の切り取り、床の順で作る（3.1）。要求の中で作り直すときは、形状の側が直前に作った生成順を手元に持ち、残った要素の順を保ち、消えた要素を除き、新しい要素を末尾へ足す。開口の切り取りは取り付け先の壁より後に置く。住宅データは種類をまたぐ順を持たないので、編集の順が違っても、住宅データが同じなら同じ形と同じ表示データになる。生成順とキャッシュは結果の正しさの前提にせず、要求の終了時に破棄できるものとする。

壁の外観は、壁IDと部屋側・外側の役割に対して保持する。住宅データは壁の色を、壁ID、面の役割、色（sRGBの各8 bit）の組の一覧で持つ。面の役割は、その側に部屋があればその部屋のID、なければ外側とし（3.1）、壁の左右やCADの面の番号では表さない。この一覧の行はIDを持たず、壁IDと面の役割の組で面を指し、一つの面に一行までとする。部屋の削除・統合や壁の分割のように面の役割を変える操作は、同じ操作の中で色を引き継ぐか、削除したものとして返す。引き継がずに残した行は、住宅データの検査が拒む（3.1）。

色を指定する操作は、壁ID、面の役割、色を受け取る。その面に色があれば、一覧の中の順を保って色を置き換え、なければ一覧の末尾に足す。指定を外す操作は、壁IDと面の役割を受け取り、その面の行を除く。色のない面の指定を外す操作は、何も変えずに成功する。どちらの操作も、存在しない壁と、その壁にない面の役割を、壁IDと理由を付けて拒む。その壁にない面の役割を拒むときは、その壁が持つ面の役割を左側の面から順に付ける。どちらの操作も、色の一覧のほかは変えない。

CADでは、住宅データの輪郭と開口を使って、開口に覆われない領域の内点を選んで色を割り当てる。点を固定して開口の中から近傍の面を探す方式は採らない。割当て後は、解決されたボディ、接する部屋、面の範囲・位置・法線を照合し、同じ平面上にある別の部屋側へ色が移ることを防ぐ。加工や開口で面が分かれても、同じ壁と側の面をすべて塗る。割当てる面が残らなければ修復するか確定を止める。

部屋の配置・境界・壁・開口・階段の経路など、住宅の関係を変える変更は住宅用の操作を通す。それ以外の形は、加工と物体で表す。加工は壁や段板に付け、取り付け先の部品の座標系で書いたスケッチと、切り取るか足し合わせるかを持つ。壁の座標系は、基準にする端（始点か終点）からの壁に沿った距離と高さで表す。作り直すときは、取り付け先の座標系の平面にスケッチを置き、押し出しの深さと対象（取り付け先のボディだけ）を住宅側が決める。既存の辺や面を選ぶ加工（面取り、丸め、shell）は、選ぶ点を取り付け先の座標系で持つ。壁や段板に付く加工と壁に付けた物体は世界座標を持たず、取り付け先が動くと一緒に動く。色・素材の操作は形を変えない。変更時には、残す要素、生成し直す要素、面の役割が変わる要素を求め、見た目と関係を引き継ぐ。

加工は、ID、取り付け先の壁、基準の端、壁の座標系で書いた輪郭、切り取りか足し合わせかを持つ。輪郭は、始点と、直線または3点で決める円弧の区間の列で書き、最後の区間の終点を始点と同じ数にして閉じる。切り取りは壁の厚さ全体を抜く。足し合わせは、壁の厚さ全体に加えて、指定した面（両面か、面の役割で指す一方の面）から指定した量だけ外へ出す。押し出す範囲は、住宅側が壁の今の側面のオフセットから求める。

住宅データを作るとき（保存したJSONを読むときを含む）、加工と物体について次のものを、要素IDと理由を付けて拒む。存在しない壁・階・面の役割への参照、有限でない数、閉じていない輪郭、区間が足りない輪郭、長さ0の直線と退化した円弧、交わるか接する区間、足し合わせで始まらない物体の形である。加工の輪郭が壁の長さ（0から境界の両端の頂点の間の長さまで）と高さ（床から壁の高さまで）の範囲を出ることも拒む。壁の端を越えて材料を足す加工もこれに当たり、どちらの端から測っても同じ理由で拒む。開口と違い、加工の範囲は住宅データを作るときに検査する。開口には壁の移動で位置と幅を調整する規則があり、その規則を変えても保存した住宅を読めるように、作るときには検査しない。加工は調整しないので、範囲は保存した値だけで決まる。作るときに検査すれば、壁の長さを変えるどの操作も、範囲を出る加工を個別の処理なしに拒む。接合部にかかる加工は、開口と同じく確定前の検査（3.6）で拒む。

円弧を含む輪郭の検査には、3.4の許容差を使う。隣り合う区間が共有点から許容差以内で出会う点は交わりとせず、接する直線と円弧を許す。中心の距離と半径の差がどちらも許容差以内の二つの円弧は同じ円の上にあるとし、範囲が重なれば交わりとする。ほぼ一直線の3点で決まる円弧は、円の中心・半径・範囲のどれかが有限でないか10 kmを超えれば、退化した円弧として拒む。

| 変更             | 引き継ぎのルール                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 壁の移動・伸縮   | 部屋・面積・開口・関連する形を更新し、壁と面の見た目を維持する。壁に付いた開口・加工・物体は、基準の端からの位置を保って動く                                       |
| 壁の分割・統合   | 新しいボディへ素材と面の役割を引き継ぎ、開口・加工・物体の取り付け先を壁上の位置で振り分ける                                                                       |
| 壁の削除         | 取り付いた窓・ドア・加工・見た目を一緒に削除し、削除したものを操作結果で返す。壁に付けた物体は、その時点の位置のまま部屋に置いた物体へ変える。部屋の関係を更新する |
| 部屋の削除・統合 | 家具は原則残す。位置を保ち、所属する部屋を求め直す。配置が成立しなければAIが調整・相談する。家具ごとの削除指示は尊重する                                           |
| 家具・階段の変更 | 取り入れた特徴と見た目を維持し、位置・寸法・接続に必要な部分を調整する。段板ごとの加工は、階段の移動や段の構成の変更で段板ごとに当て直す                           |

面の対応が解決できない場合は、誤った面へ色を移したり既存の指定を黙って消したりせず、編集を修復する。修復できなければ案の確定を止める。

### 3.6 案を確定するための整合性条件

| 判定               | 対象                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| 確定を止める       | 不正な参照・数値、自己交差や意図しない部屋の重なり、住宅とCADの対応不良、2D・3D・面積の不一致        |
| 確定を止める       | 壁の範囲をはみ出す開口、出入口をたどれない部屋、上下階につながらない階段、階段を塞ぐ床などの接続不良 |
| 確定を止める       | 対応範囲外の形、維持すべき見た目や部品の消失、設定済みの敷地からの建物のはみ出し                     |
| 確定を止める       | 取り付け先を変えなかった加工、どの住宅要素にも対応しない立体、塗るべき面の塗り残し                   |
| 説明して提示できる | 家具配置の窮屈さ、動線・使い勝手など、空間やデータの不整合には至らない懸念                           |

壁では、留めが壁長を超える形、自己交差または有限でない輪郭、一つの壁から二つ以上のボディができる形、壁の輪郭・高さの範囲をはみ出す開口を確定前に拒む。開口は端部の留めや接合相手の壁まで考慮し、自分の壁だけを切って隣の壁を開口内に残さない。壁間の意図しない重なりとすき間も検査する。体積の照合、SolidCraftの評価エラーがないこと、閉じたボディであることだけでは合格にしない。加工を当てた後の壁にも、同じ条件を適用する。

住宅の決まり（参照、壁の接合、部屋の境界、階段の接続）はCADを呼ぶ前に検査し、形を作った後に3Dを検査する。どちらかで止まったら、前の住宅データを残す。

敷地の判定には屋根の軒などの建物の張り出しも含める。敷地未設定では検査しない。仮の敷地にも同じ条件を適用し、仮置きであることを示す。収まらなければAIが配置・寸法・階への配分を調整するか相談する。

検査結果は要素ID・理由・修正に必要な情報を返す。AIが「修正した」と述べただけでは合格にしない。形を扱う部分の幾何検査と、使い勝手についてのAIの判断を分ける。

## 4. システム設計

### 4.1 全体構成とCloudflare各サービスの役割

| 部分               | 採用する構成と役割                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| Web画面            | React・TypeScript・Vite。Workers Static Assetsから配信する                                          |
| 3Dビューア         | Rust/Wasm。SolidCraftのgeom・viewport・viewport-gpuを利用し、表示とカメラ操作を受け持つ             |
| ログイン           | Cloudflare Access。招待したメールアドレスへの認証コード                                             |
| 公開API            | WorkersのTypeScript。認証、所有権確認、入力検査、保存データの読取、処理の受付                       |
| 管理データ         | D1。ユーザー、案件、パターン、会話、履歴、ジョブ、費用の記録                                        |
| 大きいデータ       | R2。住宅データ（加工と物体を含む）、表示データ、画像、処理途中のチェックポイント                    |
| パターンの実行管理 | Durable Objects。D1の待機列から実行権を取り、Workflowの開始・照合、停止・再開、進捗の通知を調整する |
| ジョブの進行       | Workflows。一指示のAIとの往復、形状操作、検査、確定を段階として進める                               |
| 形状処理           | Cloudflare Containers上のRustサービス。住宅操作とSolidCraftのSessionを実行する                      |

ブラウザはAIや形状処理サービスへ直接接続しない。Workerを入口にし、Workflowが必要な形状処理をContainerへ依頼する。カメラ操作はブラウザ内で完結する。Containersへ接続するためのDOと、パターンの進行を管理するDOは、役割と識別子を分ける。パターンの進行を管理するDOはパターンIDを名前にし、ジョブの状態を持たない。WorkflowはWorkerの `exports` に `type: "workflow"` で宣言し、パターンのDOが `ctx.exports` から作る。Workflowの名前はアカウントの中で一意なので、環境ごとに別の名前を付ける。形状処理は、パターンごとの接続用DOとそのContainerで行う。

初期構成にCloudflare Queuesは追加しない。順序と待機列を保存データで管理し、Workflowsの再開機能を使う。コンテナのメモリ・ディスクと、Workflowの保持状態を、案件の恒久保存先にはしない。

Workerの依存は、層に属さない `apps/worker/src/compose.ts` で構築する。APIは `serviceDeps(env, runtime)`、パターンのDOは `patternCoordinatorDeps(env, workflow, runtime)`、ジョブのWorkflowは `jobWorkflowDeps(env, runtime)` を使う。DOには、実行権の取得、activeなジョブの参照の読取り、Workflowの開始だけを渡す。Workflowには、実行権の復元と、実行権を受け取る確認・確定・失敗の記録・snapshotの保存、形状処理、AIとの往復、パターンのDOを起こす関数だけを渡す。組み立て関数をimportできるのは `api/app.ts`・`objects/pattern-coordinator.ts`・`workflows/job-workflow.ts` だけで、この3つも元の層のimportの制限を受ける。サービスはDOのnamespaceではなく、型付き `GeometryInstance` を受けて `GeometryApi` を返す関数に依存する。インスタンス名の導出とRPCのretryable/overloaded例外からunavailableへの変換は `geometry/geometry-client.ts` に集める。サービス基盤のジョブは、パターンごとの接続用DOのインスタンス（キー `{ kind: "pattern", patternId }`、名前 `pattern:<パターンID>`）でContainerを呼ぶ。インスタンスのキーを加えるときも導出はこのファイルに置き、呼び出し側はDOの名前を組み立てない。

内部ルートは `geometry/` の `callGeometry` で呼び、成功のバイナリまたはJSON、エラー本文、ストリームのサイズ上限と中断を共通処理する。ルートとメソッドは生成された定義を使い、タイムアウトは同じモジュールの表で管理する。形状処理の結果を再試行と失敗に振り分けるのは、ジョブが呼ぶ `services/geometry.ts` である。公開APIは形状処理を呼ばない。

Workerの内部は、`api/` から `services/` を呼び、`services/` は外から渡された保存の操作（`storage/` が作る `Store`）または形状処理用の `geometry/` を呼ぶ。AIとの往復は、外から渡された `ai/` の実装を呼ぶ。`services/` から `storage/` と `ai/` へのimportは型だけにする。`objects/` と `workflows/` は `services/` だけを呼び、`storage/`・`geometry/`・`ai/` は他の層をimportしない。`api/` から `geometry/` への型だけのimportを例外として許可する。許可先は `scripts/check/boundaries.ts` のWorker層の表で管理し、同じ層の内部とこの例外を除いて、表にない層間importを拒否する。`apps/worker/src/` 直下にディレクトリを追加するときは、この表にも層を宣言する。直下のファイルは層に含めない。`storage/` はHTTPの `Request`・`Response`・`fetch`・`Headers` を使わず、API応答の型・スキーマも使わない。

| `services/`  | 業務の判断（初期名の決め方、要求を識別する項目、条件が成り立たなかった理由の判定）。時刻とIDは外から受け取る                                                                                                                    | Request・Response・SQL                                    |
| `objects/`   | パターンごとの調整DO。起こされるとアラームを予約し、アラームで `services/` を呼んでD1から実行権を取り、そのジョブのWorkflowを開始する。ジョブの状態を持たない                                                                   | Containerへの接続処理、D1・R2の直接の読み書き             |
| `workflows/` | ジョブのWorkflowと、その作成のアダプター。段階の順序・名前・再試行の方針は `services/` が持ち、この層はWorkflowの `step` を渡してログを書く                                                                                     | 業務の判断、Containerへの接続処理、D1・R2の直接の読み書き |
| `geometry/`  | Container接続用DO。起動、準備確認、内部認証、転送と内部APIの呼出し                                                                                                                                                              | 業務の判断                                                |
| `storage/`   | D1・R2への読み書き。条件付きの書込みと冪等性の記録を、操作ごとに名前を付けた関数で原子的に行う。採番のように同じトランザクションの中でしか決まらない値は、`services/` から受け取った材料（初期名の接頭辞など）でSQLが組み立てる | HTTP、業務の判断                                          |
| `ai/`        | AIとの一回の往復。提供元によらない要求・応答の型、環境ごとの実装の選択、台本のAI。提供元ごとの接続（要求の組み立て、応答の解析、失敗の分類）もこの層に置く                                                                      | 業務の判断、再試行の方針、D1・R2・Containerへの接続       |

`ai/` の往復の型は、提供元のSDKやAPIの型に寄せず、独自に定める。会話は、システムの指示、ツールの定義、最初の利用者の発言と、アシスタントの発言とそれへの返事の組の列からなる。後の要求は、前の要求の内容を変えずに組を足すだけにする。アシスタントの発言は、本文、ツールの呼出し、思考の部分を、モデルが返した順の一つの列として持つ。思考の部分は提供元の形のまま持ち、中身を解釈せず、作った実装だけが読む。Claude Opus 5.5は、思考のブロックを変えた、並べ替えた、一部を落としたアシスタントの発言を400で拒む。そのため、発言は受け取ったとおりに次の要求へ戻す。発言の列は `ai/` の実装だけが作れる型にし、絞り込んだ列や組み直した列を型の検査で拒む。発言には、それを返した試行の利用量（キャッシュに載らなかった入力、キャッシュの読込み、5分と1時間のキャッシュの書込み、出力のトークン数）を付ける。次の試行の費用の見積もりは、この利用量から始める（5.2）。モデルが読み書きするJSON（ツールの入力と入力スキーマ）は、Workflowの `step` の結果に入れられるように、JSONの文字列で運ぶ。一回の往復は一度だけ試み、再試行は呼び出す側のWorkflowの `step` が受け持つ。失敗は、例外でなく結果の値で返す。

台本のAIは、決まった応答の列を返す実装で、テストとローカルの開発で使う。会話にある組の数から何番目の応答を返すかを決め、状態を持たない。そのため、Workflowが別のisolateで再開しても、`step` を再試行しても、同じ応答を返す。戻された発言が自分の返したものと違うとき、ツールの呼出しに結果が一つずつ揃わないときは拒み、台本の終わりを越えた要求は失敗として返す。システムの指示とツールの定義が要求の間で変わらないことは、状態を持たないので確かめない。使う実装は `compose.ts` が `ENVIRONMENT` で選び、`local` と `staging` だけが台本のAIを使える。それ以外の環境で提供元の接続がなければ、往復のたびに失敗する実装を使う。選ぶ処理は例外を投げないので、AIを呼ばないWorkflowの処理はどの環境でも動く。

`services/` を分けるのは、Workflow・Durable Objectが同じ業務の判断をHTTPを通らずに使うためである。`services/` は書込みの文を組み立てず、`storage/` の操作（例：`store.projects.renameOnce`、`store.revisions.commit`）を呼ぶ。文どうしの条件を確かめないまま、任意の文の列を一括で確定させる仕組みは作らない。D1のbatchでは条件付き更新が0件でもエラーにならず、後続の文が確定してしまうためである。`storage/requests.ts` の `OnceBatch` は中身と要求キーを非公開の欄に持つクラスとし、型だけを公開する。生成入口は作成用の `createOnceStatements` と更新用の `updateOnceStatements` の二つに限定し、記録の文を作る `recordStatement` は公開しない。各生成入口で要求キーとSQL部品を一度ずつコピーし、そのコピーからすべての文を組み立てて凍結する。バインドの値は文字列・数値・真偽値・nullの原始型に限り、組を作るときに確かめる。配列・TypedArrayなどの参照型は、文ごとの値の変化を防ぐため生成時に拒否する。クラスとprototypeも凍結し、コンストラクタはモジュール内だけで持つtokenを検査する。`runOnce(db, schema, batch)` は組の要求キーを使い、本物のクラスの非公開欄を持たない値をSQLの実行前に拒否する。Proxy、spreadやstructuredCloneの写し、型だけを偽造したオブジェクトにはこの欄がない。複数の変更の文どうしの結び付けは操作ごとに設計する。複数の条件を含む操作は、各条件が後続の文を止めるように、その操作専用のSQLとして設計する。後続の文の条件は、行の有無や値といったデータの状態で書き、`changes()` のような接続の状態には依存しない。依存してよいのは、D1の文書が保証している次の性質だけである：batchが一つのトランザクションとして順に実行され、後の文が前の文の書込みを見ること、途中の文が失敗するとbatch全体が取り消されること、一つのデータベースが一度に一つのクエリを処理すること。冪等性の記録と変更は、この条件で結び付ける。作成は `createOnceStatements` が変更の文の後に記録を置き、対象の表に指定したIDと要求の所有者IDが一致する行があることを記録の条件にする。呼び出し側は変更の文、対象の表、新しいID、結果の式を渡し、記録の条件や順序は指定しない。更新は `updateOnceStatements` で記録を先に置き、一度だけ書いた前提条件を、記録と更新の両方の条件にする。

作成の証拠の行は、その要求の文が新しく作ったものでなければならない。既存のIDを証拠にすると、変更のない記録が残る。作成の文は、何かを作るときには必ず証拠の行も作るように書く。そうでないと、記録のない変更が残り、再送で繰り返される。これらのSQLの意味と、結果のSQLが正しい結果を作ることは、型では確かめない。所有者条件と併せて実際のD1に対するテストとレビューで確かめる。`requests` 表への手書きの書込みはこの型では防げず、[#65](https://github.com/wakamenori/instant-madori/issues/65)で禁止する。

DBの行は、テーブルごとに一つのSQLの `json_object` で読み、`storage/` で共有スキーマにより検証してから返す。型引数による決めつけで行を扱わない。業務上の結果（見つからない、版の競合など）は例外でなく判別可能な結果として返し、`api/` がエラーコードへ対応付ける。予期しない例外だけを500とし、本文を含めずに記録する。

Webのコードは開発用の `scripts/` をimportしない。Viteの設定だけは、ローカルの認証プロキシに使う `scripts/dev/` をimportできる。WebからのWasmバインディングの読込みは `apps/web/src/viewer/wasm.ts` に集め、同じ `viewer/` 直下の `*.test.ts` だけはバインディングを直接importできる。`apps/geometry` には、UIツールキット（egui系・eguiの下位のepaint系・emath・ecolor・eframe・winit）とGPUの描画（wgpu系）を含めない。UIの有無は、crateの名前ではなくツールキットのcrateで判定する。UIを持たない文言の目録 `solidcraft-ui-text` は、engineを通して含まれてよい。サービスはSolidCraftのpluginを実行しない。そのため、ルートの `solidcraft-engine` は既定のfeatureを外し、Containerにwasmtimeとcraft-plugin-wasmを含めない。

開発スクリプトから計測への依存は、`scripts/shared/docker-slots.ts` が枠の記録を渡す `metrics/hook/docker-slot.ts` に限る。

TypeScriptのアプリと共有定義のimport境界は、TypeScriptのモジュール解決後の参照先ファイルで判定する。静的import、再export、文字列リテラルの動的import、import型、`import = require`、型の参照ディレクティブとモジュール拡張を対象にする。動的importの引数を囲む括弧は外し、参照先のqueryとfragmentは除いて解決する。解決できない参照は失敗にする。Node.jsの組込みと、対応するworkspaceが依存として宣言した外部パッケージだけは、解決できなくても許可する。workspaceのパッケージはこの例外に含めない。環境が宣言するambient moduleは、その宣言のファイルで判定する。相対パスの資産は実ファイルの存在を要求する。ファイルの同一性はsymlinkをたどり、OSの実パスで確かめる。大文字小文字を区別するファイルシステムでは、綴りの違う参照は未解決として拒否する。検査はESLintの自動修正と整形の後に実行し、pre-commitでもステージしたTypeScriptファイルを対象に実行する。

動的importの参照先は文字列リテラルに限定する。`import.meta.glob` と `new URL(..., import.meta.url)` による読込みは禁止し、テスト（`*.test.*` と `tests/` 内のファイル）だけは、フィクスチャやWasmを読むために後者を許可する。型の再exportは `export type` 宣言で書く。テスト以外のファイルは `*.test.*` と `tests/` 内のファイルをimportしない。テストも参照先の解決は必要とし、表でテストにも適用すると定めた境界は維持する。層に属さないファイルを経由した再exportは追跡しない。

`apps/` は起動・デプロイするもの、`crates/` はRustの機能をまとめたモジュール、`packages/` はJS/TS側から共有する定義を置く。`apps/geometry` は `crates/modeling` を呼ぶ入口とし、住宅の計算やCADとの対応をHTTP処理に散らさない。

`crates/housing` が直接依存してよいのは serde・serde_json・schemars だけとし、画面・HTTP・Cloudflare・CADへは依存させない。この一覧は、`scripts/check/boundaries.ts` の `housing-dependencies` の行と一緒に変える。`crates/modeling` は住宅モデルとSolidCraftのengine・docを利用する。kernelの機能（体積の計測など）は、engineが再exportする `solidcraft_engine::kernel` から使い、kernelには直接依存しない。engineはkernel全体を再exportし、kernelにはfeatureがないので、直接依存しても使える機能は増えない。modelingはsolidcraft-ioにも直接依存し、`external-workspace` featureを有効にする。このfeatureは、評価キャッシュの誤った再利用を防ぎ、ioのbuild.rsにこのリポジトリのgitの状態を読ませない（5.1）。`solidcraft-` で始まるcrateのうち、modelingが直接依存してよいのはengine・doc・ioだけとし、この一覧は、`scripts/check/boundaries.ts` の `modeling-solidcraft` の行と一緒に変える。`crates/viewer` はgeom・viewport・viewport-gpuを利用し、wgpuで描く。`solidcraft-viewport-egui` は使わない。ビューアには編集エンジン（modeling・engine・doc・kernel・io）とUIツールキット（egui系・eguiの下位のepaint系・emath・ecolor・eframe・winit）を含めず、依存を持たない `crates/display` の表示データで接続する。geomがsolidcoreに依存するため、Cargoの依存グラフではsolidcoreもビューアに届く。利用者に届くコードは、`pnpm check --full` がreleaseのWasm（wasm-bindgenの前）の名前セクションとexportの名前で確かめる。各関数を本体を定義したcrateに数え、CADカーネル（solidcore・solidcore-ops）・編集エンジン・UIツールキットの関数があれば失敗する。名前を変えない関数（`#[no_mangle]`・`#[export_name]`・wasm-bindgenのexport）も、crateに数える。wasm-bindgenのexportは、名前の末尾のハッシュを、`__wasm_bindgen_unstable` セクションにあるcrateの識別子と照らす。それ以外は、検査が持つcrateごとの一覧で、名前とexportの有無を照らす。どちらにも当たらない名前は失敗にする。一つの関数に複数の名前があれば、表には一度だけ数え、族の判定にはすべての名前を使う。禁止する族は、ビューアの依存グラフの行と `viewerWasmBoundary` から導く。crateごとの関数の数とコード量は、Markdownの表でログに出す。`crates/modeling` が符号化し、`crates/viewer` が復号する。`crates/geometry-api` は形状処理の内部APIを定義し、TypeScriptの定義を `packages/contracts/src/generated/geometry-internal.ts` へ生成する。公開する表示メディア型は同じ生成処理で `packages/contracts/src/generated/display.ts` に出し、`@madori/contracts` から公開する。WebとViteの設定は内部API定義をimportせず、`packages/contracts` への相対パスでの参照も使わず、公開した `@madori/contracts` から参照する。公開入口への参照もパッケージ名に限るのは、宣言した依存を通すためである。相対パスに置き換えると、Knipがパッケージの依存宣言を未使用と判断して削除でき、pnpmの依存の図からWebとcontractsの関係が消えてしまう。

内部API本文は `crates/geometry-api` のRust型にschemarsを適用し、インライン化したJSON Schemaからjson-schema-to-zodでZod検証とTypeScript型を生成する。`pnpm generate:geometry` で定数と本文を一緒に更新し、RustとNodeのテストが生成結果のずれを検出する。再帰型と参照が残る型は生成時に拒否する。結果の共用体は `kind` を判別子とする。固定幅整数には範囲を付け、JavaScriptで正確に表せない64/128ビット整数は文字列で運ぶ。ポインター幅に依存する整数も生成時に拒否し、通信には固定幅の型を選ぶ。Optionは `skip_serializing_if = "Option::is_none"` でNoneを省略し、受信時は省略とnullを許す。各ルートに本文型のスキーマ生成関数を登録し、要求・応答のスロットから方向を導出する。エラー本文はルートごとに登録せず、プロトコル共通のスキーマ・メディア型・本文上限を定義し、Rustのエラー応答とWorkerの検証で使う。同名の本文を異なる契約で登録すると生成を停止する。要求はDeserialize契約で生成し、オブジェクトの未知フィールド拒否を生成時に検査する。応答はSerialize契約で生成し、共有型に指定された未知フィールド拒否を応答スキーマから再帰的に除き、追加フィールドを許容する。ルートにはHTTPメソッドと要求・応答本文の形式（なし、JSONのスキーマと本文上限、バイナリのメディア型と本文上限）を登録し、Workerの受信方針をそこから組み立てる。

住宅データはRust側で定義し、通信に必要な型とスキーマを生成してJS/TS側へ渡す。住宅データの型のJSON Schemaは `crates/housing` がschemarsで導出する。`crates/geometry-api` は同じ形の型を写さず、その型を内部API本文とAIの操作の入力に組み込む。WebとWorkerの共通の通信定義も `packages/contracts` で管理し、同じ型を両側で独立に手書きしない。

ルートのREADME、AGENTS、開発設定は本サービス向けに整える。SolidCraft由来の資料と開発設定は取り込み領域に保持する。本計画書は `docs/plan.md`、検証記録と、画像を除く証拠は `docs/verification/` に置く。Issue、PR、検証記録に貼る画像は、main と履歴を共有しない追記だけの `images` ブランチに置き、画像を加えた commit に固定したリンクで参照する。

SolidCraftには、形状操作、フィーチャー評価、編集可能な設計データ、ボディ・面の外観、表示メッシュ、基礎的な描画を担当させる。住宅の意味、案件、指示単位の履歴、WebサービスのAI実行は利用側で作る。

既存の通常の描画経路に、素材画像や日差しの影がそのまま揃っているとは扱わない。4.8の追加実装を計画に含める。既存クレートを変更する場合は、専用機能との境界を保ち、変更理由と依存する住宅機能を追えるようにする。

### 4.3 案件・会話・履歴・モデル・画像の保存構造

| D1の主な単位                | 保持する情報                                                                                               |
| --------------------------- | ---------------------------------------------------------------------------------------------------------- |
| User / Project              | 認証主体との対応、内部ユーザーID、所有者、案件名                                                           |
| Pattern                     | 案件ID、案件内の作成順                                                                                     |
| Revision                    | パターン、履歴内の順番、編集元・復帰元、案の名前、会話の区切り、snapshotへの参照                           |
| Snapshot                    | 所有者、R2のmanifestのキーとハッシュ、保存形式の版                                                         |
| Message / ConversationEvent | 会話の番号、指示・回答・AIの説明・選択肢付きの質問・知らせ、添付参照、関連する案・ジョブ、復帰や複製の記録 |
| Job / Operation             | 指示への参照、状態、編集開始時の案ID、実行世代、待機列を保留しているか、チェックポイント参照、操作IDと費用 |
| Asset / Usage               | 所有者、R2キー、用途・形式・サイズ・ハッシュ、API試行ごとの利用量・費用予約・確定額                        |

パターンの現在の案は、履歴の順番が最後の案とし、パターンの行には現在の案を指す列を持たせない。2.5のとおり、復帰も新しい履歴項目を末尾へ追加するため、最後の案と現在の案は常に一致する。指す列を別に持つと、二つが食い違う状態を表せてしまう。確定の条件「編集元の案が現在の案である」は、「そのパターンの最後の案が編集元である」として、案を追加する文の中で検査する。履歴の順番は、追加する文の中で既存の最大値に1を足して決め、`(pattern_id, number)` の一意制約で重複を防ぐ。

案のmanifestには、保存形式の版、住宅データ、素材・画像の参照、2D・3Dの表示データ、検査結果を結び付ける。住宅データを正とし、編集可能なCADデータと対応表は保存せず、読込・変更時に住宅データから再生成する。AIの加工と家具などの物体も住宅データに含める。ファイルを分ける場合も、同じ案のmanifestで内容とハッシュを固定する。manifestの版1は、表示データ（`crates/display` の形式）だけを結び付ける。6.2では、加工と物体を含む住宅データ等を加えて版を上げ、5.4のとおり読込時に旧版を移行する。R2への書込みはWorkerが行い、Containerは結果のバイト列を返すだけとする。D1のsnapshotの行はmanifestのキーとハッシュを持ち、読込時にmanifestのハッシュを、manifestが各ファイルのハッシュを照合する。

`snapshots` の行は、所有者、manifestのキーとSHA-256、形式の版を持つ。`revisions` の行は、パターン内の番号、名前、編集元、snapshotへの参照を持つ。形式の版は、読み書きできる版だけをDBのCHECK制約で許可し、版を増やすときは読込処理と制約を一緒に更新する。所有者と親の一致、および編集元が同じパターンに属することは、複合外部キーで保証する。

`messages` は種類、本文、パターン内で全種類に共通の会話の番号を持つ。本文はD1へ保存し、UTF-8で16,384バイトを上限とする。サービスは孤立したサロゲートと、JavaScriptの `trim()` で空になる本文を拒む。D1も本文のバイト数と同じ空白文字の集合をCHECK制約で検査する。本文はtrimせず、検査した文字列をそのまま保存し、要求内容のハッシュにも使う。会話の番号は追加する文のスカラー副問い合わせで既存の最大値に1を足して決め、`UNIQUE (pattern_id, number)` で重複を防ぐ。

入力（指示・回答）は、それを受け付けたジョブが `jobs.message_id` で指すため、message側の `job_id` はNULLにする。AIの説明と質問は、書き込んだジョブのIDを持つ。知らせはジョブに伴う場合だけそのIDを持つ。jobsとmessagesの生成列 `pattern_job` はパターンIDとジョブIDを連結し、その外部キーで別のパターンのジョブへの参照を防ぐ。関連する案は、そのジョブが確定した案を `revisions.job_id` から読む。質問だけが `choices` に選択肢の文字列配列をJSONで持つ。D1では配列であることと16,384バイトの上限を検査する。部分索引 `messages_inputs` は指示と回答だけをパターンと会話の番号で引けるようにする。

`jobs` は入力（指示または回答）のmessage ID、4.6の9状態、実行世代、実行開始時の編集元のrevision IDを持つ。受付時は `queued`、世代は0、編集元はNULLとする。messageとjobの所有者は親のパターンと一致させ、messageと編集元も同じパターンに属することを複合外部キーで保証する。入力のmessage IDはジョブ間で一意とする。`running`・`validating`・`committing` の行だけを対象にした `pattern_id` の部分一意索引で、一パターンの実行権を一件に限る。パターンには実行中ジョブを指す列を持たせず、ジョブの状態から読む。待機列はパターンと状態の索引で絞り、対応するmessageの番号で順序を決める。

待機列の保留（2.4）は、保留の原因になったジョブの行の `holds_queue`（0か1）で表し、パターンの行には持たせない。実行中のジョブを指す列を持たせないのと同じく、指す列とジョブの状態が食い違う状態を表せないようにするためである。`holds_queue = 1` を許すのは、CHECK制約でcancelled・failed・limited・awaiting_answerの行だけとする。`holds_queue = 1` の行だけを対象にした `pattern_id` の部分一意索引で、一パターンの保留を一つに限る。保留の原因は保留する行そのものなので、同じパターン・同じ所有者のジョブであることも保証される。保留は、activeなジョブをcancelled・failedへ変える文の中で、待機中のジョブがあり、ほかに保留がないときだけ1にする。この式は変更前の行を読むので、失敗の段階の再試行、終わったジョブへの停止、同じ要求の再送は保留を書かない。保留を解くのは、再開・取り消し、保留中に最後の待機中のジョブを止める停止、待機中のジョブがない保留を見つけた受付だけとする。保留中は実行権を取らないので、保留中のパターンにactiveなジョブはなく、待機中のジョブが必ずある。保留を書く文と読む文は `apps/worker/src/storage/job-queue.ts` にまとめ、ほかのファイルには列名を書かない。列は既定値0とともにマイグレーションで加えるので、既存の行と前の版のWorkerが加える行は保留しない。前の版のWorkerは保留を読まないので、版が混在する間やWorkerを前の版に戻した後は、前の版の停止が保留を解かずに待機列を空にすることがある。受付が待機中のジョブがない保留を解くので、その後に送った指示は保留されない。

`revisions.job_id` はその案を作ったジョブを指し、同じパターンのジョブだけを複合外部キーで許す。NULL以外のjob IDの部分一意索引で、同じジョブから二つの案を確定することを防ぐ。結果の案はこの列から読み、jobsには結果を指す列を持たせない。`(job_id, base_revision_id)` の複合外部キーでジョブの編集元との一致を検査する。jobsとrevisionsは、編集元がNULLかどうかを表す生成列 `base_is_null` も持ち、`(job_id, base_is_null)` の複合外部キーでNULLを含む一致も保証する。`conversation_number` はその案が取り込んだ会話の最後の番号を指し、`(pattern_id, conversation_number)` の複合外部キーで同じパターンのどの種類のmessageにも結び付けられる。既存の案とジョブを使わない保存では、この二列にNULLを許す。

AIの費用は、API試行ごとに一行を持つ `ai_attempts` で表す。行は試行ID、ジョブID、実行世代、予約額、見積もりの入力と出力のトークン数、予約の時刻を持つ。精算では、確定額、区分ごとの利用量（キャッシュに載らなかった入力、出力、キャッシュの読込み、5分と1時間のキャッシュの書込み）、精算の時刻を書く。精算の列は、すべてNULLか、すべて値を持つかのどちらかだけをCHECK制約で許す。数える額は、精算済みなら確定額、未精算なら予約額とし、生成列 `counted` で表す。数える月は予約の時刻の先頭7文字（UTCの年と月）とし、生成列 `month` で表す。予約と精算の時刻は `Date#toISOString()` の形に限り、`strftime('%Y-%m-%dT%H:%M:%fZ', …)` で同じ文字列に戻ることをCHECK制約で検査する。D1は50バイトを超えるLIKE・GLOBのパターンを実行時に拒むので、時刻の形を長いGLOBで検査しない。月ごと・ジョブごとの合計の行は持たず、`month` と `job_id` の索引で予約のたびに合計を求める。合計を別に持つと、試行の行と食い違う状態を表せてしまう。この表の列名は `apps/worker/src/storage/ai-cost.ts` にだけ書く。

指示の受付は、所有者を条件にしたmessageの追加、その新しいmessageを条件にしたqueuedのjobの追加、要求の結果の記録を一つのbatchで行う。`createOnceStatements` が新しいjobのIDと要求の所有者の一致を成功の証拠にする。同じrequest IDの再送はbatchを取り消して最初に記録した結果を返す。記録する結果は受付の応答が使うジョブID・message ID・会話の番号だけとし、指示の本文を複製しない。前の版のWorkerが記録した、messageとjobを丸ごと含む結果も、再送では同じ三つの値として返す。存在しないパターンと別所有者のパターンでは何も追加せず、要求も記録しない。

公開APIで読み書きする、所有者を持つテーブルには `owner_id` を直接持たせ、読み書きのSQLで必ず条件にする。親と所有者が食い違わないよう、親の `UNIQUE (id, owner_id)` を参照する複合外部キーで保証する。内部処理の書込みは所有者だけでは実行権を表せないため、job ID・実行世代などを必須の条件にする専用の操作として作る。

案件・パターンの `version` は、名前などの管理情報の変更だけで増やす。ジョブや現在の案の更新は別の条件で競合を判定し、名前の変更と互いに競合させない。待機列の保留はジョブの行にあるので、保留の変更はパターンの行を書かない。再開・取り消しは、保留の原因のジョブIDを期待する値にして競合を判定する。パターンの初期名の番号は、案件の行が持つ次の番号から作成と同じトランザクションで採番し、同時に作成しても重複させない。

変更要求の結果は `requests` に、利用者・request ID・操作名・要求内容のハッシュとともに保存する。結果は記録と同じ文の中でSQLで作って保存し、初回の応答と再送への応答を同じ内容にする。保持期間は5.4の回収と合わせて決める。

確定案のR2オブジェクトは変更しない。新しい案は新しいキーで保存し、D1の履歴へ追加することで現在の案にする。復帰・複製では不変の内容を共有してよいが、新しいパターンの履歴項目と、その後の会話・ジョブは独立させる。

snapshotのオブジェクトは、既存のキーへの上書きを拒む書込み（作成だけのput）で保存し、同じキーへの二度目の書込みを失敗させる。`apps/worker/src/storage/r2.ts` の `putNew` は、`onlyIf: { etagDoesNotMatch: "*" }` でこれを表す。Cloudflareのedge preview内で実際のアダプターをstagingのR2へ接続し、二回目の書込みの例外と、直接の条件付きputの `null` を確かめた書き方を使う。stagingへのデプロイ後にもこの検査を実行し、外側のREST APIで元のバイト列が維持されることと作業用キーの削除を照合する。この検査がREST APIを読む（GET）ときは、5xxの応答と接続の失敗（`fetch failed`）だけを、初回を含めて3回まで、1秒、2秒と待ってやり直す。一回の読取りの試行と待ちは、合わせて30秒に収める。上限に達したら、最後に受け取った結果で、これまでどおり失敗にする。4xx、本文の形の誤り、照合の結果、作業用キーの削除（DELETE）はやり直さない。ローカルのminiflareやremote bindingだけを、この振る舞いの証拠にしない。

保存内容を識別するsnapshot IDと、履歴項目を識別するrevision IDを分ける。復帰・複製で同じ内容を再利用した場合も、表示応答には閲覧対象のrevision IDを付け、古い履歴の表示と混同しない。

パターンは複製元、起点の案、会話の上限位置を記録する。複製元に後から増えた会話が複製先へ入り込まないようにする。会話の希望と、採用・取り消し・未実行の操作を分け、AI用の要約にもその区別を残す。

### 4.4 認証とユーザーごとのアクセス制御

WorkerはAccessのJWTの署名、発行元、対象アプリ、有効期限を検査し、発行元とsubjectの組で内部ユーザーへ対応付ける。メールアドレスは表示用で、変わっても同じ内部ユーザーとして扱う。ブラウザが送ったユーザーIDを所有者として信用しない。だれがログインできるかはAccessのポリシー（招待）で決め、Worker側は初回のログインで内部ユーザーを作る。

`staging` では、任意の設定 `ACCESS_VERIFIER_CLIENT_ID` がある場合だけ、`sub` が空文字列で `common_name` が設定したClient IDと一致するAccessのservice tokenを、一人の検証用ユーザーとして受け付ける。検証用subjectはAccessのUUIDと重ならない `staging:verifier`、表示用メールアドレスは `verifier@staging.invalid` に固定する。Client IDを更新しても発行元とsubjectの組は変わらず、同じ内部ユーザーになる。設定のない場合や一致しないservice tokenは403 `forbidden` にする。`staging` 以外にこの設定があれば、設定の誤りとして拒否する。

検証済みの認証主体は、storageへ依存しない `identity.ts` の `VerifiedIdentity` で表す。これは発行元・subject・メールアドレスをprivate欄に持つ、非公開コンストラクタのクラスである。検証した値をこの型へキャストできるのは `api/access.ts` だけで、`freezeIdentity` がその値から凍結したインスタンスを作る。インスタンス、クラス、prototypeを凍結し、欄の直接代入や `Object.assign` による書き換えを実行時に拒否する。既存の証拠をspreadした値はprivate欄を持たないため、型で拒否する。保存処理はこの証拠を要求し、同じ発行元とsubjectから検索・作成した利用者行を、非公開コンストラクタとprivate欄を持つ結果として返す。`authenticatedUser` は証拠とこの結果を要求し、保存層の関数がprivate欄の発行元とsubjectの一致を確認してから `OwnerId` を生成する。結果のオブジェクト上のプロパティやメソッドを上書きしても、private欄を読む処理は変わらない。このため所有者の生成関数のimport先は制限しない。普通の `User` や証拠なしの呼び出しは型で拒否し、別主体の証拠と保存結果の組み合わせは実行時に拒否する。

型へのキャスト、`resolved.constructor` を構築可能な型へキャストする偽造、嘘の型宣言までは型で防げない。ブランドへの直接キャストと `as never` は構文検査で拒否し、SQLの所有者条件と認証主体による検索は実際のD1を通すテストとレビューで確かめる。

Accessで認証済みであることと、利用者が意図した変更であることは別である。変更を伴うAPIは、設定した画面のOrigin（本番は一つ、ローカルはその回の `pnpm dev` の画面のポートを `127.0.0.1` と `localhost` で書いた二つ）のいずれかと完全に一致する要求だけを受け付け、JSONのボディに限定する。同じマシンで同時に動く別の回の画面からの変更は、Originが一致しないので拒否する。

ローカル開発とテストでは、生成した鍵で署名したトークンを同じ検査コードで検証する。ローカルの鍵は、環境名が `local` で、発行元が予約済みの `.invalid` ドメインの場合に限って受け付け、本番の設定に紛れても使えないようにする。開発時はViteのプロキシが受け取った認証ヘッダーを必ず置き換える。

案件・パターン・会話・案・添付・表示データ・進捗のすべてで所有権を確認する。R2は非公開とし、Worker経由または所有権確認後に発行する短時間のURLで配信する。ファイル名やR2キーを知っているだけでは読めない構成にする。

AIキーと内部サービスの資格情報はサーバー側に保存する。Containerは公開の編集APIとして使わず、認証済みの内部要求だけを受ける。接続用DOは起動ごとにランダムなトークンを作り、DOのストレージへ保存してContainerの環境変数へ渡す。Containerは `/healthz` 以外の内部要求でBearerトークンを検査する。DOの再起動後は保存したトークンで実行中のContainerを引き継ぎ、起動時のイメージが現在の設定と違う場合は置き換える。

### 4.5 AIに渡す情報と、呼び出せる操作

最初のモデルはClaude Opus 5.5、API IDは `claude-opus-5-5` とする。提供元ごとのAPI契約を接続層に分け、モデルを変更できるようにする。営業向けのモデル選択UIは設けない。

AIへ渡すのは、現在の案の住宅情報と要約、対象ID、関連する会話・参考画像、仮置きした条件、利用できる操作、検査結果である。長い会話は原文を保存したうえで要約・検索し、必要な情報を選ぶ。すべての画像・メッシュ・過去のCADデータを毎回送る構成にはしない。形を確認するため、現在の案や作業案の2D・3D画像を取得する読取操作も用意する。

| 操作群         | 担当する変更・取得                                                                 |
| -------------- | ---------------------------------------------------------------------------------- |
| 住宅操作       | 階・部屋・境界・壁・開口・屋根・階段の作成、変更、削除                             |
| 加工           | 壁と段板への形の加工。取り付け先の座標系で書いたスケッチと、切り取りか足し合わせか |
| 物体・周辺形状 | 家具・造作・隣家などの形づくりと、置き場所・寸法の変更                             |
| 外観操作       | 対象の色・素材・柄の大きさ・向きの変更                                             |
| 読取・検査     | 要素の情報、寸法、対応関係、表示画像、整合性検査                                   |
| 応答           | 変更の説明、仮置きの説明、質問、残る使い勝手の懸念                                 |

各操作には入力・出力スキーマを定める。住宅用の操作は、下位のCADコマンドをまとめて実行できる単位にする。加工は取り付け先のボディだけを、物体は自分のボディだけを変えられる操作にし、住宅の境界や階段の接続を迂回して壊せないようにする。壁や段板に付く加工は、世界座標ではなく取り付け先の座標系で書かせる。

AIは実行結果を受けて修正を続ける。確定はサービス側の検査を通した後に行う。モデル選定は間取り生成能力の実証を意味せず、実装と利用を通じて品質を改善する。

### 4.6 ジョブの進行・案の確定・停止・再試行・障害復帰

#### 受付から確定まで

1. Workerが入力と所有者を確認し、同じ要求の再送を識別するrequest IDを受け取る。
2. Workerが、認証済みの指示、queuedのジョブ、要求の記録を一つのD1のbatchで保存する。受付順はこの保存で決まる。保存の後に、受付の操作がパターンIDをパターンDOへ渡して起こす。同じ要求の再送でも起こし直す。起こせなければ500を返す。保存は残るので、同じrequest IDの再送は保存した受付結果を返し、もう一度起こす。
3. パターンDOは、起こされるとアラームを予約する。アラームの中で、自分の名前（`getByName` に渡したパターンID）を `ctx.id.name` から読み、D1から指示のmessage番号が最も小さいqueuedのジョブの実行権を取り、そのジョブのWorkflowを開始する。一つの条件付きUPDATEでrunningへ変更し、実行世代を1増やし、その時点の最新案を編集元に固定する。最初の案の前は編集元をNULLとする。running・validating・committingのジョブが既にあるか、待機列が保留中（4.3）なら取得しない。activeなジョブがあれば、その参照から同じ世代のWorkflowと照合する。保留中なら何も開始しない。保留の条件も取得と同じUPDATEの中で検査する。
4. WorkflowがAIへ必要な情報を渡し、操作要求を受け取る。
5. Containerが編集元またはチェックポイントの住宅データと操作の一括を受け、要求内の作業用Sessionで住宅由来のCADと対応表を再生成し、操作・検査・表示生成を行う。一括内では評価キャッシュを引き継ぐ。家のCADと対応表は要求内の派生物であり、保存対象は4.3に従う。
6. 操作結果と必要な表示データを保存し、プレビューを通知する。失敗した操作は作業用の直前状態へ戻し、AIへ理由を返す。
7. AIが編集を終えたら3.6の検査を行う。保存前に実行権と既存の結果を読み、完了済みならその結果を返す。合格した4.3の住宅情報・表示データ等は、試行ごとに新しいsnapshot IDで不変のR2オブジェクトとして保存する。manifestにはジョブIDと世代をcustomMetadata、SHA-256をchecksumとして付ける。
8. 確定前に、実行権の所有者とsnapshot IDから作ったmanifestのキーをHEADし、存在・ジョブID・世代・SHA-256を照合する。不一致は実行権の失効と区別して返し、ジョブを変更しない。合格したらD1の一つのbatchでsnapshotとrevisionを追加し、ジョブをcompletedへ変更する。その後に完了を通知する。

WorkflowのインスタンスIDは `job-<job ID>-g<実行世代>` とし、保存せずに参照から導く。作成は `createBatch` で行い、同じIDが既にあることを示すエラーコード10405なら、そのインスタンスの状態を読む（「再試行と復帰」）。取得の応答を失った場合も、activeなジョブの参照から同じIDを導くので、二つ目のインスタンスはできない。起こす呼出しが重なってもアラームは一つにまとまり、アラームの実行中に起こされたら、終わった後にもう一度動く。

サービス基盤のジョブはAIを使わず、4から7の代わりに次の段階をこの順に進める。各段階は最初に参照からD1のジョブを読み直す。同じ世代でrunningなら実行権を復元し、completedなら結果だけを返し、cancelledなら作業をせずに停止として終わる。

- `render snapshot`：パターンの接続用DOを通して、Containerで固定のサンプルの表示データを作り、試行ごとに新しいsnapshot IDでR2へ保存する。段階の戻り値はsnapshotの情報だけで、表示データを返さない。
- `commit revision`：保存したsnapshotで、案名「サンプルの形」の案を条件付きで確定する。
- `record failure`：確定も停止もしなかったときだけ、同じ世代のactiveなジョブをfailedにする。待機中のジョブがあれば、同じ文で待機列を保留する。失敗の更新が当たらなかったら、D1を読み直して停止か確定を返す。
- `wake pattern`：確定・失敗・停止のどの後もパターンDOを起こす。確定の後は次の指示へ進む。失敗・停止で待機列を保留していれば、DOは次の指示の実行権を取らない。

試験のために、設定 `JOB_TEST_HOLD` が `before_render:<秒>` または `before_commit:<秒>` のとき、Workflowは `render snapshot` の前、または `render snapshot` が保存した後の `commit revision` の前で、ジョブがまだrunningであることをD1で確かめてから `step.sleep` で待つ。localではすべてのジョブを、stagingでは検証用の利用者（4.4）のジョブだけを待たせる。localとstaging以外の環境では `none` 以外を設定の誤りとして拒否し、APIの要求を500で失敗させ、Workflowも段階を始めない。待つ間にWorkflowは退去してよく、再デプロイを挟む試験にも使える。6.2でサンプルの段階をAIの処理に置き換えるときに消す。

受付時のmessageの番号を受付順とする。HTTPの受付は認証・Origin・入力を検査し、所有者を条件にした専用の受付操作を呼ぶ。message・queuedのjob・要求の記録は同じbatchで保存し、再送では保存した受付結果を返す。DOはパターンIDを名前にして起こし、引数は渡さない。DOは本文や受付順をメモリにもストレージにも持たない。

D1への確定では、実行権・編集元の案・実行世代が一致し、ジョブがrunningであることを条件にする。停止と上限到達はジョブの状態をcancelled・limitedへ変えて記録するので、この条件で確定を拒む。同じjob IDからの案の二重追加は一意制約で防ぐ。R2保存後に確定できなかったデータは未公開のままにし、参照されていないことを確認して後で回収する。

確定のsnapshotとrevisionの所有者は、呼出し元の値ではなくジョブ行から写す。manifestのキーもSQLの中でジョブの所有者とsnapshot IDから組み立てる。案の会話の区切りは、その案を作った指示のmessage番号とする。複製で未実行の指示を除く条件は、この番号の範囲ではなくジョブの取得の記録（世代と編集元）で決める（2.5）。

同じ世代の確定を再送したら、`revisions.job_id` から最初の案を返す。後続の案が増えていても結果は変わらない。DBとR2の障害は例外として返し、自動的にfailedへ変更しない。R2保存後にD1のbatchが失敗したら、snapshot・revision・completedへの変更はまとめて取り消され、ジョブはrunningのまま残る。同じ実行権で確定をやり直せる。失敗の専用操作 `failJobAndHoldQueue` は、同じ世代でactiveのジョブだけをfailedにし、待機中のジョブがあれば同じ文で待機列を保留する。待機中のジョブの状態は変えない。ジョブを失敗にする操作はこれだけとし、障害復帰の照合もこれを使う。

「revisionを持つジョブは完了している」という表をまたぐ条件は、CHECK制約と外部キーだけでは保証しない。確定の専用操作が、revisionの追加とジョブの `completed` への変更を同じbatchで行って守る。

実行権はD1のジョブの行（job ID、実行世代、状態）にある。パターンDOは、次のジョブの実行権の取得、そのWorkflowの開始、D1とWorkflowの状態の照合を受け持つ。DOのメモリ内の状態だけで実行可否を決めず、再起動時はD1から読み直す。長いAI・形状処理の間、DO全体をロックし続けない。Workerの停止とWorkflowの確定は、DOを通さず、D1の条件付き更新で順序を決める。

実行権の型は公開要求のOwnerIdと分け、パターン・ジョブID・世代・編集元・所有者を非公開の欄に持つ。取得と復元の操作だけが、検査済みのD1の行からこの型を作る。受け取るすべての操作は、非公開の欄の存在を確かめてからその欄を読み、偽造した値をD1とR2への呼出しの前に拒む。型は現在の有効性を保証せず、書込みのSQLで再検査する。

パターンIDからactiveのジョブの参照（パターン・ジョブID・世代）を読める。Workflowにはこの参照を渡し、`readCurrentJobExecution` がD1と照合する。同じ世代のrunningなら実行権を復元し、completedなら結果だけを返し、cancelledなら停止として返す。それ以外は無効とする。復元と確定の再送では世代を増やさない。取得の応答を失っても、この読取りと復元で同じ世代を続けられる。

表示データだけを生成する段階ではvalidatingとcommittingを使わず、runningからcompletedへ一つのbatchで変更する。次の表には、AIとの往復と整合性検査を含む状態も定義する。

#### 状態と停止

| ジョブ状態                   | 意味                                                                                                               |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| queued                       | 指示を受け付けた。パターンが保留中なら実行しない                                                                   |
| running                      | 実行権を取得して編集中                                                                                             |
| validating                   | 確定前の整合性検査中                                                                                               |
| committing                   | 検査済みデータの保存と条件付き確定を進めている                                                                     |
| completed                    | 案または会話応答が保存された                                                                                       |
| awaiting_answer              | 質問を保存し、回答を待っている。実行権を解放し、待機列を保留する                                                   |
| cancelled / failed / limited | 停止・失敗・上限到達。未確定案を採用しない。activeな状態から変わったときに待機中のジョブがあれば、待機列を保留する |

停止は、Workerが所有者を条件にした一つの文でジョブの行を更新し、要求の記録と同じbatchで行う。queued・running・validating・committingのジョブだけをcancelledにする。activeなジョブを止めたときに待機中のジョブがあれば、同じ文で待機列を保留する。保留中に最後の待機中のジョブを止めたら、同じbatchで保留を解く。待機中のジョブを止めても保留しない。待機中に止めたジョブは実行権を取っていないので、世代は0のまま残る。世代を増やすのは実行権を取る文だけなので、世代が1以上のジョブを実行したジョブとする。確定のbatchはジョブがrunningであることを条件にするので、停止と確定はD1が先に処理したほうに決まる。停止が先なら確定のbatchは何も追加しない。確定が先なら停止は行を変えず、completedと確定した案を返す。completed・cancelled・failed・limitedは終端の状態で、どの操作もほかの状態へ戻さない。

停止はWorkflowへ要求を送らず、インスタンスを終了させない。`terminate()` が実行中の段階をどう扱うかは文書に書かれておらず、どちらにしてもD1の条件が確定を拒むためである。Workflowの各段階は作業の前にD1からジョブを読み直し、cancelledなら作業をせずに終わる。Workflowの戻り値とログでは、停止をcancelledとして失敗と分ける。実行中の段階の試行は最後まで進むことがあるが、その結果はR2へ保存する前の検査と確定のbatchの条件で捨てられる。その検査の後に停止が届いた場合と、確定の前で待たせている間に止めた場合は、R2へ保存した内容が参照されないまま残り、5.4の回収の対象になる。止めたジョブのWorkflowは、実行中の段階の試行が終わるまで残る（`render snapshot` では試行ごとの期限の3分まで）。

停止を記録したら、WorkerがパターンDOを起こす。DOは止めたジョブのWorkflowに触れない。待機列を保留していれば、DOは次の実行権を取らない。保留していなければ（待機中のジョブを止めたときなど）、次のqueuedのジョブの実行権を取ってWorkflowを開始する。次のジョブを始めたとき、止めたジョブのWorkflowがまだ動いていても、二つのWorkflowは別のジョブの行・実行世代・インスタンスIDを使うので、D1とR2への書込みは互いに影響しない。起こせなければ停止の要求は500で終わり、同じrequest IDの再送が記録した結果を返して起こし直す。止めたジョブのWorkflowも最後にDOを起こす。

再開は、保留の原因のジョブIDと、そのジョブがまだ保留していることを条件に、その行の保留を解く一つの文と要求の記録を、一つのbatchで行う。取り消しは同じ条件で、要求の記録、待機中のジョブをすべてcancelledにする文、保留を解く文を一つのbatchで行う。取り消したジョブは実行していないので、世代は0のまま残る。記録は書込みの前に結果を作るので、応答はbatchの前に待機していたジョブを番号順に返す。保留の原因が変わっていたら何も書かない。ジョブは一度しか終わらず、保留はその終わりのときだけ書くので、原因のジョブIDは一つの保留を指す。再開と取り消しが重なっても、D1が先に処理したほうだけが効く。再開の後はパターンDOを起こす。起こせなければ500を返し、同じrequest IDの再送が記録した結果を返して起こし直す。取り消しの後は待機中のジョブが残らないので、起こさない。

Containerへの停止要求は、ジョブを扱うContainerのルートとともに6.2で加える（4.7）。Rustの計算を即座に止められない場合も、停止したジョブの結果は確定できない。

質問への回答は、質問イベントと関連付けて新しいジョブにする。保留中の通常指示より先に回答を処理し、その後の待機列の再開は利用者が選べるようにする。

#### 再試行と復帰

AI呼び出し、形状操作、保存・確定を別のWorkflowステップに分け、ステップ名と操作IDを再実行で変えない。大きな戻り値はR2へ保存し、Workflowには参照と小さな結果を返す。

この設計は、Workflowsの次の性質を前提にする。

- 同じインスタンスIDでの `create()` は、既存のインスタンスが保持期間を過ぎるまで例外になる。完了したインスタンスの保持期間は、Workers Paidの既定で7日である（[WorkflowsのWorkers API](https://developers.cloudflare.com/workflows/build/workers-api/)、[Workflowsの制限](https://developers.cloudflare.com/workflows/reference/limits/)）。
- ステップの戻り値は1 MiBまでである（[Workflowsの制限](https://developers.cloudflare.com/workflows/reference/limits/)）。表示データなどの大きなデータはR2へ保存する。
- ステップは既定で、最初の試行の後に5回まで再試行する。間隔は10秒から指数的に延び、期限は試行ごとに10分である（[スリープと再試行](https://developers.cloudflare.com/workflows/build/sleeping-and-retrying/)）。

サービス基盤のジョブの段階は、次の方針で再試行する。Containerへ一時的につながらない場合（`start_failed`・`exited`・`not_ready`・`token_rejected`・`unreachable`）は、`render snapshot` が例外を投げて段階を再試行する。Containerが無効な環境（`containers_disabled`）、Containerとのプロトコルの版の不一致（`protocol_mismatch`）、形状の生成の失敗、内部プロトコル違反は再試行しない。結果の値として返し、ジョブをfailedにする。この分類は `services/geometry.ts` の一つの表に置き、理由を加えると型検査が分類を求める。D1・R2の例外は段階の再試行に任せ、再試行が尽きたら `retries_exhausted` としてジョブをfailedにする。

| 段階                                                | 再試行の回数 | 間隔                  | 試行ごとの期限 |
| --------------------------------------------------- | ------------ | --------------------- | -------------- |
| `render snapshot`                                   | 3            | 5秒から指数的に延ばす | 3分            |
| `commit revision`・`record failure`・`wake pattern` | 5            | 2秒から指数的に延ばす | 1分            |

`render snapshot` の期限には、Containerの準備の待ち（最大60秒）と表示データの要求（30秒）が一回分入る。

操作は入力スナップショットと操作IDを固定し、完了済みなら保存した結果を返す。Containerが停止して途中のメモリを失った場合は、最後に保存したチェックポイントからやり直す。古い実行世代の結果は無効にする。

APIの応答を受け取れず再呼び出しが必要になった場合、課金を伴う外部処理まで「一回しか実行されない」とは仮定しない。試行ごとに費用を扱い、案の確定は一度に限定する。

パターンDOは、アラームの最初に30秒後のアラームを予約してからD1とWorkflowを照合する。照合で例外が起きても次のアラームでやり直す。実行するジョブがないか、待機列が保留中なら、自分が予約した時刻と一致するアラームだけを取り消す。照合中に届いた起動通知のアラームは残る。

| 同じ世代のWorkflowの状態                                       | D1にactiveなジョブが残っているときの処理                     |
| -------------------------------------------------------------- | ------------------------------------------------------------ |
| インスタンスがない（保持期間を過ぎた場合を含む）               | 同じIDで作成し、取得済みの編集元で実行する                   |
| queued、running、waiting、rollingBack                          | 次の照合まで待つ                                             |
| paused、waitingForPause、unknown、未知の状態、状態の読取り失敗 | 実行権の取得から24時間までは待ち、24時間に達したら失敗にする |
| errored、terminated、complete                                  | 実行権を再確認して失敗にする                                 |

失敗には `failJobAndHoldQueue` を使い、後続の指示があれば同じ更新で待機列を保留する。利用者は保留を再開するか取り消すかを選ぶ。状態を読んだ後に実行権を復元するので、その間に停止や確定が成立していれば、その結果を保つ。終えられないと判断したWorkflowが実際は動いていても、その確定はD1の状態の条件で拒まれる。

照合は新しい世代を作らず、終わったWorkflowをやり直さない。errored のインスタンスは段階の再試行を使い切っている。同じ原因でまた失敗しうるうえ、6.2では課金を伴う処理を利用者の知らないまま繰り返すことになる。terminated は運用者が止めたものである。インスタンスがないときだけ、同じ世代のIDで作り直す。編集元は変わらないので、複製（2.5）が前提とする取得の記録も変わらない。

止まった状態の上限を実行権の取得から24時間とするのは、サンプルのジョブが試験の待ち（最大7200秒）と段階の再試行を合わせても24時間に届かず、動いているジョブを一度の読取りで失敗にしないためである。6.2でAIのジョブの所要時間を測ったら見直す。

5分ごとのCron Triggerは、取得から5分を超えたactiveなジョブ、または保留されずに受付から5分を超えたqueuedのジョブがあるパターンを無作為に最大200件選び、各DOを起こす。ジョブの取得と照合はDOが行う。

ローカルの `wrangler dev` を再読込または再起動すると、実行中だったWorkflowはrunningを返したまま処理を再開しない。状態では動いているものと区別できないので、照合では終わらない。開発中は停止操作でそのジョブを終える。本番のWorkflowはデプロイを越えて続く。Worker再起動をまたぐ実行の継続は、stagingで検証用の利用者のジョブを待たせて再デプロイし、DOの再起動後に案が一件だけ増えることを確かめる。

### 4.7 APIと途中経過の配信・再接続

以下を初期の公開APIとする。変更要求はrequest IDを持ち、同じIDと内容の再送は同じ結果へ対応付ける。復帰や管理情報の変更では期待する版を送り、意図しない上書きを防ぐ。

request IDは利用者ごとの範囲で一意とし、固定するのは成功した結果だけとする。失敗した要求は記録せず、同じIDで内容を直した再試行を新しい要求として扱う。一度成功したIDを別の操作・内容に使った場合は拒否する。同じ要求の同時の再送では、先に確定した結果を全員に返す。

表示データ以外の応答はJSONで、失敗は共有定義のエラーコードを `{ error }` で返す。エラーコードには、公開APIのいずれかのルートが返すものだけを定める。利用者ごとのデータを返すため、API応答はすべてキャッシュさせない。応答と構造化ログに追跡用のIDを付け、ログには会話・名前などの本文を出さない。案件の一覧は作成日時の新しい順に、案の一覧は履歴の番号の降順に、会話は会話の番号の降順に並べ、続きを取得するためのカーソルを付けて返す。パターンの一覧は番号の昇順に、ページに分けずに返す。

案の一覧は50件ずつ返し、カーソルには最後の番号を符号化する。作成時刻ではなく履歴の番号で並べるため、作成時刻が同じ場合や実行元の時計が前後した場合も、現在の案と一覧の先頭は一致する。表示データの応答には、閲覧対象の案IDを `x-revision-id` ヘッダーで付ける。

`GET /api/patterns/:id/messages` は省略可能な `cursor` だけを受け付け、`{ messages, nextCursor }` を返す。各行は `{ id, number, kind, body, createdAt, jobId, revision }` で、質問だけに `choices` が付く。jobIdは入力を受け付けたジョブか、その行を書いたジョブのIDで、ジョブがなければnullとする。revisionはそのジョブが確定した案（案の一覧と同じ形）で、なければnullとする。1ページは最大50件。続きがあれば最後の行の番号をJSONにしてbase64urlで符号化したカーソルを返し、なければnullを返す。開き直した画面は、カーソルなしで最新のページを読み、nextCursorで古い会話へさかのぼる。新しい行は既存の最大より大きい番号を取るので、最新のページにだけ現れ、手元のカーソルで取得する古い行は変わらない。所有者から見えるパターンの存在確認とページの取得は同じD1 batchで行う。番号の索引でカーソルより古い行から読み始め、ジョブと案は索引で結び付けるため、深いページでも読取り量はページの件数で決まる。

`POST /api/patterns/:id/messages` はJSONの `{ requestId, body }` を受け取る。bodyはUnicodeとして正しく、空白だけではなく、UTF-8で16,384バイト以下とする。本文の空白やUnicodeを正規化しない。JSON全体の上限はこのルートだけ128 KiBとし、ほかのJSON要求の既定は16 KiBとする。

受付の応答は202の `{ job: { jobId, messageId, number } }` で、numberはmessageの会話の番号で、受付順に増えるが連続しない。この応答は受付の記録であり、ジョブの現在の状態を表さない。同じrequest IDと内容の再送は、ジョブの状態が変わった後も同じ状態コードと本文を返す。現在の状態は `GET /api/patterns/:id/state` で読む。

入力が不正なら400 `invalid_request`、JSON全体の上限超過は413 `payload_too_large`、成功済みのrequest IDを別の内容や操作に使うと422 `request_id_reused` とする。認証の失敗は401 `unauthenticated`、認証後のOriginの拒否は403 `forbidden`、別の所有者と存在しないパターンは同じ404 `not_found` とする。

`POST /api/jobs/:id/stop` はJSONの `{ requestId }` を受け取り、待機中または実行中の指示を止める。所有者・Origin・request IDは他の変更要求と同じに確かめ、別の所有者と存在しないジョブは同じ404 `not_found` にする。応答は200で、`outcome` が結果を分ける。この要求で止めた場合は `{ outcome: "stopped", job: { jobId, messageId, number, state: "cancelled" } }` を返す。既に終わっていた場合は行を変えず、`{ outcome: "already_finished", job }` を返す。jobのstateはcompleted・cancelled・failedのいずれかで、completedなら確定した案を `revision` に含める。どちらの結果も記録し、同じrequest IDの再送は同じ状態コードと本文を返す。ジョブの状態は応答の時点で決まっているので202にはしない。エラーの本文は `{ error }` だけで確定した案を運べないので、既に終わっていた場合もエラーにしない。

`POST /api/patterns/:id/queue/resume` と `POST /api/patterns/:id/queue/cancel` は、JSONの `{ requestId, heldBy }` を受け取る。heldByは画面が読んだstateの `queueHold.job.jobId` で、そのジョブがまだ待機列を保留している場合だけ適用する。所有者・Origin・request IDは、ほかの変更要求と同じに確かめる。別の所有者と存在しないパターンは同じ404 `not_found` に、保留していない場合と別のジョブが保留している場合は409 `version_conflict` にする。再開は保留を解き、保留を解いた時点の待機中の指示を `{ jobs: [{ jobId, messageId, number }] }` で番号順に返す。取り消しは、保留中に受け付けた指示も含めて待機中の指示をすべてcancelledにし、保留を解いて `{ jobs: [{ jobId, messageId, number, state: "cancelled" }] }` を返す。どちらも200で、結果を記録し、同じrequest IDの再送には同じ状態コードと本文を返す。heldByは一つの保留を指すので、再開を二度押しても、その間に失敗した次の指示の保留は解かない。

stateはqueryパラメータを受け付けず、`{ pattern, currentRevision, runningJob, queuedJobs, queueHold, lastFinishedJob }` を返す。runningJobは実行権を持つジョブ（running・validating・committing）の `{ jobId, messageId, number }` で、なければnullにする。DBがパターンごとにactiveなジョブを一つに限るので、配列にしない。queuedJobsは同じ形の配列で、対応するmessageの番号の昇順に並べ、待機中がなければ空配列にする。同じジョブを両方に入れない。パターン・最新案・実行中のジョブ・待機中のジョブ・保留・最後に終わったジョブは同じD1 batchで読み、所有者を条件にする。実行中のジョブのSELECTは `jobs_one_active_per_pattern` 索引を `INDEXED BY` で使う。所有者の条件を加えると、統計を取った後のSQLiteはこの索引を使わず、パターンのジョブをすべて読むためである。待機列のSELECTはjobsをCROSS JOINの外側に置き、`jobs_queue` 索引でパターンとqueuedを絞ってからmessageを読む。lastFinishedJobは、実行したジョブ（4.6）のうち終わった（completed・cancelled・failed）もので、messageの番号が最も大きいものを、停止の応答のjobと同じ形で返し、なければnullにする。待機中に止めたジョブと取り消したジョブは、実行していないので含めない。開き直した画面がここから読む区別（2.4）は、実行したジョブにだけあるためである。このSELECTはmessageを外側に置き、部分索引 `messages_inputs` で指示と回答だけを番号の降順に読み、最初に見つかった実行済みの終わったジョブで止めるので、そのジョブより新しい入力だけが追加の読取り対象になる。これには待機中・実行中のジョブの入力、実行せずに終わったジョブの入力、ジョブのない入力が含まれる。完了済みの会話とジョブの件数を読取り量に含めない。実行せずに終わったジョブの入力は、後の指示が実行されて終わるまで読取り対象に残り、その件数は利用者が待機中に止めた指示と取り消した指示の数で決まる。後の指示が実行されて終わると、lastFinishedJobはその指示に置き換わる。待機中の指示を止めても取り消しても、lastFinishedJobは変わらない。止めた画面は、記録された停止の応答を同じrequest IDの再送で読み直せる。

queueHoldは、待機列が保留中なら `{ job: { jobId, messageId, number, state } }`、保留していなければnullにする。jobは保留の原因になったジョブで、stateはcancelledかfailedである。保留中は、queuedJobsのすべてが保留中の指示で、runningJobはnullである。このSELECTは `jobs_one_queue_hold_per_pattern` 索引を `INDEXED BY` で使い、ほかの読取りと同じD1 batchで、所有者を条件にして読む。

受付のログにはrequest ID・pattern ID・job ID・message ID・受付番号と、初回か再送かを表す `acceptance: applied | replayed` を型付きのキーで記録する。指示の本文はログに含めない。

ジョブの実行のログは、ジョブIDをtrace IDとして型付きのキーで記録する。パターンDOはアラームごとに `pattern.advanced`（結果、ジョブID、世代、インスタンスを作ったか）を書く。保留中は、結果 `queue_held` と保留の原因 `heldBy` を書く。Workflowは段階の試行ごとに `job.step`（段階名、試行の番号、結果）を、終わりに `job.finished` を書く。`job.finished` の結果はcommitted・cancelled・failed・not_runningで、committedとcancelledはinfo、それ以外はerrorで書く。停止の要求のログには、request ID・job ID・pattern IDと、記録が初回か再送かを表す `stop: applied | replayed`、`outcome: stopped | already_finished`、停止後のジョブの状態 `jobState` を型付きのキーで記録する。待機列の要求のログには、request ID・pattern ID・`heldBy` と、記録が初回か再送かを表す `queue: applied | replayed`、`outcome: resumed | cancelled` を型付きのキーで記録する。形状処理の呼出しにも同じtrace IDを渡すので、接続用DOの `container.started`・`container.ready` も同じIDでたどれる。受付のログとはジョブIDでつながる。

SSEのイベントにはパターン、job ID、案IDまたは作業版、増加するイベント番号を付ける。画像・メッシュの本体は含めず、取得先を通知する。操作中にパターンや条件を変えた場合、遅れて届いた別の版の結果を表示しない。

再接続時はイベント番号から差分を読み、保存範囲を外れていたらstateと現在の表示データを再取得する。SSEの接続をジョブの生存条件にしない。通信できない間の入力は送信済みとせず、再送時にもrequest IDを保持する。

Containerの内部APIは、入力スナップショットと操作の一括を受け、検査済みの住宅スナップショットと表示データを返す一つの要求にまとめる。読込・操作・検査・保存用バイト列の書出しを別要求のSession IDで結ばない。6.2では生成、住宅の形状変更、加工と物体の変更、色だけの変更、確定前の検査・保存用出力をこの形で実行する。色だけの一括でも、加工と物体を含めて住宅からCADを作り直す。同じ要求内のプレビュー生成では3.5の評価キャッシュを引き継ぐ。表示だけの要求はR2の保存済み表示データを読み、Containerへ送らない。

ジョブを扱う要求にはjob ID、操作ID、実行世代、入力スナップショットを必須にする。要求ごとのSessionを分離し、完了した要求のCADを次の要求の前提にしない。停止は実行中の要求の停止tokenと世代の失効で扱い、遅れて届いた結果を確定しない。Containerのメモリを失った場合も保存済みの入力から再実行する。入力スナップショットの内容をキーにしたSessionキャッシュを要求間へ足すかは、Cloudflare上で住宅一軒と要求種別ごとの処理・メモリを測る#103の後に決める。

内部APIは `/v1` のパスで版を識別し、`/healthz` もプロトコルの版を返す。DOは自分の扱える版だけを受け付ける。固定サンプルの `GET /v1/sample/display` はジョブの識別子を持たず、要求ごとのSessionで評価する。公開APIはContainerを呼ばない。起動・接続の失敗、形状生成の失敗、内部プロトコル違反は、ジョブの `render snapshot` が `services/geometry.ts` の分類で段階の再試行かジョブの失敗にする（4.6「再試行と復帰」）。

本文を持つ内部ルートは、ハンドラーの要求・応答型をルート表に結び付け、表の `request.max_bytes` からaxumの本文上限を適用する。axumの既定の2 MB上限には頼らず、ルートごとに適した上限を選ぶ。バイナリ要求はメディア型も検証する。413と422の拒否応答は、内部APIのErrorBodyのコードへ変換する。本文の上限と拒否応答の変換は、実際のルートで本文を転送するテストで確かめる。

### 4.8 2D生成・3D描画・素材表示・日差しの計算

2Dは住宅の輪郭・開口・階段情報と、置いた後の物体の投影から生成する。部屋の輪郭を変える加工がある部屋は、3.4のとおり壁の立体の投影から輪郭を描く。部屋名・面積・方位・寸法を同じ案に結び付ける。SVGを表示とPNG出力の共通の入力にする初期設計とする。

3Dはサーバーで評価した形状から表示メッシュを作り、住宅要素IDとの対応、色、素材を付けてWasmへ渡す。モデルの判断は住宅情報とCADの形状に基づき、表示メッシュの変更を住宅編集として保存しない。対象選択はブラウザで候補を求め、サーバーがその案の形状と対応表で確定する。

表示形式は `crates/display` で管理する。版1は `MDSP` ヘッダー、全体の長さ、8バイト境界にそろえたセクション表を持つ。ボディごとのf32メッシュ、三角形のB-rep面番号、RGBA色、閉じたボディかどうか、面のRGB色、住宅要素IDを格納する。WorkerとWebはバイト列を解釈せずに渡し、Wasmの復号時に検証する。内部APIは16 MiBを上限にする。

版1の必須セクションは ELEM、BODY、POSN、NORM、TRIS、TFAC、FCOL の順に固定する。その後に任意セクションを表の順で追加し、任意セクションのフラグは0とする。各セクションの前には8バイト境界にそろえる最小限のゼロ埋めだけを置き、最後のセクションの後に余分なバイトを置かない。既知の任意セクションがない場合は、その情報の既定値を使う。

新しい情報はセクションとして追加する。旧ビューアが無視できる追加は任意とし、必須の未知セクションは読込を拒否する。任意セクションは旧読込側も保持し、受理したバイト列は再符号化しても一致する。既存セクションの意味を変える場合は形式の版を上げる。R2に保存したオブジェクトは書き換えず、ビューアに保存済みの各版の読込処理を残す。

素材は、画像の読み込み、面への座標の割り当て、柄の実寸・向き、表示用キャッシュを追加する。通常のSolidCraftビューアの色指定だけでは木目やタイルの表示は完成しない。6.4で、壁の移動・分割・伸縮後にも柄と適用面が保たれることを確認する。

日差しは、地域・日時・方位から太陽方向を求め、開口、壁、家具、屋根、隣家による遮蔽を計算して3Dへ表示する。初期実装は検証で用いた太陽方向と幾何遮蔽の考え方を編集可能な案へ広げ、床を含む室内で光が届く場所を示す。表示用に隠した屋根も遮蔽に含める。ガラスは初期計算では光を通すものとする。

日差しの結果は案IDと日時・地域・方位の条件で識別・キャッシュする。計算中に条件が変わったら古い結果を採用しない。精度と処理時間、壁・天井への表示方法は6.5で実装中に確認し、粗い計算が細い日差しを消してしまう問題を検査する。床のサンプリングによる既存の検証結果は、任意の住宅での精度や通常の影描画の完成を保証しない。

## 5. 運用と保守

### 5.1 開発環境と本番へのデプロイ

ルートに自作RustコードのCargo workspaceとJS/TSコードのpnpm workspaceを置く。Rust側は `apps/geometry` と自作の `crates/`、JS/TS側は `apps/web`・`apps/worker`・`packages/contracts` を対象にする。SolidCraft側のCargo workspaceは別に保持し、自作側から必要なクレートをpath依存で利用する。

SolidCraft一式を保持することと、通常のビルド・テスト対象に全アプリを含めることは分ける。自作workspaceへ取り込み領域の全クレートが自動参加しないよう設定し、サービス側のビルドでは必要な依存先だけを使う。

開発ツールの版を固定し、検査はローカルの `pnpm check` にまとめる。先にPrettier・rustfmt・ESLint・Clippyで自動修正できるものを直し、型付きlint・型確認・未使用検査・秘密情報・テストを実行する。RustはnativeとWasmを検査する。手元の通常・軽い検査は、分岐点以降の変更と作業中の変更がRustの入力に触れていなければRustのコンパイルを省く。CI、`--full`、`--rust`、変更を判定できない場合は、そのモードのRust検査をすべて実行する。作業中の `--fast` はテスト実行とアプリのビルドを省き、`--full` はWasmの再生成、全ビルド、接続確認、JS/Rustのライセンス・取得元・脆弱性監査まで行う。初回以外はビルドキャッシュを再利用し、各工程の時間を表示する。コミット前フックはステージ対象ファイルの整形・lint、ステージ対象のTypeScriptファイルのimport境界、ステージ済み差分の秘密情報を検査し、作業ツリーやステージ内容を書き換えない。具体的なコマンド、検査範囲、PRでの検査は[README](../README.md)にまとめる。

Rustの版とWasmのターゲットは `rust-toolchain.toml` で固定し、rustupを通して使う。ほかのrustがPATHの前にある環境（T3のエージェントのシェルなど）でも、miseの実行では `mise.toml` が `$CARGO_HOME/bin` をPATHの先頭に置き、rustupのcargoを使う。`pnpm setup`・`pnpm check`・`pnpm dev`・`pnpm build` は、cargoを使う前に、PATHで最初に見つかるcargoがrustupのproxyかを確かめ、違えば理由と直し方を示して止まる。proxyかどうかは、ファイルの置き場所ではなく振る舞いで見分ける。一時的な仮のtoolchainを `RUSTUP_TOOLCHAIN` で指定して `cargo --version` を実行し、仮のtoolchainが動けばproxyとする。そのため、rustupの公式のインストーラー、Debianのパッケージ、proxyをシェルスクリプトで包むHomebrewのrustupのどれでも止まらない。`mise.toml` の二行（`activate_aggressive` と `_.path`）は、本物のmiseで、有効にした後に別のcargoをPATHの先頭に足しても `$CARGO_HOME/bin` のcargoが選ばれることを確かめる試験で守る。

worktreeごとに専用の `target/` を持つ。手元のRustの検査とreleaseのWasmビルドはstable Rustとmbxを使う。新しいworktreeは `.tools/` だけを複製し、mbxはworkspaceのルートを正規化してコンパイル結果をユーザーごとに共有する。target viewsとlearned incrementalを無効にし、ストアはmbxの自動回収で8 GiBを目安に保つ。mbxを使えないときと `MADORI_MBX=0` のときは、従来どおりtargetを複製し、ローカルクレートの更新時刻を進めてCargoでビルドする。GitHub Actionsはrunnerのtargetを使い続ける。契約生成器の出力先は呼び出し時に渡す。

サービスの依存解決はルートのCargo.lockとpnpm-lock.yamlで固定する。Cargoのプロファイル・依存パッチは利用側ルートで必要な設定を管理し、SolidCraft側の設定が自動で引き継がれるとは仮定しない。devプロファイルはincrementalコンパイルを無効にする。Cargoはincrementalの有無を成果物のハッシュに含めるので、有効にすると、環境変数の `CARGO_INCREMENTAL=0` や `CI` を設定した実行と設定しない実行が、同じコードの成果物を二組作るためである。キャッシュを利用する場合は、識別値に実際の依存解決とビルド条件を反映する。誤った再利用を避けるため、サービスから使うSolidCraftの評価キャッシュを無効にする。SolidCraftのbuild.rsには、このリポジトリのgitの状態を読ませない。このリポジトリのHEADはSolidCraftのソースを表さず、読むとコミットやcheckoutのたびにsolidcraft-ioとそれに依存するcrateを作り直すためである。

配信するWasmはreleaseプロファイルでビルドする。`pnpm setup`・`pnpm dev`・`pnpm build`・`pnpm check --full` は同じ生成スクリプトを使い、開発・検査・配信のWasmをそろえる。スクリプト内の一つのプロファイル値からCargoの `--profile` とwasm-bindgenの入力先を導き、`target/wasm32-unknown-unknown/release/` の出力からバインディングを生成する。プロファイルと入力先をログへ出す。バインディングを生成する前に、Wasmに入る自作のクレートがすべてそのチェックアウトの `target/` でコンパイルされたことを、rustcがクレートごとに書くdep-infoで確かめ、違えば止める。開発用worktreeでは、ローカル依存のソース、マニフェストとロックファイル、設定、ツールチェーン、ビルド手順が一致すると、ユーザーごとのキャッシュから変換前のWasmとバインディングをまとめて復元する。GitHub Actionsではキャッシュを使わず生成経路を検査する。RustのテストとClippyはdebugのままにする。通常・軽い検査は生成済みの型定義を使い、全体検査はreleaseのWasmを準備して、ローカル配信と実Containerの接続を確かめる。

開発では `pnpm dev` がWeb画面、Worker・D1、Wasmと、`wrangler dev` 経由のDocker Containerを接続する。画面だけを扱うときは `MADORI_DEV_CONTAINERS=0` でContainerを無効にする。

担当と検証役は、別のworktreeで同時に `pnpm dev` を動かして確かめる。そのため、画面（Vite）とWorkerのポートは、`scripts/dev/dev-session.ts` が起動の初めに一度だけ決める。指定がなければ5173番と8787番を使う。環境変数 `MADORI_DEV_PORTS=auto` を付けると、20000〜32767番から空いている二つを無作為に選ぶ。この範囲は、OSが番号0の待ち受けに割り当てる範囲（macOSは49152番から）と、DockerがContainerの公開に使う範囲（32768番から）を避ける。そのため、選んでから実際に待ち受けるまでの間（Dockerの枠の待ちとイメージのビルドを含む）に、ほかのプロセスが同じ番号を偶然取ることはほとんどない。取られた場合は、ViteかWranglerが起動に失敗して `pnpm dev` が止まり、別の回の画面を見せることはない。空いているとは、`127.0.0.1` と `::1` への接続がどちらも拒否されることをいう。待ち受けを試す方法では、ワイルドカードのアドレスで待ち受ける別のプロセスを見落とし、`localhost` がそのプロセスに届くためである。既定のポートが空いていなければ、マイグレーションとDockerの枠を待つ前に止まり、別のポートへ黙って移らない。決めたポートは `Web: http://127.0.0.1:<画面のポート> | Worker: http://127.0.0.1:<Workerのポート>` の一行で出す。Workerにはそのポートと、既定以外の回ではインスペクターの `--inspector-port 0` を渡す。Wranglerはインスペクターのポートを起動時に9229番から探して決め、実際に待ち受けるまでに間があるので、同時に起動した二つの回が同じ番号を選びうるためである。Viteにはポートを引数で渡し、プロキシの宛先のWorkerのポートは子プロセスの環境変数 `MADORI_DEV_WORKER_PORT` で渡す。Viteの設定は `MADORI_DEV_PORTS` を読まない。`.dev.vars` の `APP_ORIGINS` には、その回の画面のポートを `127.0.0.1` と `localhost` で書いた二つだけを書く。`wrangler.jsonc` のローカルの `APP_ORIGINS` は、どの画面とも一致しない仮の値にする。ローカルのD1と `.dev.vars` はチェックアウトごとに一つで、二つの `wrangler dev` が同じD1の状態を使うとDurable Objectの書き込みが失われる。そのため、`pnpm dev` は起動の初めに `.local/dev.lock` へ `O_EXLOCK` のflockを取り、同じチェックアウトの二つ目の `pnpm dev` を止める。Dockerの枠と同じく、このロックはmacOSでだけ働く。

`pnpm check --full` はDockerイメージをビルドし、実Containerとの接続も検査する。Dockerはビルドプラットフォーム上のRustからLinux amd64向けにコンパイルし、Cargoのキャッシュを再利用する。イメージのビルドに送る材料からは、取り込み領域のうちビルドが読まない大きなデータ（テストの正解データと入力、資料、使わない資産とクレート）を `.dockerignore` で除く。除くパスは、Linux向けのビルドのdep-infoに現れないことで確かめる。テスト用と本番用の認証設定・DB・R2・秘密情報は分離する。

形状サービスのイメージのビルドでは、Cargoの `target/` をDocker Engineのcache mountに一つ置き、そのEngineでビルドするすべてのチェックアウト（各worktreeとself-hosted runner）で共有する。Cargoはpath依存のクレートの新しさをソースの更新時刻で判断するが、COPYはチェックアウトごとの更新時刻をそのまま持ち込み、それらは互いに比べられない。そのままビルドすると、後から作ったチェックアウトは同じ内容のクレートをすべて作り直し、先に作ったチェックアウトは別のチェックアウトの内容からコンパイルした成果物をそのまま使う。そのため、cache mountには `target/` と並べてソースの写しを置き、Cargoは写しをビルドする。ビルドのたびに、写しと材料の各項目の種類と内容のハッシュを比べ、違う項目だけを写しへ書き、写しにだけある項目を消す。Cargoは依存するファイルをシンボリックリンクを解決したパスで記録し、コンパイルしたときのリンクの先の更新時刻を見る。そのため、写しにはリンクを置かず、リンクの先のファイルとディレクトリを、リンクの名前の通常のファイルとディレクトリとして写す。参照先の無いリンクは写さない。写しの更新時刻は、その内容が写しに入った時刻になる。Cargoから見ると一つのチェックアウトを順に編集したのと同じになり、内容が変わったクレートとそれに依存するクレートだけを作り直す。写しは比べるための状態を別に持たず、毎回両側を読み直すので、途中で止まったビルドの後も正しい状態に戻る。写しの更新からCargoの終了までは `sharing=locked` で一つのビルドだけが行い、同時に始まったビルドは順に実行する。Cargoも一つの `target/` では順にしか実行しない。内容が違う二つのチェックアウトが交互にビルドすると、違うクレートとそれに依存するクレートを、そのたびに作り直す。worktreeごとのcache mountは採らない。ビルドの引数はWranglerの設定に固定されていてworktreeを区別する値がビルドに届かず、約4.1 GBの `target/` を複数持つと回収の上限の8 GiBに収まらないためである。写しの作り方や置き場所を変えるときは、古い規則のビルドと同じcache mountを使わないよう、cache mountのidを変える。

開発用のMacでは、複数のエージェントとself-hosted runnerが一つのCPUとDocker Engineを共有する。Dockerを使う重い作業が重なると、関係の無い試験まで時間切れで落ちる。そのため、Dockerを使う作業の数を、マシン全体で共有する「Dockerの枠」で制限する。`pnpm check --full` の実Containerの接続検査、形状サービスのイメージの回収、ビルドキャッシュの回収、Containerを有効にした `pnpm dev` は、枠を一つ取ってから始め、枠が埋まっていれば空くまで待つ。枠は開発用に二つ、runner用に一つとし、その数は `scripts/shared/docker-slots.ts` の一つの表だけで定める。runnerは環境変数 `GITHUB_ACTIONS=true` で見分け、runner用の枠だけを使うので、開発の作業が枠を埋めていても待たない。PRのモード判定と通常検査は専用の `madori-light` で動かす。`--full` とデプロイは `madori` が一度に一つずつ動かすので、stagingへのデプロイで `wrangler deploy` が行うイメージのビルドを含めても、runnerのDockerの作業は一つまでになる。

枠は、ユーザーのホーム（`os.userInfo().homedir`）の `.local/state/instant-madori/docker-slots/` にある枠ごとのファイルへの、排他のflockで表す。macOSには `flock(1)` が無いので、`O_EXLOCK` を付けた一回の `open(2)` で取る。共有するマシンはmacOSなので、枠はmacOSでだけ働く。Linuxでは枠を取らずに実行し、そのことを一行出す。枠を使っているかはロックだけで決め、pidや時刻の記録には頼らない。そのため、落ちたプロセスや `kill -9` で止めたプロセスの枠は、OSが外して残らない。枠は取ったプロセスだけが持ち、子プロセスへは渡さない。Wranglerは自分の子プロセスに別のファイル記述子を渡し、Dockerのビルドを別のプロセスグループで起動するので、子に渡しても実際のDockerの作業までは届かない。そのうえ、`kill -9` の後に残った `wrangler dev` が枠を持ち続ける。枠を持つプロセスは、枠のファイルに目的・pid・開始時刻・チェックアウトを書き、手放すときに消す。待つプロセスと `status` は、この記録を表示だけに使う。ロックを取るのは枠を取るときだけで、自分の側（開発用かrunner用）の枠に限る。開発の作業がrunner用の枠のロックに触れることはない。待つプロセスは、待ち始めとその後の一分ごとに、各枠を持つプロセスを表示する。長く起動したままの `pnpm dev` は枠を一つ持ち続けるが、時間で止めることはしない。別のチェックアウトの `pnpm dev` は同時に動かせるので、Containerを有効にした `pnpm dev` が二つ動くと開発用の枠は両方埋まり、三つ目の `pnpm dev` と `pnpm check --full` のDockerの段階は、どちらかが止まるまで待つ。

`pnpm check --full` は、実Containerとの接続を検査した直後に、同じDockerの枠を持ったまま、ローカルDocker Engineの未使用ビルドキャッシュを回収する。Cargoのregistry・git・targetを含む `exec.cachemount` は合計8 GiBまで保持する。別の枠で `regular` と `frontend` を合計6 GiBまで保持する。形状サービスの一組の層（Rustの基底層・aptのRUN・COPY・CargoのRUN・実行用の段・frontend）は、計測値で約3.5 GBである。6 GiBは、この一組に更新1回分の余裕を足した大きさとして、2026-11-22に運用者が決めた上限である。Rustの基底イメージを更新すると、各worktreeが新しいmainに追いつくまで新旧の二組（約6.9 GB）が並び、6 GiBには収まらない。そのときは、古いほうの組のビルドの段の鎖が、CargoのRUNとソースのCOPYからaptのRUNまで消える（約1.0 GB）。古い組の基底層と、最後の段の `COPY --from=build` は残る。最後の段の記録は、ビルドのたびに最も新しい時刻になるためである。古いmainのworktreeの次のビルドは、aptのRUNとCargoのRUNを実行し直す。この結果は、`scripts/dev/prune-build-cache.test.ts` の試験「after a Rust base bump, 6 GiB removes the older set's build chain through its apt RUN」が、2026-11-22の計測値で確かめる。使用中の記録も枠に数えるので、並行するビルドがあると、さらに多く消える。時間の範囲では集中したビルドの容量を制限できないため、容量を上限にする。

BuildKitの記録は親子でつながり、ビルドの各段の層は前の段の層を親に持つ。BuildKitは、子が残っている記録を、指定されても削除しない。また、ビルドが読み込んだ記録の最終使用時刻だけを更新し、再利用した基底層とaptのRUNの時刻は古いまま残す。そのため、回収は記録自身の最終使用時刻で順位を決めない。各記録の順位には、その記録と子孫のうち最も新しい使用時刻を使い、それが古い記録から、子を親より先に削除する。基底層は、その上に作った最も新しいビルドと同じ順位になる。子が一つでも残る記録は選ばないので、選んだ記録は一度の回収ですべて削除できる。各枠の報告値が上限を超えた場合だけ削除し、上限に収まったところで止める。`source.local`・`source.git.checkout`・`internal` の未使用記録は、子が残らないかぎりすべて回収する。使用中の記録と未知の種類の記録は、その祖先も含めて削除しない。未知の種類は一行で報告する。すべての段がキャッシュに当たったビルドは、最後の段の記録の時刻だけを更新し、最後の段の `COPY --from` の記録はビルドの段と親子でつながらない。そのため、ビルドの段の順位は、そのソースで最後にビルドの段を実行した時刻になる。ソースを変えずにビルドし直すだけのworktreeでは、ビルドの段の枝が古く見え、回収されることがある。枝を回収した後も、同じソースのビルドはすべての段がキャッシュに当たり、作り直しはそのworktreeのソースが次に変わったときに起きる。新旧の二組が並ぶと、ビルドの段を最後に実行した時刻が古いほうの組は、aptのRUNと基底層まで回収されることがある。

Dockerは使用中のcache mountを0バイトと報告するため、その実容量を上限の計算に含められず、使用が終わった後に上限を超えることがある。並行したビルドや回収で計測後の状態も変わる。回収後の報告値は使用中のmountの実容量を保証しない。選別はDocker EngineのID・種類・バイト数・使用状態・時刻・親を検証した純粋関数で行い、選んだIDだけをBuildKitへ渡す。Docker Engine 29は親のIDを先頭に空白の付いたキー `" Parents"` で返すため、そのキーと `"Parents"` の両方を読む。親のつながりが循環していれば、何も回収しない。手動のdry-runも同じ選別を使い、保持・削除の記録と回収後の見込みを出す。回収の後には、選んだのに残った記録を報告する。手元とrunnerで同じ入口を使い、UnixソケットのローカルEngineだけを対象にする。ビルドキャッシュの回収は、イメージ・Container・ボリューム、runnerのCargoのtargetとツールを対象にしない。

`pnpm check --full` は、実Containerとの接続を検査した直後、ビルドキャッシュを回収する前に、同じDockerの枠を持ったまま、このリポジトリの形状サービスのイメージを回収する。対象は、Wranglerが付ける `cloudflare-dev/geometrycontainer-geometry-<クラス名とイメージ名のハッシュ>` のタグと、stagingへのデプロイが手元に残す `registry.cloudflare.com/<アカウント>/instant-madori-staging-geometrycontainer-geometry` のタグだけとする。他のリポジトリのタグは、同じイメージを指していても外さない。Wranglerは起動ごとに無作為のタグを付けるが、同じソースのビルドは同じイメージになるので、タグの数はディスクの使用量を表さない。そのため、イメージを単位にして、最後にタグを付けた時刻が新しい3個を残し、残すイメージのタグは一つにする。それより古いイメージは、すべてのタグを外して消す。Containerが使うイメージ、動いているWranglerのうち最も古いものの起動時刻の5分前より後にタグを付けたイメージ、タグを付けた時刻が分からないイメージは、数に関係なくすべてのタグを残す。動いているセッションは、休止したContainerを自分のタグから作り直すので、Containerの有無だけでは守れないためである。5分は、Docker DesktopのVMとホストの時計のずれに備える余裕である。Dockerの枠の記録は表示だけに使い、Linuxでは枠を取らないので、動いているセッションはプロセスの一覧から判断する。Dockerの出力とプロセスの一覧は受け取る箇所で検証し、選別は純粋関数で行う。削除はタグを指定した `docker image rm` で行い、`--force` を使わない。計画の後に始まったセッションがイメージを使い始め、Dockerが削除を断った場合は、記録して続ける。stagingへのデプロイが残したタグは、次の `--full` で回収する。

実Containerの試験は、成功・失敗・中断のどの終わり方でも、自分のセッションのContainerを残さない。workerdは、アプリのContainerと、その通信を中継する `-proxy` のContainerに、セッションごとのラベル `dev.workerd.session` を付ける。Wranglerは、終了するときにこのラベルのContainerを消す。試験は、Wranglerを小さな監視プロセスの下で起動する。監視プロセスはWranglerのプロセスグループの先頭になり、試験のプロセスとのパイプが閉じると、Wranglerだけに SIGTERM を送る。パイプは、試験がWorkerを止めるときにも、試験のプロセスが中断の信号で終わるときにも閉じる。workerdには直接 SIGTERM を送らない。workerdが自分でアプリのContainerを消し始めると、同じContainerを消すWranglerの後始末がDockerに拒まれ（409）、`-proxy` を消さずに終わるためである。

Wranglerは、Containerのイメージのビルドなどの docker CLI を、自分のプロセスグループの外で起動し、対話の画面を使わない終了ではそれらを止めない。そのため、試験と `pnpm dev` は、Wranglerの環境変数 `WRANGLER_DOCKER_BIN` に仲介（`scripts/shared/docker-tether.ts`）を指定する。仲介は、本物の docker CLI を自分の子として同じプロセスグループで起動する。自分を起動したWranglerが終了・異常終了・強制終了で終わったことを、親のプロセスIDの変化で知ると、自分のプロセスグループに SIGTERM を送る。このグループには、その docker CLI とその子しかいないので、ほかのセッションのビルドには届かない。起動した時点でWranglerがすでに終わっていれば、docker CLI を起動しない。試験が時間切れで終わったときは、試験の後処理でWorkerを止める。

招待した利用者が使い始めるまでは、stagingだけを環境とし、本番の環境は作らない。本番の環境（設定、Accessアプリ、D1、R2、デプロイ手順）は、招待の前に6.6で用意する。本番はWorkerと静的ファイル、D1マイグレーション、R2、DO・Workflow、Containerイメージを一組の版としてデプロイする。RustはContainerの対象であるLinux向けにビルドし、Wasmは別の成果物として作る。形状処理のメモリと起動時間を測り、Containerのサイズ・同時実行数・休止条件を選ぶ。Cloudflareの利用料はできるだけ少なくする。Containerは動いている間だけ、確保したメモリ・ディスクと使ったCPUで課金される（[Containersの料金](https://developers.cloudflare.com/containers/platform/pricing/)）。そのため、インスタンスの種類と休止時間を利用料を左右する値として選び、止め忘れたContainerを残さない。

stagingはworkers.devのホスト名で公開し、Worker宛先のAccessアプリで守る（preview URLは無効）。mainへのpushでは、デプロイが読むファイルを一つでも変更したときにstagingへデプロイする。文書とエージェント向けの指示だけを変えるpushではデプロイせず、それらを読む検査はPRの `check` で行う。デプロイしないパスはworkflowの `paths-ignore` だけで定義する。デプロイは、出荷するコミットで `pnpm check --full` を実行し、通ったコミットだけをデプロイする。これが出荷するコミットでの全体検査で、PRの `--full` は、Containerの経路に触れる変更の失敗をマージの前に見つけるために残す。失敗したmainに変更を積み重ねないよう、デプロイを起こすマージは一件ずつ行い、前のデプロイが成功してから次をマージする。mainの最新の検査が失敗している間は、デプロイを起こさないPRと、その失敗を直すPRだけをマージする。この判定は指揮役のスクリプトが、mainの履歴とデプロイの実行の記録から毎回導く。マイグレーションはデプロイの前に適用するため、動いている前の版のWorkerと両立する形で書く。mainのデプロイのマイグレーションの検査は、mainからstagingへ最後に成功したデプロイのコミットと比べる。デプロイの流れ、デプロイしないパス、試験用ブランチのデプロイ、最初に環境を作る手順は、README「stagingへデプロイする」にまとめる。初期値の `.invalid` 発行元はローカル以外で拒否する。インスタンスの種類と休止時間は環境別の変数で指定する。Workers Logsを有効にし、Container内の標準出力もそこへ集める。接続用DOが出す `container.ready` ログの `mode: cold` で起動時間、Rustの要求ログの `vmHwmKib` でLinux上のメモリ最大値を読む。

Wranglerは、アップロードした版を約3秒のうちに読めないと、その版を公開したまま、Containerのアプリケーション設定とトリガーを適用せずに失敗し、同じ `wrangler deploy` のやり直しを求める。Wranglerの版を変えても直らないため、stagingのデプロイは `scripts/deploy/wrangler-deploy.ts` を通し、この失敗のときだけ同じコマンドを初回を含めて3回まで、待たずにやり直す。失敗はWranglerの構造化出力にある失敗の文の完全一致で見分け、ほかの失敗はやり直さない。

疎通の確認では、Accessのservice tokenを4.4の検証用ユーザーとして使う。確かめる項目、Client IDの渡し方、要求の期限は、README「stagingへデプロイする」にまとめる。

デプロイ・疎通・R2の確認が成功した後、`scripts/deploy/registry-retention.ts --apply` でstagingのContainerイメージを回収する。レジストリの `_catalog?tags=true` から、通常のタグと、Wranglerの一覧に出ないダイジェスト名を取得する。Cloudflareがデプロイ時に作る実行用イメージは、マニフェストの注釈 `io.cloudflare.cloudchamber.image_digest` が指す生成元のダイジェストで判定する。注釈がなければ自身のダイジェストを使う。最新10版と現在のデプロイに含まれる全版が、自身のダイジェストか生成元のどちらかを参照するものは、別名も含めて保持する。そのため、これらの版が直接参照するマニフェストは、注釈が古い版だけの生成元を指していても保持する。古い版だけが参照する通常のタグと生成元のダイジェスト名を削除する。レジストリは実行用イメージの削除を409（`SINGLETON_ARTIFACT_EXISTS`）で拒否するため、生成元を古い版だけが参照する実行用イメージは `prepared` に記録して残す。どの版からも参照されないものはデプロイ途中の可能性があるため、`unreferenced` に記録して残す。イメージを更新するたびに実行用イメージが1個残る。stagingのマニフェストに記載されたサイズでは、固有のレイヤーは約61〜91 MBで、約39 MBのベースレイヤーは共有される。Cloudflareは、実行用イメージの容量がアカウントの50 GB上限に算入されるかを明記していない。

対象リポジトリは保持対象の版のイメージ参照から一つに特定し、カタログのアカウントとリポジトリ名が一致するキーだけを使う。他のリポジトリは対象にしない。キーが見つからない場合、カタログに `Link` ヘッダーがある場合、版を全ページ読み切れない場合は何も消さずに失敗する。全対象マニフェストを取得して本文と注釈を検証し、`Docker-Content-Digest` が本文のバイト列のSHA-256と一致することを確かめる。ダイジェスト名はこの値とも一致しなければならない。検証に失敗した場合や、収集中にデプロイまたは最新版が変わった場合も削除を始めない。表示だけの実行にも同じ判定を使う。削除時は通常のタグを先に消し、続いてダイジェスト名を消す。タグと一緒に消えたダイジェスト名の404は記録して続行する。通常のタグの404はエラーとする。削除後に一度だけ未使用レイヤーの回収を依頼し、失敗は警告として記録する。workflowはデプロイと回収を一つずつ実行し、デプロイか疎通確認が失敗した実行では回収しない。

版の一覧に出た版の詳細が、コード100146（版が存在しない）のエラー一件だけの本文を返すときは、その版を読めない版として扱う。アップロードした直後の版にはCloudflareの版のAPIがこの404を返し、`wrangler deploy` をやり直した実行では失敗した試行の版も履歴に残る。その版が回収の時点（デプロイの0.5〜4.5分後）に読めるかは観測しておらず、24〜28分後には読めた。読めない版が最新10版か現在のデプロイに含まれるときは、その版がどのイメージを参照するか分からないので、その実行では何も削除せず、レジストリの認証情報も取得せずに `registry retention deferred` の警告を出し、成功で終える。版が読めるようになった後の実行が、残ったイメージを回収する。読めるまで待って読み直すことはしない。読めるまでの時間が分からず、デプロイは一つのrunnerで順に流れるので、待つ間は次のデプロイも止まるためである。保持対象より古い版が読めないときは、回収を続ける。古い版はもともとイメージを保護しないので、その版の参照が分からなくても削除の候補は増えず、その版だけが参照するイメージは `unreferenced` に記録して残る。保持対象のうち読める版が参照するリポジトリが一つでなければ、読めない版があっても失敗する。版の詳細のほかの404、ほかの状態コード、形の違う本文では、これまでどおり何も消さずに失敗する。

stagingの計測から、次の構成と値を使う。数値と手順は[検証3](verification/verification-03.md)にある。

- Container上のSolidCraftは、standard-1の資源の範囲でサンプルを処理できた。4.1の構成を採る。
- インスタンスの種類（`GEOMETRY_INSTANCE_TYPE`）は、当面standard-1とする。サンプルではliteとの処理時間の差が出なかったため、#103 で住宅一軒分の形状処理を測り、処理時間と利用料から決め直す。
- 休止時間（`GEOMETRY_IDLE_TIMEOUT_MS`）は、当面10分とする。#103 で起動時間と利用料を測って決め直す。
- 内部ルートのタイムアウト（`routeTimeouts`。healthは2秒、sampleDisplayは30秒）と、readinessの期限（60秒）は変えない。新しいイメージの最初の起動は、readinessの期限に近い時間がかかった。期限を延ばすと、本当に起動できないときに利用者が失敗を知るまでの待ち時間が延びるため、6.2でイメージを小さくする方法を検討する。
- 資源設定の根拠には、Cloudflare上の計測を使う。ローカルの値はamd64のエミュレーション上の値なので、根拠にしない。

起動確認が終わってから処理を渡す。長い処理ではコンテナの生存時間を明示的に管理する。ブラウザ、Workflow、ContainerのHTTP接続が切れたことだけを、ジョブの完了や取消の証拠にしない。

Containerを止める時刻は、接続用DOが決める。DOは要求の開始時と終了時に最後の操作の時刻をストレージに保存する。操作には起動待ちと応答本文の読取り・検証を含め、失敗した操作も終了時刻を記録する。readinessの確認、アラーム、DOの再起動は操作に数えない。アラームは最後の操作の時刻に休止時間を足した期限に置く。期限前なら最新の期限に置き直し、操作中なら現在時刻から休止時間後に置き直す。最後の操作の完了で再び期限を更新する。操作が無く期限を過ぎていれば、`destroy()` でContainerを止める。成功後に、次の起動を待たせたまま開始の記録・操作時刻・アラームを消し、`container.idle_stopped` の `ms` に最後の操作からの時間を出す。停止済みのアラームの再配信は新しい停止を起こさない。停止に失敗したら記録を残して `container.destroy_failed` を出し、1秒から倍増し休止時間を上限とする間隔で自分でアラームを置き直す。間隔はDOのストレージに持つので、再試行の間にDOが再起動しても倍増を続ける。操作が始まるか停止に成功したら、間隔を消す。実行環境の回数に限りがあるアラーム再試行だけには頼らない。

DOが再起動しても、動いているContainerの保存済みの期限を戻し、操作時刻を更新しない。時刻が無い・不正・未来なら現在時刻を保存して期限を作る。止まっているContainerの記録とアラームは片付ける。`setInactivityTimeout` は、起動時、DOの再起動時、各操作の終了時に、休止時間 + 60,000 msで設定する。この値は、DOが非アクティブになった後にContainerが動き続ける時間である（[Container API](https://developers.cloudflare.com/containers/api/durable-object-container/)）。ローカルの実行環境は、この時間を呼んだ時点から数え、actorを最後の要求から10秒で止める（workerdの `ContainerClient::setInactivityTimeout`）。そのため操作のたびに設定し直し、続けて操作した後もContainerがアラームまで動くようにする。設定に失敗しても操作の結果は変えず、`container.inactivity_failed` を出す。アラームが新しいDOを起こす場合でも実行環境に先に止められないよう、60秒の余裕を持たせる。実行環境の上限6時間に収まるよう、休止時間は60,000〜21,540,000 msを設定の境界で受け付ける。

接続用DOの呼出しは、操作が終わったときに閉じる。DOでは、終わっていないI/Oとタイマーがすべて、呼出しの完了を待つ作業に数えられる（workerdの `IoContext`）。最新の呼出しは、それらが空になるか、次の呼出しが届くか、DOが止まるまで終わらない。Workers Logsは呼出しのログを呼出しが終わってから載せる。DOは、操作が退去を妨げている間、時間で課金される（[DOのライフサイクル](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)）。そのため接続用DOは `container.monitor()` を呼ばない。待ち中の `monitor()` は、Containerが止まるまで呼出しを開いたままにする。内部要求とreadinessの試行の期限には、`AbortSignal.timeout()` ではなく、解除できるタイマーを使う。内部要求の期限は応答本文の読取りまでを含み、操作の終わりに解除する。readinessの試行の期限は、試行ごとに解除する。

Containerの終了は `container.running` で知る。実行環境は、`monitor()` を呼ばなくても、Containerが終わると `running` を偽にする。readinessの確認では、試行の前と健全な応答の後に `running` を読み、偽なら `exited` で失敗にする。準備ができた後の終了には、次の操作・アラーム・DOの再起動で気づき、次の操作は新しいContainerを起動する。接続用DOは終了のログを出さない。終了の時刻と終了コードは、実行環境がContainerのサービスとしてWorkers Logsに出す `Container exited (code: N)` で読む。この行はローカルの `wrangler dev` には出ない。

呼出しが閉じると、DOは休眠または退去しうる。次の呼出しでは、新しいDOが保存したトークンで動いているContainerを引き継ぎ、healthを一度確かめる（`container.ready` の `mode: adopted`）。

停止の時刻を接続用DOが決めるのは、Cloudflare側の仕組みだけでは、Containerが休止時間どおりに止まらなかったためである（[検証3の休止後の停止](verification/verification-03.md#休止後の停止)）。

### 5.2 AI費用・処理時間・利用量の上限

| 設定               | 初期値と扱い                                                                     |
| ------------------ | -------------------------------------------------------------------------------- |
| AI費用の月額       | サービス全体で100米ドル。初期設計ではUTCの暦月で集計する                         |
| 一指示のAI費用     | 5米ドル。再試行と修正のための呼び出しも含む                                      |
| 同じパターンの編集 | 同時に一件                                                                       |
| Cloudflare利用料   | AI予算とは別に計測・監視し、できるだけ少なくする。月額の実測前に定額を約束しない |

これらは運営が変更できる初期の歯止めであり、費用・速度の目標値ではない。月額の残額が不足すれば新しいAI処理を受け付けず、実行中の指示が上限に達したら未確定案を採用せず終了する。元の指示と理由は会話に残す。一指示の処理時間には上限を置かず、5.3のとおり所要時間を記録する。

各API試行の前に、入力、画像、最大出力、モデルの料金から費用を見積もり、月額とジョブ双方の残額を条件付きで予約する。応答後に利用量で精算する。使用量が取得できない試行は予約額を解放せず保守的に計上し、後から照合する。既に開始した外部呼び出しまで厳密に即時停止できるとは扱わない。

予約は、試行の行を追加する一つの文で行い、次の三つがすべて成り立つときだけ行を追加する。

- 実行権のジョブが、その世代で `running` である。
- 予約の時刻の月に数える額の合計に予約額を足しても、月額の上限以下である。
- そのジョブのすべての試行に数える額の合計に予約額を足しても、一指示の上限以下である。

D1は一つのデータベースで一度に一つの問い合わせを処理するので、同時に予約しても、各予約は先に処理された予約を含めた合計を読む。同じbatchの次の文が、追加の文と同じ条件の部品で結果を分け、予約できた、一指示の上限、月額の上限、実行権の喪失のどれかを返す。両方の上限に当たるときは一指示の上限を返す。一指示の上限はほかのジョブに左右されず、月額に残りがあれば新しい指示はまだ予約できるためである。上限は `storage/` が `limits.ts` から読み、呼び出し側が上限を渡す方法は作らない。

試行IDは、サービスが予約のたびに新しく作る。同じ試行IDで予約を繰り返しても行は増えない。その場合、ジョブが動いていれば予約できたと返し、停止の後なら実行権の喪失を返す。Workflowの段階を再試行したときは、前の実行がAPIを呼んだかを知れないので、新しい試行IDで予約し直す。前の試行は、精算されなければ予約額のまま数える。

精算は、ジョブの参照（ジョブIDと世代）と試行IDで行を特定し、未精算の行にだけ確定額と利用量を書く。同じ精算を繰り返しても何も変わらず、記録と違う額や利用量での精算は例外にする。精算は実行権を求めず、ジョブの状態も問わないので、停止・失敗・上限到達の後にも行える。請求は外部呼び出しの時点で生じているためである。確定額が予約額を超えても、そのまま記録して数える。利用量が分からない試行を表す操作は作らず、精算されない行が予約額のまま数えられる。

試行は予約した時刻の月に数え、精算した時刻の月へは移さない。上限を検査した月と、その額を数える月を一致させるためである。月が変わると、新しい月の合計は、その月に予約した試行だけから求める。一指示の上限は月をまたいで、そのジョブのすべての試行を数える。

金額は、マイクロ米ドル（100万分の1米ドル）の整数で扱い、保存も同じ単位にする。料金は、100万トークンあたりのマイクロ米ドルの整数で持つ。キャッシュの読込みの0.20米ドルは、1トークンあたりでは0.2マイクロ米ドルだが、100万トークンあたりなら200,000で整数になる。見積もりと精算の額は、区分ごとにトークン数と料金を掛けて足し、100万で割って一度だけ切り上げる。

見積もりは、その試行に請求されうる額の上限とする。入力トークンの上限に入力側で最も高い料金を掛け、最大出力に出力の料金を掛けて足す。Claude Opus 5.5では、入力側で最も高いのは1時間のキャッシュ書込みの料金である。キャッシュが残っている保証はなく、どの試行もキャッシュの書込みか通常の入力として請求されうるので、キャッシュの読込みを当てにしない。思考は常に有効で、そのトークンは最大出力に含まれ、出力として請求される。そのため、最大出力の全量を出力として数える。

入力トークンの上限は、Anthropicのトークン数のAPIを呼ばず、要求の内容から求める。トークン数のAPIは、試行ごとに通信と失敗の経路を一つ増やし、会話を二度送らせる。その数も見積もりと明記されているので、余裕を足す必要は残る。

- 最初の試行では、システムの指示、ツールの定義、最初の発言の文字列を、UTF-8のバイト数で数える。一つのトークンは1バイト以上を表すので、バイト数はトークン数以上になる。ツールがあれば、ツール利用のシステムの指示（Claude Opus 5.5では286トークン）を足す。要求、発言、部分、ツールごとに、枠の分として固定のトークン数を足す。
- 2回目以降の試行では、直前のアシスタントの発言に付いた利用量を使う（4.2）。会話は前の要求に組を足すだけなので、その試行の入力の合計は、今回の要求の先頭部分と等しい。これに、その発言の出力トークン（思考を含めて請求された数）と、新しい返事を最初の試行と同じ方法で数えた数と、枠の分を足す。思考の部分は中身が読めないので、その大きさを請求された出力トークンで抑える。
- 画像は、⌈幅/28⌉×⌈高さ/28⌉ の視覚トークンで数え、Claude Opus 5.5の一枚の上限の4,784トークンを超えれば4,784とする。縮小はトークン数を減らすだけなので、縮小前の寸法で求めた数を上限で抑えれば、縮小を再現しなくても上限になる。寸法はPNGのIHDRからだけ読み、JPEG、GIF、WebPと、読めないPNGは4,784トークンとする。GIFの論理画面やJPEGの区切りの読み取りは、復号器が使う寸法より小さい値を示しうる。一枚を多めに数えても、予約は0.04米ドルしか増えない。

精算では、区分ごとの利用量にそれぞれの料金を掛ける。利用量が見積もりの入力または出力のトークン数を超えたかも返す。試行の行は見積もりのトークン数と利用量を残すので、超えた試行は行から分かる。枠の固定値とバイト数による上限が実際の請求と合っているかは、この記録で照合する。

予約の大きさは最大出力で大きく変わる。ジョブの試行は一つずつ進み、精算で予約が確定額に置き換わる。そのため、予約の大きさは、一指示の最後に使えずに残る額の上限と、同時に動くジョブが押さえる月額の枠を決める。入力トークンの上限と最大出力ごとの一回の予約額は、次のとおりである。

| 入力トークンの上限 | 最大出力16,000 | 最大出力32,000 | 最大出力64,000 |
| ------------------ | -------------- | -------------- | -------------- |
| 50,000             | 0.72米ドル     | 1.04米ドル     | 1.68米ドル     |
| 100,000            | 1.12米ドル     | 1.44米ドル     | 2.08米ドル     |
| 200,000            | 1.92米ドル     | 2.24米ドル     | 2.88米ドル     |

最大出力はAIの接続で決め、32,000トークンを目安にする。32,000トークンで会話が10万トークンなら、一指示は使った額が3.56米ドル以下の間、次の試行を予約できる。会話が16万〜20万トークンに育つと、実際の一往復が0.2米ドル前後でも予約は2米ドル前後になり、一指示の3〜4割を残して上限に達しうる。上限を超えないことを優先して、これを受け入れる。AIの接続がキャッシュの書込みを5分だけに限ると決めた場合は、入力を5分の書込みの料金で数え、予約の入力の分を3/8減らせる。

料金の表は、通常の速度と、全世界への振り分け（既定）の料金である。米国内だけで推論する指定（全区分1.1倍）と、拒否のときに代替モデルへ回す設定は、その料金を表に加えるまで使わない。

設定ファイルは `apps/worker/src/limits.ts` とする。どの層にも属さない直下のファイルなので、`services/` と `storage/` の両方が読める。月額と一指示の上限、使うモデル、モデルごとの料金と画像のトークンの規則を持つ。ほかの5.2の上限もここに加える。

添付の形式・ファイルサイズ・画素数、操作数、一つのジョブのAIの往復と検査で直させる回数、形状の規模、APIの頻度にもサーバー側の上限を設ける。往復と直させる回数の上限は、同じ失敗を繰り返して終わらない処理を止める。数値は資源消費を確認して設定ファイルへまとめる。操作数・往復と直させる回数・形状の規模・APIの頻度は6.1と6.2で、添付の数値は添付を受け付ける6.4で決める。モデルやプロンプトに対する変更で、上限検査を迂回できないようにする。

### 5.3 ログ・性能・費用の計測

request ID、job ID、操作ID、案IDを通して処理を追えるようにする。AI待ち、形状計算、検査、保存、転送、描画、初回プレビューまでの時間と、一指示の実行開始から終了までの時間、Containerのメモリと稼働時間、API利用量・費用を分けて記録する。

WorkerとContainerの要求ログは、503を含む5xxをerror、それ以外をinfoとする。エラーログには段階と原因を残し、会話・画像・CADデータの本文や秘密情報を無条件に出力しない。必要な調査では、権限のある保存データを参照する。

WorkerとContainer接続用DOのログは、許可するキーとキーごとの値の型を共通の `LogFields` で定義する。文字列の値を持つキーは、値の出どころが持つ閉じた語彙だけを受け付ける。そのため、要求の本文や資格情報を値に書くコードは型検査を通らない。`route` はHTTPのメソッドとAPIのルートのパスの組とし、healthの要求は `/api/health` とする。`method` はRFC 9110とRFC 5789が定めるメソッドとする。`step` はジョブの段階名とする。`outcome` は、ジョブの段階・ジョブ・停止・パターンDOの前進の結果の種類と、段階が例外で終わったことを表す `error` とする。`reason` は形状の呼出し・ジョブ・Containerの失敗の種類、`geometryFailure` と `geometryViolation` は形状の呼出しの失敗と規約違反の種類とする。`request.method` はクライアントが選ぶ値なので、受け取る箇所で標準のメソッドと照らす。一覧に無い値は、`rayId` と同じく記録しない。

ログのモジュールはNode.jsの型だけで検査するテストからも読み込むので、語彙の型はWorkersの型に依存しないモジュールからだけimportする。メソッドとルートのパスは `apps/worker/src/api/http.ts` の型を使い、ルートの定義の `path` もその型で検査する。形状の呼出しの失敗と規約違反の種類は、`apps/worker/src/geometry/geometry-protocol.ts` の結果の型から導く。Workers専用のモジュールが持つ語彙（ジョブの段階名・結果の種類・ジョブの失敗理由）と、ログの呼出しにだけ現れる値は `LogFields` に列挙する。値を書く箇所では出どころの型をそのまま代入するので、出どころに値を足すと、`LogFields` に足すまで型検査が失敗する。

閉じた語彙を持たないキーは文字列のまま残す。`traceId`・`requestId`・`patternId`・`jobId`・`messageId`・`revisionId` は、Workerが生成したIDか、受け取る箇所でUUIDとして検証したIDを持つ。`userId` の出どころの型は所有者IDのブランドだが、その定義はD1の型に依存するモジュールにあるので、ログの型には使わない。`rayId` は文書化された形と一致する値だけを持つ。`image` はContainerの実行環境が返すデプロイのイメージの参照で、要求からは来ない。任意の文字列を受け付けるキーの一覧はテストの型検査で固定する。キーを足したときや語彙が任意の文字列へ広がったときは、その型検査が失敗する。

出力するキーの表は、各キーを値の原始型（`"string"` か `"number"`）に対応させる。表の型は `LogFields` の各キーの型から導いて過不足なく照合するので、キーの追加・削除や原始型の変更には、型定義と表の両方の変更を必要とする。文字列と数値の両方を受け付けるキーは定義できない。JSON化する前に、表にあるキーで、値の `typeof` が表の原始型と一致する項目だけを写す。変数の代入や `Object.assign` で混ざった未許可キー、原始型の違う値、許可キーの値に入ったオブジェクト・配列・関数は出力しない。値の `toJSON` も呼ばない。出力時には文字列の内容を検査しない。`error` の型は、ログのモジュール内だけで見える `unique symbol` のブランドを持つ `describeError` の戻り値とする。

利用時の確認は、希望の反映、空間の整合性、変更の引き継ぎ、質問の有用さ、待ち時間を分けて記録する。どれを改善すればよいか判断できる粒度を保つ。

### 5.4 データの保護・復旧・形式変更

D1の復旧手段を用意し、復旧時点の履歴が参照するR2の不変オブジェクトを揃えて戻せるようにする。DBだけを戻して案の実体が欠ける復旧を避ける。初回提供前に、別環境への復元と保存済みの案の再編集を確認する。

未確定の作業データ、未参照のアップロード、期限切れプレビューを回収対象にする。確定しなかった案のR2オブジェクト（R2へ保存した後にD1へ確定できなかったsnapshot）もこれに含める。確定案や複製元から参照される画像・形状・会話は、利用中の参照を確認せず削除しない。復旧用の保持範囲も回収判定に含める。snapshotがどの案からも参照されていないことは、`revisions` の `(snapshot_id, owner_id)` の索引で判定する。

画像と会話は、必要な範囲を選んでAIの商用APIへ送る。利用するAPIのデータ利用・保持条件を運営で確認し、利用者が確認できる場所に説明する。AIを呼ぶ資格情報やモデルの変更はサーバー設定で管理する。

保存形式には版を付け、読込時の移行処理を用意する。旧形式の案を直接上書きせず、移行結果を確認したうえで新しい内容を保存する。

### 5.5 AIモデル・SolidCraft・依存ライブラリの更新方針

SolidCraftの初回取り込みは `https://github.com/tangency-labs/solidcraft` のコミット `9325e3ac8cc1dcad67bc5d218274e89e8a9b26fc` を基準とし、`third_party/solidcraft/` をgit subtreeとして管理する。既存のGit履歴を保持し、初回取り込みとupstreamの対応を記録して、次回以降もsubtreeとして更新できる状態にする。現在の採用版は[取り込み記録](../third_party/solidcraft.json)に記録する。

住宅固有の機能は取り込み領域の外に置く。SolidCraft自体に必要な変更は、その内部の配置や名称をできるだけ保ち、サービス側の変更とはコミットを分ける。取り込み元・採用コミット・独自変更の理由と更新手順を `third_party/solidcraft.md` に記録する。

更新時は採用するupstreamのコミットを選び、専用の作業ブランチでsubtreeへ取り込む。独自変更と同じ箇所が変われば競合を解消し、ビルドと住宅機能への影響を確認して採用する。ルートへ通常のupstreamマージを行う手順とは区別する。upstreamの更新は原則取り込む。住宅サービスの機能・構成・動作環境に問題が出る場合は調整するか、理由と再検討条件を記録して保留する。有用な改善を継続して取り込める状態を維持する。

モデル・プロンプト・操作スキーマ・住宅データ・描画の版も記録する。

更新時は、保存済みの案の読込・再編集、形と面の対応、素材の引き継ぎ、2D・3D・面積、ジョブの復帰を確認する。AIの変更では同じ相談例で生成・編集を見比べる。品質向上の作業を、本体実装開始の条件へ戻さない。

**完了条件**

断片的な希望から小さな平屋を生成し、表示された壁を選んで移動・色変更を指示できる。壁にアーチ形の入口などの加工と簡単な物体を指示でき、壁を動かすと、加工と壁に付けた物体が3.5の引き継ぎのとおりについていく。2D・3D・面積が一致し、色が維持され、再ログイン後も編集できる。質問だけの応答は案を増やさない。不正な操作、上限到達、停止で未確定の変更が公開されない。別利用者のパターンの途中経過（SSE）を受け取れない。

**この段階で確かめること**

住宅情報とCADの更新方式、共有境界と斜めの接合に拡張できる形、面積計算の許容差、AIのツール往復に必要な情報。住宅一軒分の形状処理でContainerのメモリと処理時間、表示データの大きさを測り、インスタンスの種類と休止時間を決め直す（[検証3](verification/verification-03.md)のサンプルは軽すぎて決められなかった）。実際の相談例で、一指示の所要時間を測る。Containerのイメージを小さくする方法を検討し、新しいイメージの最初の起動時間を測る（検証3では、readinessの期限60秒に近かった）。計測には、検証3で使ったbashのスクリプト（`docs/verification/evidence/verification-03/`）をTypeScriptで `scripts/measure/` に作り直したものを使う。`scripts/` の型検査・ESLint・テストの決まりに合わせるためである。間取りの提案品質は記録して改善し、初期に高品質な提案が出ないことだけで全体の実装を止めない。

参考画像から取り入れた特徴を示せ、その家具を移動・変更できる。家具の変更で2Dの占有範囲が更新され、部屋の面積は変わらない。壁の移動・伸縮・分割後も素材と柄の尺度が維持される。部屋の変更で家具を勝手に拡大・削除しない。別利用者の添付画像を読めず、指示にも添えられない。

**この段階で確かめること**

素材対応を追加したWasmのサイズと描画負荷、画像からの特徴の取り込み、形状更新での素材座標の維持。実際の画面で確認する。

### 6.5 敷地・隣家と日差し

**実装するもの**

- 敷地画像・寸法・会話からの入力、隣家の形・位置・高さ、仮置き条件の表示。
- 敷地内への配置検査、地域・方位・月・時刻の指定。
- 編集中の住宅モデルへの直射光と遮蔽の計算・表示、条件ごとの結果管理。

**完了条件**

同じ日時で、窓の位置、屋根、建物配置、隣家を変えた日差しの違いを確認できる。屋根を表示から隠しても日差しの計算は変わらない。敷地に収まらない案は確定しない。仮の地域・方位・寸法が実測値のように表示されない。

**この段階で確かめること**

細い日差しを見落とす条件、床・壁・天井での表示、時刻変更への応答、一般の住宅と周辺形状での処理時間。答えを別に求められる単純な条件で誤差を確認し、表示の細かさと速度を調整する。

### 6.6 履歴・複製・画像出力を含む相談体験の完成

**実装するもの**

- 複数パターンの切り替え・複製、履歴の一覧・プレビュー・復帰。
- 会話の引き継ぎと取り消された操作の区別、待機・保留指示の操作。
- 間取りPNGの出力、次の商談での再開、運用の計測と復旧手順。
- 5.4の回収。未確定の作業データ、確定しなかった案のR2オブジェクト、未参照のアップロード、期限切れのプレビュー。
- 招待の前に用意する本番の環境。設定、Accessアプリ、D1、R2、デプロイ手順（5.1）。

**完了条件**

一つの案件で異なる土地と家を検討し、それぞれ独立して相談を続けられる。過去案への復帰で後の案が消えず、複製後の会話や変更が混ざらない。ブラウザを閉じても処理が継続し、開き直して結果を見られる。間取り画像を保存でき、別環境へのデータ復元後も編集できる。

**この段階で確かめること**

招待した営業が、案件作成から生成・変更・比較・保存・再開まで使えること。PCブラウザでの日本語入力、対象選択、室内の視点操作、通信断、長い会話、複数パターンを含めて確認する。利用中に見つかった不足を、機能・品質・性能に分けて改善する。

## 付録C. 面積表示の参照先

[不動産の表示に関する公正競争規約施行規則、第9条第16号](https://www.rftc.jp/webkanri/kanri/wp-content/uploads/2025/08/20250826_kiyakushuu.pdf#page=17)では、居室等の畳数表示に対し、壁心面積を表示畳数で割った値を1.62 m²以上とする基準がある。

本サービスは内法面積を1.62 m²で割った参考値を表示する。この換算値の参照だけをもって、広告表示規則への適合を保証するものではない。
