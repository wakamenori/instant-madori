# 住宅相談サービス 実装計画

更新日：2026-11-14

初回提供までの仕様、設計、実装順をまとめる。事前の技術検証は完了扱いとし、これから本体を実装する。生成品質・性能・一般の住宅への対応は、各実装段階で確認・改善する。合意した要件に加え、API、モジュール名、保存形式などは実装に向けた初期設計を記す。

## 1. 目的と初回提供の範囲

### 1.1 目指す体験と到達点

施主の断片的な希望をその場で間取りと3Dにし、営業と一緒に見ながら住まいのイメージを具体化する。家の形だけでなく、家具の配置、素材、敷地や隣家との関係、窓からの日差しも相談できるようにする。

初回提供の到達点は、招待された営業が自分の案件で案を作り、変更・比較し、保存して次の商談から再開できること。6章の全段階を初回提供の範囲とする。最初の一往復が動いた時点は、途中の実装到達点である。

### 1.2 利用者・利用場面・利用環境

- 注文住宅の初回相談で、営業が操作し、施主と同じ画面を見る。
- PCのブラウザを対象にする。住宅を変更するためのCAD操作は要求しない。
- 招待制とし、メール認証コードでログインする。案件は個々のユーザーに所属する。
- AIは運営側で用意し、費用を負担する。営業によるAPIキーの登録は不要。
- 対応ブラウザの確認は6.1と6.6で行う。WebGPUの利用可否を判定し、利用できない場合に理由を表示する。

### 1.3 対応する住宅と機能、初期の対象外

| 対象         | 初回提供で扱う範囲                                                                           |
| ------------ | -------------------------------------------------------------------------------------------- |
| 階・部屋・壁 | 平屋と2階建て。各階の床は同一高さ。直線の壁、斜めの壁、L字などの部屋。LDKは一室として扱う    |
| 屋根         | 陸屋根・片流れ・切妻・寄棟。複数の屋根の組み合わせ、勾配・軒の出の変更                       |
| 階段         | 直階段・L字・折り返し。踊り場と回り段。段板・手すりなどの形と見た目の変更                    |
| 窓・ドア     | 取り付け先の壁、位置、幅・高さを持ち、間取りと3Dで同じ配置を表す                             |
| 家具・素材   | 言葉や参考画像から特徴を取り入れた家具の作成・配置・変更。色と、木目・タイルなどの柄の表示   |
| 敷地・周辺   | 敷地の形・寸法・方位・道路、隣家の配置・高さ・形。画像と会話で入力し、不明な条件は仮置きする |
| 日差し       | 地域・方位・月・時刻に応じた直射日光と遮蔽。家の配置・窓・屋根・隣家の影響を反映する         |
| 相談の継続   | 案件、複数パターン、会話、案の履歴、過去案からの再開、複製、間取り画像の保存                 |

初期の対象外は、3階以上、地下室、スキップフロア、曲面の壁、螺旋・自由曲線の階段、曲面屋根、壁のない用途別領域の面積表示、住所からの周辺建物の自動取得とする。画像の完全再現、写実的な反射、反射光を含む室内照度の定量予測も要求しない。

タブレット、会社・チームでの共同編集、一般向けの自己登録、課金機能、案を横に並べる比較、図書一式の出力、CAD連携、法規・構造の適合判定は初回提供に含めない。

## 2. 利用の流れと画面の仕様

### 2.1 案件の作成とパターンの管理

案件一覧から案件を作り、一つ目のパターンを開始する。案件名とパターン名には初期名を入れ、後から画面で変更できる。敷地が未定でも始められる。案件名などの管理情報の変更と、住宅内容の編集は区別する。

一つの案件に、別の土地での検討と、同じ土地での別案を持てる。パターンを切り替えると、住宅・敷地・会話・履歴・実行状態も切り替わる。別パターンで進行中の処理は継続する。

案件画面は、間取り・3Dの表示領域と、会話・履歴・指示欄で構成する。現在のパターン、表示中の案、編集中か確定済みかを分かるようにする。

### 2.2 AIへの指示・画像添付・対象選択・聞き返し

住宅・家具・素材・敷地・隣家の変更は、テキストと画像によるAIへの指示で行う。画面から壁や家具などを選択し、指示の対象として添えられる。初期設計では選択対象を最後の確定案に限定し、作業途中の形を確定した対象として送らない。

希望が全部揃うまで入力を要求せず、未指定の部分を仮置きして案を作る。画像では、気に入った特徴を取り入れることを目指す。読めない寸法や見えない部分を推定した場合は、その条件を会話で伝える。

AIは必要に応じて質問や選択肢を出せる。聞き返す基準は運用中に調整する。質問だけの応答では案を増やさない。初期設計では、未確定の編集の途中で質問する場合、その作業用コピーを破棄し、回答を受けて最後の確定案から編集を始める。

生成中も追加指示を送れる。指示には受付順と、選択時の案・対象IDを記録する。実行時には直前までの確定結果を使い、選択対象が消えていたら勝手に別の対象へ置き換えず、会話で確認する。

### 2.3 間取り・3D・日差しの表示と操作

| 表示   | 操作と内容                                                                                                   |
| ------ | ------------------------------------------------------------------------------------------------------------ |
| 間取り | 階の切り替え、拡大・移動。部屋名・広さ・方位、壁・窓・ドア・階段・家具の配置を表示する                       |
| 寸法   | 初期設計では建物の外形寸法と選択した部屋・壁の主要寸法を表示する。複雑な部屋を一つの幅・奥行きだけで表さない |
| 3D     | 回転・拡大、室内を見るための視点移動、視点リセット。室内を見やすくする屋根・上階の表示切り替えを用意する     |
| 日差し | 月と30分刻みの時刻を選択する。各月21日を代表日とし、実際に計算する年・日付・時刻を表示する                   |

視点や表示、日差しの月・時刻は画面で直接変更し、案の履歴を増やさない。地域と方位は住宅・敷地の条件として案に保存し、変更はAIへの指示で行う。未指定なら仮の条件を表示する。初期値は東京相当の位置・日本標準時・画面上方向を北とし、計算年は利用時の年を使う。

間取り・3D・面積は同じ案を表示する。別の時点の表示データを混ぜない。屋根などを見やすさのため非表示にしても、日差しの遮蔽物からは除かない。

### 2.4 生成途中・待機・停止・失敗時の表示

| 状態                 | 画面と次の処理                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| 実行中               | 作業の区切りでプレビューを更新し、最後の確定案と区別する。追加指示は待機列に入れる             |
| 質問待ち             | 質問を会話に残し、確定案を維持する。質問への回答を先に扱えるよう、待機列の自動進行を保留する   |
| 完了                 | 新しい案へ切り替え、変更内容と残る使い勝手の懸念を説明する。次の待機指示を実行する             |
| 停止・失敗・上限到達 | 未確定の変更を採用せず、最後の確定案へ戻す。待機指示は保留し、再開・取り消しを選べるようにする |
| 接続断・画面を閉じた | サーバーで処理を継続する。開き直したときに進行状況と結果を読み直す                             |

停止の受理後に届いた結果は採用しない。確定のほうが先に完了していた場合は、その完了を返し、停止によって完成済みの案を取り消さない。過去案への復帰は別の操作で行う。

プレビューの更新間隔は実測で調整する。負荷が大きければ更新頻度を下げ、完了時だけの更新にも切り替えられる構成にする。10分の処理上限は、目指す応答速度ではない。

### 2.5 履歴の閲覧・復帰・パターンの複製

AIが編集をまとめて案を提示するたびに履歴を一件追加する。案には変更内容から名前を付ける。内部コマンドや会話一件ごとに案を増やさない。

過去案は閲覧専用とし、プレビュー中の編集入力を無効にする。「この案から続ける」でその内容を新しい履歴項目として末尾へ追加する。後の案と会話は消さず、どの案へ戻ったかを記録する。AIは希望や参考画像を参照しつつ、取り消された操作を再適用しない。

パターンの複製では、起点となる確定案と、そこまでの案の履歴・会話を引き継ぐ。最新案からの複製は、その時点までに完了した会話も含める。質問だけで終わった往復も対象とする。過去案からの複製は、その案を提示した時点で会話を区切る。未実行の指示と進行中のジョブは複製先へ持ち込まない。複製後の変更は独立する。

初期設計では、実行中のパターンを復帰させる操作は、完了または停止を待って行う。待機指示があれば保留する。複製は確定済みの案から行えるため、複製元の処理を止める必要はない。

### 2.6 保存・再開・間取り画像の出力

確定案と会話はサーバーに保存し、手動保存を要求しない。再開時には最後の確定案と、待機・実行中・保留の状態を復元する。

間取り画像は表示中の階をPNGで保存する。部屋名、面積、方位、表示中の寸法を含め、案件・パターン・案・階が分かる名前にする。対象は確定済みの案とし、プレビュー中の過去案も出力できる。生成途中の形は出力対象にしない。

## 3. 住宅データと編集のルール

### 3.1 階・部屋・共有境界・壁の表現

住宅の編集データを次の構成で持つ。各要素には名前とは別の安定したIDを与える。

| 要素       | 保持する情報                                                         |
| ---------- | -------------------------------------------------------------------- |
| 階         | 基準高さ、階高、床領域、階段の床開口                                 |
| 頂点・境界 | 平面上の座標、境界の始点・終点、接する部屋、対応する壁               |
| 部屋       | 名前・用途、向きを持った境界の列。輪郭はこの境界から得る             |
| 壁         | 境界への参照、厚さ、高さ、室内側・室外側などの面の役割、開口への参照 |

隣室との境界を一つのデータで共有し、変更時に両側の部屋と壁を更新する。部屋の輪郭と壁座標を独立に書き換えて後から合わせる方式は採らない。壁厚を反映した室内側の輪郭から、面積と2D表示を生成する。LDK内部の用途は設備・家具の配置で表し、用途別の面積境界を追加しない。

壁の追加・分割・統合では、境界と部屋の関係も同じ操作内で更新する。部屋IDを残すか統合先へ移すかを操作結果に含め、参照先が変わったことをAIへ返す。

### 3.2 窓・ドア・屋根・階段の表現

開口は、取り付け先の壁ID、壁上の位置、幅、高さ、床からの高さ、種別、見た目を持つ。壁の移動では壁上の位置関係を保ち、壁を短くして収まらなくなった場合は再配置・寸法変更を調整する。開口の形状やドアの開き方など、表示に必要な情報を別に持つ。

屋根は、覆う領域、形式、基準高さ、勾配、軒の出、素材を持つ。複数の屋根の接合も更新対象に含める。建物の外形変更で屋根だけが元の大きさのまま残らないようにする。

階段は、接続する階、昇り口・降り口、経路、幅、段の構成、踊り場・回り段、床開口を持つ。段板・手すりの意匠を別の部品として関連付け、経路や寸法の変更時に引き継ぐ。CADの一つの立体へ置き換えて、上下階の接続情報を失う扱いにはしない。

### 3.3 家具・素材・敷地・隣家の表現

家具は、形を作る編集可能なCADデータ、位置・姿勢、基準寸法、素材、関連する部屋ID、参考画像への参照を持つ。部屋の広さが変わっただけで家具を拡大しない。2Dの外形は変更後の3Dから生成する。

素材は、色、柄の画像または生成パラメータ、実寸の柄の大きさ、向き、適用する部品・面の役割を持つ。壁の伸縮で木目やタイルの大きさまで伸びない初期設計とする。参考画像と、実際に表示に使う素材データを区別する。

敷地は境界、寸法、地域・方位、道路を持つ。隣家は配置、形、高さを持ち、室内の間取り情報を要求しない。入力には画像と会話を使い、確認済みの寸法と推定値を区別して保存する。形・配置は後から変更できる。

### 3.4 寸法・面積の計算と表示基準

長さはmm、面積はm²で保持・計算する。寸法を固定のマス目へ丸めず、任意の値を指定できるようにする。AIが生成時に目安となる寸法を使うことは許容する。

部屋面積は壁の内側の床領域で求める。初期の計算基準では、床のない階段開口などを除き、ドアの敷居部分を部屋へ重複加算しない。参考畳数は内法面積を1.62 m²で割って表示し、換算基準を明記する。丸めは表示時だけ行う。

建物全体は各階の参考面積を別に算出する。初期設計では外周壁の中心線で囲む領域から床のない部分を除き、階ごとの値と合計を表示する。内法の部屋面積の単純合計とは区別する。この計算を法定床面積の判定へ広げない。

幾何計算の許容差と面積の表示桁は6.2で固定し、検査にも同じ基準を使う。特定の例を通すために期待値へ合わせて変更しない。畳換算の出典は付録Cに記す。

### 3.5 SolidCraftの形状との対応、変更・削除時の引き継ぎ

住宅情報から、対応するSolidCraftのフィーチャー・パラメータ・ボディを作成・更新する。対応表には住宅要素ID、CAD要素の識別子、面の役割を記録する。一つの壁が複数ボディになる場合も扱う。表示名を識別の唯一の手掛かりにしない。

部屋の輪郭に関わる形状変更は住宅用の操作を通す。家具などの自由な形にはCAD操作を使う。色・素材の操作は形を変えない。変更時には、残す要素、生成し直す要素、面の役割が変わる要素を求め、見た目と関係を引き継ぐ。

| 変更             | 引き継ぎのルール                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| 壁の移動・伸縮   | 部屋・面積・開口・関連する形を更新し、壁と面の見た目を維持する                                     |
| 壁の分割・統合   | 新しいボディへ素材と面の役割を引き継ぎ、開口や参照先も更新する                                     |
| 壁の削除         | 取り付いた窓・ドアを一緒に削除し、部屋の関係を更新する                                             |
| 部屋の削除・統合 | 家具は原則残す。所属を更新し、配置が成立しなければAIが調整・相談する。家具ごとの削除指示は尊重する |
| 家具・階段の変更 | 取り入れた特徴と見た目を維持し、位置・寸法・接続に必要な部分を調整する                             |

面の対応が解決できない場合は、誤った面へ色を移したり既存の指定を黙って消したりせず、編集を修復する。修復できなければ案の確定を止める。

### 3.6 案を確定するための整合性条件

| 判定               | 対象                                                                                           |
| ------------------ | ---------------------------------------------------------------------------------------------- |
| 確定を止める       | 不正な参照・数値、自己交差や意図しない部屋の重なり、住宅とCADの対応不良、2D・3D・面積の不一致  |
| 確定を止める       | 壁から外れた開口、出入口をたどれない部屋、上下階につながらない階段、階段を塞ぐ床などの接続不良 |
| 確定を止める       | 対応範囲外の形、維持すべき見た目や部品の消失、設定済みの敷地からの建物のはみ出し               |
| 説明して提示できる | 家具配置の窮屈さ、動線・使い勝手など、空間やデータの不整合には至らない懸念                     |

敷地の判定には屋根の軒などの建物の張り出しも含める。敷地未設定では検査しない。仮の敷地にも同じ条件を適用し、仮置きであることを示す。収まらなければAIが配置・寸法・階への配分を調整するか相談する。

検査結果は要素ID・理由・修正に必要な情報を返す。AIが「修正した」と述べただけでは合格にしない。形を扱う部分の幾何検査と、使い勝手についてのAIの判断を分ける。

## 4. システム設計

### 4.1 全体構成とCloudflare各サービスの役割

| 部分               | 採用する構成と役割                                                             |
| ------------------ | ------------------------------------------------------------------------------ |
| Web画面            | React・TypeScript・Vite。Workers Static Assetsから配信する                     |
| 3Dビューア         | Rust/Wasm。SolidCraftのgeom・render・gpuを利用し、表示とカメラ操作を受け持つ   |
| ログイン           | Cloudflare Access。招待したメールアドレスへの認証コード                        |
| 公開API            | WorkersのTypeScript。認証、所有権確認、入力検査、保存データの読取、処理の受付  |
| 管理データ         | D1。ユーザー、案件、パターン、会話、履歴、ジョブ、費用の記録                   |
| 大きいデータ       | R2。住宅・編集可能なCADデータ、表示データ、画像、処理途中のチェックポイント    |
| パターンの実行管理 | Durable Objects。指示の受付順、実行権の取得、停止・再開、進捗の通知を調整する  |
| ジョブの進行       | Workflows。一指示のAIとの往復、形状操作、検査、確定を段階として進める          |
| 形状処理           | Cloudflare Containers上のRustサービス。住宅操作とSolidCraftのSessionを実行する |

ブラウザはAIや形状処理サービスへ直接接続しない。Workerを入口にし、Workflowが必要な形状処理をContainerへ依頼する。カメラ操作はブラウザ内で完結する。Containersへ接続するためのDOと、パターンの進行を管理するDOは、役割と識別子を分ける。

初期構成にCloudflare Queuesは追加しない。順序と待機列を保存データで管理し、Workflowsの再開機能を使う。コンテナのメモリ・ディスクと、Workflowの保持状態を、案件の恒久保存先にはしない。

### 4.2 モジュール構成とSolidCraftの利用範囲

リポジトリのルートをinstant-madoriの開発用にし、SolidCraftは `third_party/solidcraft/` に一式を保持してgit subtreeで管理する。使わないアプリや資料も削除せず、内部の配置をできるだけ維持してupstreamの更新を取り込みやすくする。

以下を配置方針とする。環境整備で主要なworkspaceと入口を作成し、各機能の内部ディレクトリは実装時に追加する。

```text
instant-madori/
├── apps/
│   ├── web/
│   │   ├── src/
│   │   ├── public/
│   │   ├── package.json
│   │   └── vite.config.ts
│   ├── worker/
│   │   ├── src/
```

`services/` を分けるのは、Workflow・Durable Objectが同じ業務の判断をHTTPを通らずに使うためである。`services/` は書込みの文を組み立てず、`storage/` の操作（例：`renameProjectOnce`、`commitRevision`）を呼ぶ。文どうしの条件を確かめないまま、任意の文の列を一括で確定させる仕組みは作らない。D1のbatchでは条件付き更新が0件でもエラーにならず、後続の文が確定してしまうためである。`storage/` の `runOnce` はbatchの前後の確認の順番だけを受け持ち、文どうしの結び付けは操作ごとに設計する。複数の条件を含む操作は、各条件が後続の文を止めるように、その操作専用のSQLとして設計する。後続の文の条件は、行の有無や値といったデータの状態で書き、`changes()` のような接続の状態には依存しない。依存してよいのは、D1の文書が保証している次の性質だけである：batchが一つのトランザクションとして順に実行され、後の文が前の文の書込みを見ること、途中の文が失敗するとbatch全体が取り消されること、一つのデータベースが一度に一つのクエリを処理すること。冪等性の記録と変更は、この条件で結び付ける。作成は「この要求で生成した新しいIDの行がある」ことを記録の条件にする。更新は `updateOnceStatements` で記録を先に置き、一度だけ書いた前提条件を、記録と更新の両方の条件にする。

DBの行は、テーブルごとに一つのSQLの `json_object` で読み、`storage/` で共有スキーマにより検証してから返す。型引数による決めつけで行を扱わない。業務上の結果（見つからない、版の競合など）は例外でなく判別可能な結果として返し、`api/` がエラーコードへ対応付ける。予期しない例外だけを500とし、本文を含めずに記録する。

`apps/` は起動・デプロイするもの、`crates/` はRustの機能をまとめたモジュール、`packages/` はJS/TS側から共有する定義を置く。`apps/geometry` は `crates/modeling` を呼ぶ入口とし、住宅の計算やCADとの対応をHTTP処理に散らさない。

`crates/housing` は画面・HTTP・Cloudflareへ依存させない。`crates/modeling` が住宅モデルとSolidCraftのengine・doc・kernelを利用し、`crates/viewer` はgeom・render・gpuを利用する。ビューアには編集エンジンや既存のegui UIを含めず、依存を持たない `crates/display` の表示データで接続する。`crates/modeling` が符号化し、`crates/viewer` が復号する。`crates/geometry-api` は形状処理の内部APIを定義し、TypeScriptの定義を `packages/contracts/src/generated/geometry-internal.ts` へ生成する。公開する表示メディア型は同じ生成処理で `packages/contracts/src/generated/display.ts` に出し、`@madori/contracts` から公開する。Webは内部API定義をimportしない。

内部API本文は `crates/geometry-api` のRust型にschemarsを適用し、インライン化したJSON Schemaからjson-schema-to-zodでZod検証とTypeScript型を生成する。`pnpm generate:geometry` で定数と本文を一緒に更新し、RustとNodeのテストが生成結果のずれを検出する。再帰型と参照が残る型は生成時に拒否する。結果の共用体は `kind` を判別子とする。固定幅整数には範囲を付け、JavaScriptで正確に表せない64/128ビット整数は文字列で運ぶ。ポインター幅に依存する整数も生成時に拒否し、通信には固定幅の型を選ぶ。Optionは `skip_serializing_if = "Option::is_none"` でNoneを省略し、受信時は省略とnullを許す。各ルートに本文型のスキーマ生成関数を登録し、要求・応答のスロットから方向を導出する。エラー本文はルートごとに登録せず、プロトコル共通のスキーマ・メディア型・本文上限を定義し、Rustのエラー応答とWorkerの検証で使う。同名の本文を異なる契約で登録すると生成を停止する。要求はDeserialize契約で生成し、オブジェクトの未知フィールド拒否を生成時に検査する。応答はSerialize契約で生成し、共有型に指定された未知フィールド拒否を応答スキーマから再帰的に除き、追加フィールドを許容する。ルートにはHTTPメソッドと要求・応答本文の形式（なし、JSONのスキーマと本文上限、バイナリのメディア型と本文上限）を登録し、Workerの受信方針をそこから組み立てる。

住宅データはRust側で定義し、通信に必要な型とスキーマを生成してJS/TS側へ渡す。WebとWorkerの共通の通信定義も `packages/contracts` で管理し、同じ型を両側で独立に手書きしない。

ルートのREADME、AGENTS、開発設定は本サービス向けに整える。SolidCraft由来の資料と開発設定は取り込み領域に保持する。本計画書は `docs/plan.md`、検証記録と証拠は `docs/verification/` へ配置した。関連する参照リンクも移行先に合わせる。

SolidCraftには、形状操作、フィーチャー評価、編集可能な設計データ、ボディ・面の外観、表示メッシュ、基礎的な描画を担当させる。住宅の意味、案件、指示単位の履歴、WebサービスのAI実行は利用側で作る。

既存の通常の描画経路に、素材画像や日差しの影がそのまま揃っているとは扱わない。4.8の追加実装を計画に含める。既存クレートを変更する場合は、専用機能との境界を保ち、変更理由と依存する住宅機能を追えるようにする。

### 4.3 案件・会話・履歴・モデル・画像の保存構造

| D1の主な単位                | 保持する情報                                                                        |
| --------------------------- | ----------------------------------------------------------------------------------- |
| User / Project              | 認証主体との対応、内部ユーザーID、所有者、案件名                                    |
| Pattern                     | 案件ID、受付順、実行中ジョブID、待機列の保留状態                                    |
| Revision                    | パターン、履歴内の順番、編集元・復帰元、案の名前、会話の区切り、snapshotへの参照    |
| Snapshot                    | 所有者、R2のmanifestのキーとハッシュ、保存形式の版                                  |
| Message / ConversationEvent | 会話内の順番、指示・質問・回答、添付参照、関連する案・ジョブ、復帰や複製の記録      |
| Job / Operation             | 指示、状態、編集開始時の案ID、実行世代、チェックポイント参照、操作ID、結果と費用    |
| Asset / Usage               | 所有者、R2キー、用途・形式・サイズ・ハッシュ、API試行ごとの利用量・費用予約・確定額 |

パターンの現在の案は、履歴の順番が最後の案とし、パターンの行には現在の案を指す列を持たせない。2.5のとおり、復帰も新しい履歴項目を末尾へ追加するため、最後の案と現在の案は常に一致する。指す列を別に持つと、二つが食い違う状態を表せてしまう。確定の条件「編集元の案が現在の案である」は、「そのパターンの最後の案が編集元である」として、案を追加する文の中で検査する。履歴の順番は、追加する文の中で既存の最大値に1を足して決め、`(pattern_id, number)` の一意制約で重複を防ぐ。

案のmanifestには、保存形式の版、住宅データ、編集可能なSolidCraftデータ、対応表、素材・画像の参照、2D・3Dの表示データ、検査結果を結び付ける。ファイルを分ける場合も、同じ案のmanifestで内容とハッシュを固定する。manifestの版1は、6.1bの単位4の時点で存在する表示データ（`crates/display` の形式）だけを結び付ける。住宅データ・編集可能なCADデータ・対応表は6.2でmanifestの版を上げて加え、5.4のとおり読込時に旧版を移行する。R2への書込みはWorkerが行い、Containerは結果のバイト列を返すだけとする。D1のsnapshotの行はmanifestのキーとハッシュを持ち、読込時にmanifestのハッシュを、manifestが各ファイルのハッシュを照合する。

公開APIで読み書きする、所有者を持つテーブルには `owner_id` を直接持たせ、読み書きのSQLで必ず条件にする。親と所有者が食い違わないよう、親の `UNIQUE (id, owner_id)` を参照する複合外部キーで保証する。内部処理の書込みは所有者だけでは実行権を表せないため、job ID・実行世代などを必須の条件にする専用の操作として作る。

案件・パターンの `version` は、名前などの管理情報の変更だけで増やす。ジョブや現在の案の更新は別の条件で競合を判定し、名前の変更と互いに競合させない。パターンの初期名の番号は、案件の行が持つ次の番号から作成と同じトランザクションで採番し、同時に作成しても重複させない。

変更要求の結果は `requests` に、利用者・request ID・操作名・要求内容のハッシュとともに保存する。結果は記録と同じ文の中でSQLで作って保存し、初回の応答と再送への応答を同じ内容にする。保持期間は5.4の回収と合わせて決める。

確定案のR2オブジェクトは変更しない。新しい案は新しいキーで保存し、D1の履歴へ追加することで現在の案にする。復帰・複製では不変の内容を共有してよいが、新しいパターンの履歴項目と、その後の会話・ジョブは独立させる。

保存内容を識別するsnapshot IDと、履歴項目を識別するrevision IDを分ける。復帰・複製で同じ内容を再利用した場合も、表示応答には閲覧対象のrevision IDを付け、古い履歴の表示と混同しない。

パターンは複製元、起点の案、会話の上限位置を記録する。複製元に後から増えた会話が複製先へ入り込まないようにする。会話の希望と、採用・取り消し・未実行の操作を分け、AI用の要約にもその区別を残す。

### 4.4 認証とユーザーごとのアクセス制御

WorkerはAccessのJWTの署名、発行元、対象アプリ、有効期限を検査し、発行元とsubjectの組で内部ユーザーへ対応付ける。メールアドレスは表示用で、変わっても同じ内部ユーザーとして扱う。ブラウザが送ったユーザーIDを所有者として信用しない。だれがログインできるかはAccessのポリシー（招待）で決め、Worker側は初回のログインで内部ユーザーを作る。

Accessで認証済みであることと、利用者が意図した変更であることは別である。変更を伴うAPIは、設定した画面のOrigin（本番は一つ、ローカルは開発サーバーの名前ごと）のいずれかと完全に一致する要求だけを受け付け、JSONのボディに限定する。

ローカル開発とテストでは、生成した鍵で署名したトークンを同じ検査コードで検証する。ローカルの鍵は、環境名が `local` で、発行元が予約済みの `.invalid` ドメインの場合に限って受け付け、本番の設定に紛れても使えないようにする。開発時はViteのプロキシが受け取った認証ヘッダーを必ず置き換える。

案件・パターン・会話・案・添付・表示データ・進捗のすべてで所有権を確認する。R2は非公開とし、Worker経由または所有権確認後に発行する短時間のURLで配信する。ファイル名やR2キーを知っているだけでは読めない構成にする。

AIキーと内部サービスの資格情報はサーバー側に保存する。Containerは公開の編集APIとして使わず、認証済みの内部要求だけを受ける。接続用DOは起動ごとにランダムなトークンを作り、DOのストレージへ保存してContainerの環境変数へ渡す。Containerは `/healthz` 以外の内部要求でBearerトークンを検査する。DOの再起動後は保存したトークンで実行中のContainerを引き継ぎ、起動時のイメージが現在の設定と違う場合は置き換える。

### 4.5 AIに渡す情報と、呼び出せる操作

最初のモデルはClaude Opus 5.5、API IDは `claude-opus-5-5` とする。提供元ごとのAPI契約を接続層に分け、モデルを変更できるようにする。営業向けのモデル選択UIは設けない。

AIへ渡すのは、現在の案の住宅情報と要約、対象ID、関連する会話・参考画像、仮置きした条件、利用できる操作、検査結果である。長い会話は原文を保存したうえで要約・検索し、必要な情報を選ぶ。すべての画像・メッシュ・過去のCADデータを毎回送る構成にはしない。形を確認するため、現在の案や作業案の2D・3D画像を取得する読取操作も用意する。

| 操作群         | 担当する変更・取得                                                         |
| -------------- | -------------------------------------------------------------------------- |
| 住宅操作       | 階・部屋・境界・壁・開口・屋根・階段の作成、変更、削除                     |
| 家具・周辺形状 | 家具や隣家などの形づくり、位置・寸法変更。許可したSolidCraft操作を利用する |
| 外観操作       | 対象の色・素材・柄の大きさ・向きの変更                                     |
| 読取・検査     | 要素の情報、寸法、対応関係、表示画像、整合性検査                           |
| 応答           | 変更の説明、仮置きの説明、質問、残る使い勝手の懸念                         |

各操作には入力・出力スキーマを定める。住宅用の操作は、下位のCADコマンドをまとめて実行できる単位にする。家具用の自由なCAD操作で、住宅の境界や階段の接続を迂回して壊せないよう、対象の種類と操作権限を検査する。

AIは実行結果を受けて修正を続ける。確定はサービス側の検査を通した後に行う。モデル選定は間取り生成能力の実証を意味せず、実装と利用を通じて品質を改善する。

### 4.6 ジョブの進行・案の確定・停止・再試行・障害復帰

#### 受付から確定まで

1. Workerが入力と所有者を確認し、同じ要求の再送を識別するrequest IDを受け取る。
2. パターンDOが指示と受付順をD1へ記録する。実行権は一パターン一件とし、実行開始時の最新案を編集元に固定する。
3. job IDに対応するWorkflowを開始する。AIへ必要な情報を渡し、操作要求を受け取る。
4. Containerが編集元またはチェックポイントを読み、作業用のSessionで操作を実行する。住宅情報・CAD・対応表をまとめて更新する。
5. 操作結果と必要な表示データを保存し、プレビューを通知する。失敗した操作は作業用の直前状態へ戻し、AIへ理由を返す。
6. AIが編集を終えたら3.6の検査を行う。合格した住宅情報・CAD・表示データを不変のR2オブジェクトとして保存する。
7. D1の一つのトランザクションで、案と履歴を追加し（追加した案が現在の案になる）、ジョブ状態を更新する。その後に完了を通知する。

D1への確定では、実行権・編集元の案・実行世代が一致し、停止や上限到達が記録されていないことを条件にする。同じjob IDからの案の二重追加は一意制約で防ぐ。R2保存後に確定できなかったデータは未公開のままにし、参照されていないことを確認して後で回収する。

D1には公開する案とジョブ状態を保存し、DOはその条件付き更新を通して実行権を管理する。DOのメモリ内の状態だけで実行可否を決めず、再起動時はD1から復元する。長いAI・形状処理の間、DO全体をロックし続けない。

#### 状態と停止

| ジョブ状態                   | 意味                                                             |
| ---------------------------- | ---------------------------------------------------------------- |
| queued                       | 指示を受け付けた。パターンが保留中なら実行しない                 |
| running                      | 実行権を取得して編集中                                           |
| validating                   | 確定前の整合性検査中                                             |
| committing                   | 検査済みデータの保存と条件付き確定を進めている                   |
| completed                    | 案または会話応答が保存された                                     |
| awaiting_answer              | 質問を保存し、回答を待っている。実行権を解放し、待機列を保留する |
| cancelled / failed / limited | 停止・失敗・上限到達。未確定案を採用せず、待機列を保留する       |

停止はD1のジョブ状態を条件付きで変更し、確定との順序をそこで決める。停止が受理されたらWorkflowとContainerへ停止要求を伝える。Rustの計算を即座に止められない場合も、停止済み世代の結果は確定できない。

質問への回答は、質問イベントと関連付けて新しいジョブにする。保留中の通常指示より先に回答を処理し、その後の待機列の再開は利用者が選べるようにする。

#### 再試行と復帰

AI呼び出し、形状操作、保存・確定を別のWorkflowステップに分け、ステップ名と操作IDを再実行で変えない。大きな戻り値はR2へ保存し、Workflowには参照と小さな結果を返す。

操作は入力スナップショットと操作IDを固定し、完了済みなら保存した結果を返す。Containerが停止して途中のメモリを失った場合は、最後に保存したチェックポイントからやり直す。古い実行世代の結果は無効にする。

APIの応答を受け取れず再呼び出しが必要になった場合、課金を伴う外部処理まで「一回しか実行されない」とは仮定しない。試行ごとに費用を扱い、案の確定は一度に限定する。

DOの再起動、Workflow開始前後の失敗、完了通知の消失を回復できるよう、保存したジョブ状態とWorkflow IDを照合する再開処理を用意する。実行中と記録したまま永久に待つ状態を残さない。

### 4.7 APIと途中経過の配信・再接続

6.2で最初のJSONまたはバイナリ要求ルートを追加するとき、そのルートに適した本文上限を選び、axumの既定の2 MB上限を調整する。413/422拒否応答は内部APIのErrorBodyコードへ変換し、実際のルートで本文の転送を検査するテストを追加する。最初の本文ルートではハンドラーの要求・応答型をルート表に結び付け、表の `request.max_bytes` からaxumの本文上限を適用し、バイナリ要求のメディア型も検証する。

以下を初期の公開APIとする。変更要求はrequest IDを持ち、同じIDと内容の再送は同じ結果へ対応付ける。復帰や管理情報の変更では期待する版を送り、意図しない上書きを防ぐ。

request IDは利用者ごとの範囲で一意とし、固定するのは成功した結果だけとする。失敗した要求は記録せず、同じIDで内容を直した再試行を新しい要求として扱う。一度成功したIDを別の操作・内容に使った場合は拒否する。同じ要求の同時の再送では、先に確定した結果を全員に返す。

表示データ以外の応答はJSONで、失敗は共有定義のエラーコードを `{ error }` で返す。利用者ごとのデータを返すため、API応答はすべてキャッシュさせない。応答と構造化ログに追跡用のIDを付け、ログには会話・名前などの本文を出さない。案件の一覧は作成日時の新しい順に、案の一覧は履歴の番号の降順に、続きを取得するためのカーソルを付けて返す。パターンの一覧は番号の昇順に、ページに分けずに返す。

| API                                         | 役割                                                                    |
| ------------------------------------------- | ----------------------------------------------------------------------- |
| GET /api/me                                 | 内部ユーザーと利用可能な設定                                            |
| GET・POST /api/projects                     | 案件一覧・作成                                                          |
| PATCH /api/projects/:id                     | 案件名などの管理情報                                                    |
| GET・POST /api/projects/:id/patterns        | パターン一覧・作成                                                      |
| PATCH /api/patterns/:id                     | パターン名などの管理情報                                                |
| GET /api/patterns/:id/state                 | 現在の案、会話・履歴の位置、ジョブ、待機・保留状態                      |
| GET /api/patterns/:id/messages・revisions   | 会話と履歴のページ取得                                                  |
| POST /api/patterns/:id/messages             | 指示・質問への回答を受け付ける                                          |
| POST /api/patterns/:id/restore・clone       | 確定案からの復帰・複製                                                  |
| POST /api/jobs/:id/stop                     | 実行中の処理の停止                                                      |
| POST /api/patterns/:id/queue/resume・cancel | 保留指示の再開・取り消し                                                |
| POST /api/assets                            | 添付画像の登録・検査                                                    |
| GET /api/sample/display                     | サンプルの3D表示データ。一時的なAPIで、案を作る経路ができたら削除       |
| GET /api/revisions/:id/view                 | 2D・3D表示データと取得先。6.1bの単位4では3Dの表示データのバイト列を返す |
| POST /api/revisions/:id/pick・sunlight      | 対象選択の確定と日差しの計算                                            |
| GET /api/patterns/:id/events                | 途中経過と状態変更をSSEで配信                                           |

SSEのイベントにはパターン、job ID、案IDまたは作業版、増加するイベント番号を付ける。画像・メッシュの本体は含めず、取得先を通知する。操作中にパターンや条件を変えた場合、遅れて届いた別の版の結果を表示しない。

再接続時はイベント番号から差分を読み、保存範囲を外れていたらstateと現在の表示データを再取得する。SSEの接続をジョブの生存条件にしない。通信できない間の入力は送信済みとせず、再送時にもrequest IDを保持する。

Containerの内部APIは、スナップショットの読込、操作バッチ、検査、保存、停止、表示データ取得に分ける。内部APIは `/v1` のパスで版を識別し、`/healthz` もプロトコルの版を返す。DOは自分の扱える版だけを受け付ける。ジョブを扱う要求にはjob ID、操作ID、実行世代、入力スナップショットを必須にし、Sessionを共有して同時変更しない。固定サンプルの `GET /v1/sample/display` はジョブの識別子を持たず、要求ごとのSessionで評価する。起動・接続失敗は公開APIの503 `service_unavailable` と `retry-after` に対応付け、形状生成の失敗と内部プロトコル違反は500にする。

### 4.8 2D生成・3D描画・素材表示・日差しの計算

2Dは住宅の輪郭・開口・階段情報と、家具の投影から生成する。部屋名・面積・方位・寸法を同じ案に結び付ける。SVGを表示とPNG出力の共通の入力にする初期設計とする。

3Dはサーバーで評価した形状から表示メッシュを作り、住宅要素IDとの対応、色、素材を付けてWasmへ渡す。モデルの判断は住宅情報とCADの形状に基づき、表示メッシュの変更を住宅編集として保存しない。対象選択はブラウザで候補を求め、サーバーがその案の形状と対応表で確定する。

表示形式は `crates/display` で管理する。版1は `MDSP` ヘッダー、全体の長さ、8バイト境界にそろえたセクション表を持つ。ボディごとのf32メッシュ、三角形のB-rep面番号、RGBA色、閉じたボディかどうか、面のRGB色、住宅要素IDを格納する。WorkerとWebはバイト列を解釈せずに渡し、Wasmの復号時に検証する。内部APIは16 MiBを上限にする。

版1の必須セクションは ELEM、BODY、POSN、NORM、TRIS、TFAC、FCOL の順に固定する。その後に任意セクションを表の順で追加し、任意セクションのフラグは0とする。各セクションの前には8バイト境界にそろえる最小限のゼロ埋めだけを置き、最後のセクションの後に余分なバイトを置かない。既知の任意セクションがない場合は、その情報の既定値を使う。

新しい情報はセクションとして追加する。旧ビューアが無視できる追加は任意とし、必須の未知セクションは読込を拒否する。任意セクションは旧読込側も保持し、受理したバイト列は再符号化しても一致する。既存セクションの意味を変える場合は形式の版を上げる。R2に保存したオブジェクトは書き換えず、ビューアに保存済みの各版の読込処理を残す。

素材は、画像の読み込み、面への座標の割り当て、柄の実寸・向き、表示用キャッシュを追加する。通常のSolidCraftビューアの色指定だけでは木目やタイルの表示は完成しない。6.4で、壁の移動・分割・伸縮後にも柄と適用面が保たれることを確認する。

日差しは、地域・日時・方位から太陽方向を求め、開口、壁、家具、屋根、隣家による遮蔽を計算して3Dへ表示する。初期実装は検証で用いた太陽方向と幾何遮蔽の考え方を編集可能な案へ広げ、床を含む室内で光が届く場所を示す。表示用に隠した屋根も遮蔽に含める。ガラスは初期計算では光を通すものとする。

日差しの結果は案IDと日時・地域・方位の条件で識別・キャッシュする。計算中に条件が変わったら古い結果を採用しない。精度と処理時間、壁・天井への表示方法は6.5で実装中に確認し、粗い計算が細い日差しを消してしまう問題を検査する。床のサンプリングによる既存の検証結果は、任意の住宅での精度や通常の影描画の完成を保証しない。

## 5. 運用と保守

### 5.1 開発環境と本番へのデプロイ

ルートに自作RustコードのCargo workspaceとJS/TSコードのpnpm workspaceを置く。Rust側は `apps/geometry` と自作の `crates/`、JS/TS側は `apps/web`・`apps/worker`・`packages/contracts` を対象にする。SolidCraft側のCargo workspaceは別に保持し、自作側から必要なクレートをpath依存で利用する。

SolidCraft一式を保持することと、通常のビルド・テスト対象に全アプリを含めることは分ける。自作workspaceへ取り込み領域の全クレートが自動参加しないよう設定し、サービス側のビルドでは必要な依存先だけを使う。

開発ツールの版を固定し、検査はローカルの `pnpm check` にまとめる。先にPrettier・rustfmt・ESLint・Clippyで自動修正できるものを直し、型付きlint・型確認・未使用検査・秘密情報・テストを実行する。RustはnativeとWasmを検査する。作業中の `--fast` はテスト実行とアプリのビルドを省き、`--full` はWasmの再生成、全ビルド、接続確認、JS/Rustのライセンス・取得元・脆弱性監査まで行う。初回以外はビルドキャッシュを再利用し、各工程の時間を表示する。GitHub Actionsには依存しない。コミット前フックはステージ対象ファイルの整形・lintとステージ済み差分の秘密情報を検査し、作業ツリーやステージ内容を書き換えない。具体的なコマンドと検査範囲は[README](../README.md)にまとめる。

サービスの依存解決はルートのCargo.lockとpnpm-lock.yamlで固定する。Cargoのプロファイル・依存パッチは利用側ルートで必要な設定を管理し、SolidCraft側の設定が自動で引き継がれるとは仮定しない。相対パスで参照する資産、ビルドスクリプト、評価キャッシュの識別処理も移行時に確認する。キャッシュを利用する場合は、識別値に実際の依存解決とビルド条件を反映する。環境整備では誤った再利用を避けるため、サービスから使うSolidCraftの評価キャッシュを無効にする。

開発では `pnpm dev` がWeb画面、Worker・D1、Wasmと、`wrangler dev` 経由のDocker Containerを接続する。画面だけを扱うときは `MADORI_DEV_CONTAINERS=0` でContainerを無効にする。`pnpm check --full` はDockerイメージをビルドし、実Containerとの接続も検査する。Dockerはビルドプラットフォーム上のRustからLinux amd64向けにコンパイルし、Cargoのキャッシュを再利用する。テスト用と本番用の認証設定・DB・R2・秘密情報は分離する。

本番はWorkerと静的ファイル、D1マイグレーション、R2、DO・Workflow、Containerイメージを一組の版としてデプロイする。RustはContainerの対象であるLinux向けにビルドし、Wasmは別の成果物として作る。形状処理のメモリと起動時間を測り、Containerのサイズ・同時実行数・休止条件を選ぶ。

stagingはworkers.devのホスト名で公開し、Worker宛先のAccessアプリで守る（preview URLは無効）。手順の順序はREADMEに従う。Accessアプリとstaging用のD1を作成し、`apps/worker/wrangler.jsonc` の `env.staging` にDB ID、Accessの発行元とaudience、画面のOriginを設定する。初期値の `.invalid` 発行元はローカル以外で拒否する。インスタンスの種類と休止時間は環境別の変数で指定し、stagingでの計測（[検証3](verification/verification-03.md)）に基づいて決める。Workers Logsを有効にし、Container内の標準出力もそこへ集める。stagingのCloudflareリソースの作成、デプロイ、D1のマイグレーションは、AGENTS.mdのとおり、ユーザーが明示して許可した場合に限りエージェントが行う。接続用DOが出す `container.ready` ログの `mode: cold` で起動時間、Rustの要求ログの `vmHwmKib` でLinux上のメモリ最大値を読む。

起動確認が終わってから処理を渡す。長い処理ではコンテナの生存時間を明示的に管理する。ブラウザ、Workflow、ContainerのHTTP接続が切れたことだけを、ジョブの完了や取消の証拠にしない。

### 5.2 AI費用・処理時間・利用量の上限

| 設定               | 初期値と扱い                                                 |
| ------------------ | ------------------------------------------------------------ |
| AI費用の月額       | サービス全体で100米ドル。初期設計ではUTCの暦月で集計する     |
| 一指示のAI費用     | 5米ドル。再試行と修正のための呼び出しも含む                  |
| 一指示の処理時間   | 実行開始から10分。受付後の待機時間は含めない                 |
| 同じパターンの編集 | 同時に一件                                                   |
| Cloudflare利用料   | AI予算とは別に計測・監視する。月額の実測前に定額を約束しない |

これらは運営が変更できる初期の歯止めであり、費用・速度の目標値ではない。月額の残額が不足すれば新しいAI処理を受け付けず、実行中の指示が上限に達したら未確定案を採用せず終了する。元の指示と理由は会話に残す。

各API試行の前に、入力、画像、最大出力、モデルの料金から費用を見積もり、月額とジョブ双方の残額を条件付きで予約する。応答後に利用量で精算する。使用量が取得できない試行は予約額を解放せず保守的に計上し、後から照合する。既に開始した外部呼び出しまで厳密に即時停止できるとは扱わない。

添付の形式・ファイルサイズ・画素数、操作数、形状の規模、APIの頻度にもサーバー側の上限を設ける。数値は6.1と6.2で資源消費を確認して設定ファイルへまとめる。モデルやプロンプトに対する変更で、上限検査を迂回できないようにする。

### 5.3 ログ・性能・費用の計測

request ID、job ID、操作ID、案IDを通して処理を追えるようにする。AI待ち、形状計算、検査、保存、転送、描画、初回プレビューまでの時間、Containerのメモリ、API利用量・費用を分けて記録する。

WorkerとContainerの要求ログは、503を含む5xxをerror、それ以外をinfoとする。エラーログには段階と原因を残し、会話・画像・CADデータの本文や秘密情報を無条件に出力しない。必要な調査では、権限のある保存データを参照する。

利用時の確認は、希望の反映、空間の整合性、変更の引き継ぎ、質問の有用さ、待ち時間を分けて記録する。どれを改善すればよいか判断できる粒度を保つ。

### 5.4 データの保護・復旧・形式変更

D1の復旧手段を用意し、復旧時点の履歴が参照するR2の不変オブジェクトを揃えて戻せるようにする。DBだけを戻して案の実体が欠ける復旧を避ける。初回提供前に、別環境への復元と保存済みの案の再編集を確認する。

未確定の作業データ、未参照のアップロード、期限切れプレビューを回収対象にする。確定案や複製元から参照される画像・形状・会話は、利用中の参照を確認せず削除しない。復旧用の保持範囲も回収判定に含める。

画像と会話は、必要な範囲を選んでAIの商用APIへ送る。利用するAPIのデータ利用・保持条件を運営で確認し、利用者が確認できる場所に説明する。AIを呼ぶ資格情報やモデルの変更はサーバー設定で管理する。

保存形式には版を付け、読込時の移行処理を用意する。旧形式の案を直接上書きせず、移行結果を確認したうえで新しい内容を保存する。

### 5.5 AIモデル・SolidCraft・依存ライブラリの更新方針

SolidCraftの初回取り込みは `https://github.com/tangency-labs/solidcraft` のコミット `9325e3ac8cc1dcad67bc5d218274e89e8a9b26fc` を基準とし、`third_party/solidcraft/` をgit subtreeとして管理する。既存のGit履歴を保持し、初回取り込みとupstreamの対応を記録して、次回以降もsubtreeとして更新できる状態にする。現在の採用版は[取り込み記録](../third_party/solidcraft.json)に記録する。

住宅固有の機能は取り込み領域の外に置く。SolidCraft自体に必要な変更は、その内部の配置や名称をできるだけ保ち、サービス側の変更とはコミットを分ける。取り込み元・採用コミット・独自変更の理由と更新手順を `third_party/solidcraft.md` に記録する。

更新時は採用するupstreamのコミットを選び、専用の作業ブランチでsubtreeへ取り込む。独自変更と同じ箇所が変われば競合を解消し、ビルドと住宅機能への影響を確認して採用する。ルートへ通常のupstreamマージを行う手順とは区別する。upstreamの更新は原則取り込む。住宅サービスの機能・構成・動作環境に問題が出る場合は調整するか、理由と再検討条件を記録して保留する。有用な改善を継続して取り込める状態を維持する。

モデル・プロンプト・操作スキーマ・住宅データ・描画の版も記録する。

更新時は、保存済みの案の読込・再編集、形と面の対応、素材の引き継ぎ、2D・3D・面積、ジョブの復帰を確認する。AIの変更では同じ相談例で生成・編集を見比べる。品質向上の作業を、本体実装開始の条件へ戻さない。

## 6. 実装順と各段階の完了条件

表示データの応答には、閲覧対象の案IDを `x-revision-id` ヘッダーで付ける。案の一覧は履歴番号の降順に50件ずつ返し、続きのカーソルには最後の番号を符号化する。履歴の順序を確定する番号を使うため、作成時刻が同じ場合や実行元の時計が前後した場合も、現在の案と一覧の先頭は一致する。

ローカルの保存テストでは、HTTPテスト用Workerを一時停止し、同じ永続化先を指定したWranglerの `getPlatformProxy` で実際のD1・R2に対してサービスを実行する。proxyを終了してからWorkerを再開し、保存済みの内容を公開APIから読む。同じSQLiteファイルを二つのworkerdが同時に開かないようにする。Workerの型とNodeの型の衝突を避けるため、サービスを呼ぶfixtureは既存の `tests/rpc` の型検査対象に置き、Node側のHTTPテストから子プロセスとして実行する。

- Cloudflare上の起動時間とメモリは、ローカルの検査からは確かめられない。ローカルの値はamd64のエミュレーション上の値なので、資源設定の根拠にしない。単位3で測る。

**stagingでの計測（単位3）の結果**

手順と数値は[検証3](verification/verification-03.md)に記録した。stagingは `instant-madori-staging.firpmnfiywl.workers.dev` で、Worker宛先のAccessアプリで守る。

- Container上のSolidCraftは、standard-1（仕様は1/2 vCPU、4 GiB）の範囲で動いた。メモリの上限が設定どおりに適用されていることを、Container内のcgroupの値で確かめた。サンプルのメモリの最大値は約46 MiB、温まった後のContainer内の処理は中央値29 msだった。コールドスタートは5回が339〜377 msで、イメージを変えた後の最初の起動だけが8,078 msと38,247 msだった。4.1の構成は変えない。
- `GEOMETRY_INSTANCE_TYPE` はstandard-1のままにする。liteも設定どおり適用されたが、サンプルの処理が約30 msと短く、処理時間に差が出なかった。6.2で住宅一軒分の形状処理を測って決め直す。
- `routeTimeouts`（health 2秒、sampleDisplay 30秒）は変えない。readinessの期限（60秒）も変えない。新しいイメージの最初の起動（38.2秒）まで余裕は約22秒なので、6.2でイメージを小さくする方法を検討する。期限を延ばすと、本当に起動できないときに利用者が失敗を知るまでの待ち時間が延びる。
- `GEOMETRY_IDLE_TIMEOUT_MS` は10分のままにする。再デプロイを挟まなかった各1回では、休止時間を10分にしても60秒にしても、Containerは起動から約16分で止まった。接続用DOが待ち続ける `container.monitor()` がDOの退去を最長15分防ぐことが原因と推測しているが、10分の回の停止時刻はCloudflareの文書の説明だけでは説明できない。DOがメモリから退去した時刻がログに出ないため、原因は確かめられない。確かめるには、退去の時刻を記録し、休止時間を15分より長くした回と比べる。休止時間どおりに止める方法は、上の単位5の注記のとおりDOのアラームで止める方式に決めた。実装は単位5で行う。
- 同時に動かすContainerの上限は、複数のDOがContainerを使う経路ができる単位5で決める。

## 付録C. 面積表示の参照先

[不動産の表示に関する公正競争規約施行規則、第9条第16号](https://www.rftc.jp/webkanri/kanri/wp-content/uploads/2025/08/20250826_kiyakushuu.pdf#page=17)では、居室等の畳数表示に対し、壁心面積を表示畳数で割った値を1.62 m²以上とする基準がある。

本サービスは内法面積を1.62 m²で割った参考値を表示する。この換算値の参照だけをもって、広告表示規則への適合を保証するものではない。
