# instant-madori の検証マップ

利用者から見える機能ごとに、確かめ方をまとめた一覧。アプリを動かす前にこの索引を読み、当てはまる機能のファイルを手順として使う。準備、起動、状態確認、片付けは [../SKILL.md](../SKILL.md) にある。

## 前提

- SKILL.md の手順で、自分の worktree から `pnpm dev` を起動している。
- 状態確認で、`/api/health` と `/api/me` が期待どおりに応答している。
- 画面を確かめるときは、SKILL.md の起動の二つ目の確認（Container まで届くこと）が通っている。
- 既定の利用者は `dev@example.com` で、subject は `local:dev@example.com`。

## 操作の決まり

- 画面は T3 のプレビューで操作する。要素は ARIA の役割と名前で指し、座標やタブ順に頼らない。
- API は `http://127.0.0.1:5173/api` へ送る。認証の拒否を確かめるときだけ、8787 番へ直接送る。
- GET 以外の要求には `-H "$O"` を付ける。`O='origin: http://127.0.0.1:5173'` と `J='content-type: application/json'` を先に設定しておく。
- コマンドは書いてあるとおりに使う。名前やフラグを変えない。
- 書き込みを伴う手順では、毎回新しい `requestId` を使う。再送を確かめる手順だけ、同じ値を使い回す。

## 証拠と未確認の報告

- 証拠のファイルは `$EVIDENCE/<機能>/` に置き、手順の名前をファイル名に入れる。
- 画面の証拠は、操作の前後のスクリーンショットと、そのときの `[role="status"]` と `[role="alert"]` の中身。
- API の証拠は、状態コードと応答本文。書き込みには、別の読み出しの結果も添える。
- 前提が欠けて通れなかった手順は、試したコマンドと欠けていた前提を報告する。別の入口で確かめたものを、その入口で確かめたと書かない。

## 機能ファイルの形

各ファイルは、H1 の題と、利用者から見える振る舞いを書いた一段落で始める。続けて、次の四つの H2 をこの順に置く。

1. `Sub-features`：短い ID と、一行の説明。
2. `How to get to it (user POV)`：利用者の入口をすべて。
3. `Driving it with <harness>`：`Preconditions:` から始め、操作ごとにコマンドと見える結果を組にする。
4. `Gotchas`：確認を無駄にしたり、結果を無効にしたりする落とし穴。

実装の詳細は書かない。利用者の経路、安定した手がかり、必要な状態、コマンド、見える証拠だけを書く。

## 機能

- [サンプルの住宅モデルを見る](./sample-view.md)：指示の送信と案の描画、再読込、回転、拡大・縮小、失敗と停止の表示。
- [本人確認](./sign-in.md)：ローカルの Access、認証の拒否、未知の経路、別の利用者。
- [案件](./projects.md)：作成、再送、一覧、名前の変更、版の競合。
- [パターン](./patterns.md)：一覧、作成、名前の変更、状態の読み出し。
- [指示を送る](./instructions.md)：受付、再送、仕事の実行と案の確定、案の表示データ、案の一覧。
- [指示を止める](./stop.md)：待機中と実行中の停止、確定の後の停止、再送、存在しない仕事。
- [待機列の保留](./queue-hold.md)：停止と失敗の後の保留、再開、取り消し、再送、古い保留への操作、保留にならない場合。
