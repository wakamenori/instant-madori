# 指揮役として計画を進める

pstack の poteto-mode の Orchestrate に従い、各 PR は Autopilot-full の形で進める。このファイルには、このリポジトリと T3 で違うところだけを書く。担当の手順は [madori-owner](../madori-owner/SKILL.md)、アプリの確かめ方は [verify-madori](../verify-madori/SKILL.md) にある。

ユーザーへの報告と、Issue と PR のコメントは、見回りと通知のターンでも日本語で書く。ユーザーに判断を求めるときは一件ずつ聞き、何が変わるか、得るもの、失うもの、元に戻せるかを書く。

引数が「見回り」なら、「見回り」の節だけを行う。

## pstack と違うところ

- 指揮役は、メインのチェックアウトで動く Claude Code の T3 スレッド一つ。コードも PR も作らない。
- プログラムの状態は GitHub に置き、milestone、Issue、PR から読み直す。Orchestrate の `notes.md` と store は作らない。show-me-your-work の判断の記録は、Issue と PR のコメントに書く。
- 担当は T3 のスレッドとして、検証役は指揮役のスレッドの子として立てる。cloud VM の代わりに、このマシンの worktree を使う。
- 同時に動かす担当は五人まで。担当はこのマシンで、CPU とメモリ、ディスクを共有するため。その内側の枠は「次の Issue を選ぶ」にある。Rust の `target` は worktree ごとに持つので、担当と検証役は同時に cargo を使ってよい。
- 検証は、head ごとに検証役一人で行う。Autopilot-full の swarm にはしない。
- マージするかは指揮役が決める。コマンドも指揮役が打ってよい。
- シェルの手順は、[scripts/](scripts/) のスクリプトを、各節に書いたコマンドで呼ぶ。着手する Issue の順も [scripts/rank-ready.mjs](scripts/rank-ready.mjs) で出す。依存の鎖の長さは手で数えられないため。番号や SHA を書き込んだコマンドを一つずつ打ち、変数、ループ、ファイルへのリダイレクトで手順を組み立てない。Bash ツールの zsh は、`noclobber` で既存のファイルへの `>` を拒み、引用符の無い変数を単語に分けないので、組み立てた手順は黙って失敗する。新しい手順が要るときは、スキルにシェルを書かずに、テスト（`*.test.mjs`。`pnpm check` が実行する）と一緒にスクリプトを `scripts/` に足す。その場で書いたスクリプトとポーリングのループは使わない。
- Autopilot-full の `/loop 1h` は、T3 の定期タスクに置き換える。プロンプトは `/madori-coordinator 見回り` の一行だけにする。

## 始めるとき

指揮役のセッションを新しく始めたら、まずメインのチェックアウトを `git pull --ff-only` で main に合わせる。このスキルとスクリプトは、そこから読み込まれる。続けて、`node .claude/skills/madori-coordinator/scripts/poteto-mode.mjs` が出す poteto-mode の `SKILL.md` を全部読む。検証役への指示に入れるのも、このパスである。引き継ぎのメモは探さずに、状態を次から読み直す。

- 開いている PR と、それぞれの head と `check`（`gh pr list --state open`、`gh pr checks <番号>`）
- T3 のスレッドの一覧（`t3_thread_list`）。担当のスレッドの題は `#<番号> <Issue の題>` にしてある
- 定期タスク（`list_scheduled_tasks`）。指揮役のスレッドが変わったら、見回りの紐付けを新しいスレッドへ移す
- 直近のデプロイ（`gh run list --workflow deploy-staging.yml --limit 5`）

## 計画を Issue に分ける

- 段階の milestone は plan.md 6章の段階に一つずつ作る。名前に節の番号を付けない（例：サービス基盤）。milestone の番号は、6章の節と同じ順にする。このほかに、常設の milestone「開発基盤」「期限なし」「初回提供の後」がある。
- 計画にある作業は、着手する前にすべて Issue にする。plan.md にだけ書かれた作業を残さない。
- Issue は一つの PR で終わる作業にし、[種類別のテンプレート](../../../.github/ISSUE_TEMPLATE/)の欄をすべて埋める。milestone は「Issue の置き場」で決める。
- 住宅相談サービスの利用者の画面と経路（`apps/web`、`apps/worker` と、その奥の形状 Container。ローカルと staging の両方）の振る舞いを変える Issue は、「触ってよいパス」に verify-madori の `features/` を入れる。担当は同じ PR で地図を直すため（madori-owner「確かめる」）。「触ってよいパス」に `apps/web/` か `apps/worker/src/` の下があり `.claude/skills/verify-madori/features/` の下が無いと、「下書きから Issue を作る」の `records.mjs` の `draft` と `issue` が理由を出して止まる。作りの見直しやテストだけの変更など、利用者から見た振る舞いを変えないので地図を入れないときは、「範囲」に `- 地図を変えない理由：<理由>` の一行を足す。開発の仕組みの画面（計測の viewer など）だけを変える Issue には地図を入れず、終わった証拠に、振る舞いを確かめる入口（生成コマンドとブラウザなど）を書く。担当と検証役は、その入口で確かめる。

### 種類とラベル

種類は作業の目的で決める。次の問いに順に答え、該当するテンプレートの `labels` にある長いラベルを一つ付ける。種類はラベルで記録する。不具合と作りの見直しでは、本文先頭の yaml に `found_at`、`found_by`、`cause` を書く。作りの見直しでは `plan_change` も書く。開発の仕組みの改善では `target` を書く。機能、外の変化への追従、確かめと判断は「目的」から書き始める。

1. 変える理由が外から来たか。依存、脆弱性、外のサービスや道具の変化に合わせるなら「外の変化への追従」。
2. 成果が分かったことや決めたことか。試作、計測、確かめ、受け入れ、計画づくりなら「確かめと判断」。そのためにスクリプトを作る場合も含む。
3. 変えるのは製品か、開発の仕組みか。製品には利用者が使うコード、データ、素材と、その約束を定めた計画が入る。開発の仕組みには担当・検証役の手順、検査、CI、デプロイ、ログ、集計、本番環境など、作る・確かめる・届ける・動かす仕組みが入る。
4. 変える前に約束どおり動いていたか。plan.md、Issue の終わった証拠、AGENTS.md と README の決まり、公開 API の仕様、これまでの振る舞いと、実際の動作を比べる。

| 変える理由                                                             | 製品               | 開発の仕組み               |
| ---------------------------------------------------------------------- | ------------------ | -------------------------- |
| 約束どおりに動かなかった                                               | 製品の不具合       | 開発の仕組みの不具合       |
| 約束どおりで、できることを増やす、速くする、まだ起きていない事故を防ぐ | 機能               | 開発の仕組みの改善         |
| 約束どおりで、できることも出来の良さも保って作りを変える               | 製品の作りの見直し | 開発の仕組みの作りの見直し |

作業中に種類が変わったら、ラベルを付け替え、必要な項目が変わったら本文先頭の yaml をそろえる。移行時に開いている開発の仕組みの改善は、担当を立てる前に狙いを yaml の `target` に書く。計測には閉じた時点のラベルを使う。製品か開発の仕組みかもその種類で決め、PR の変更ファイルとの食い違いは計測の信頼性に出す。種類がなかった過去の Issue だけは、同じ問いで一度分類し、後から付けた記録として扱う。「スループット」は急ぎの印である。計測の Issue と PR には別に `metrics` を付ける。

### 下書きから Issue を作る

段階を Issue に分けるときは、次の順に進める。

1. 下書きを `.issues/<id>.md` に書く。このフォルダーは Git で追跡しない。本文はテンプレートの「目的」から後の見出しと欄を使う。テンプレートを選ぶための `type`（ラベルの「：」の前の名前）と、その種類に必要な yaml の各項目は下書きのフロントマターに書く。そのほかに `id`、`title`、`milestone`、`blockedBy` を書く。`blockedBy` には、先に閉じる必要がある下書きの `id` か、既存の Issue の `#<番号>` をカンマ区切りで書く。`#` を含む値は引用符で囲む。YAML では、値の先頭か空白の直後にある、引用符の外の `#` から後ろがコメントになる。依存の欄では、番号のない下書きを `#<id>` で指し、`blockedBy` と同じものだけを並べる。
2. 下書きを書いたのとは別のエージェントに、下書きを plan.md とコードに照らして確かめさせる。見るのは、計画の抜けと重複、下書き同士の食い違い、終わった証拠を実行できるか、依存の向き、人の判断が要る項目。plan.md がコードや決めたことと食い違っていれば、正しい内容を決めて下書きをそれに合わせ、plan.md を直す Issue も作る。指摘を直してから次へ進む。
3. 依存の先から順に、下書きの依存の欄の `#<id>` を実際の番号に置き換える。下のコマンドで本文を作り、検査が通った本文を使って Issue を作る。下書きから作る場合も種類のラベルを付ける。作った Issue ごとに、`blockedBy` の番号を「依存を登録する」のとおりに登録する。依存の欄には番号がもうあるので、`--reason` は要らない。作った後は Issue を正とし、下書きを消す。

```sh
node .claude/skills/madori-coordinator/scripts/records.mjs draft .issues/<id>.md > <本文ファイル>
node .claude/skills/madori-coordinator/scripts/records.mjs issue <本文ファイル> <種類のラベル>
```

製品と開発の仕組みのどちらも、不具合と作りの見直しでは、最初に見つけた人や役割を `found_by` に書く。`found_at` は原因になった作業のマージを基準に「マージの前の検証」「マージの後」から選ぶ。別の担当がマージ済みの問題に作業中に気づいた場合も「マージの後」である。`cause` は `"#123"`、`"PR #123"`、「外の変化」「もとからあった」「不明」から選び、本文に根拠を書く。作りの見直しでは、計画の変更によるものかを `plan_change` に「はい」「いいえ」で書く。

開発の仕組みの改善では、測れる項目の一覧から狙いを選び、その識別子を `target` に書く。一覧にないときは、自動で取れる記録を探す。測れるなら、急ぎでも先に計測の Issue を作り、改善をそれに依存させる。計測の終わった証拠には、記録が取り込まれ、狙いの値を読めることを入れる。計測にも通常どおり担当を立てる。自動で測る手段がないときだけ、成功の条件を `target` に書いて改善を進める。

依存には、先に閉じる必要がある Issue のほかに、次も入れる。下書きでも、作った後の Issue でも同じにする。

- 同じファイルを触る Issue。先に進める方を依存の先にする。`README.md` と `docs/plan.md` は、同じ節を触るときだけ同じファイルと数える。ディレクトリで書いたパスは、その下のファイルをすべて触るものと数える。
- 調べた結果が別の Issue の設計の前提になるとき、調べる Issue。

### 依存を登録する

Issue の依存は、GitHub の依存関係（blocked by）と本文の依存の欄の両方に置く。どの場面でも、次のコマンドで登録する。

```sh
node .claude/skills/madori-coordinator/scripts/blocked-by.mjs <番号> <依存の先の番号>... --reason '<理由>'
```

- GitHub に無い依存の先を登録し、依存の欄に無い依存の先を `- #<依存の先>。<理由>` の一行で足す。欄が「なし」なら、その行に置き換える。欄に全部あれば、`--reason` は省いてよい。
- 0で終わったら、GitHub と依存の欄を読み直して、両方にあることを確かめてある。0以外なら、表示された理由を直して打ち直す。打ち直すと、足りない分だけを書く。
- 番号に `#` を付けず、理由は一重引用符で囲む。zsh は、`#` で始まる語から後ろをコメントとして捨て、二重引用符の中のバッククォートをコマンドとして実行する。

## Issue の置き場

Issue の milestone は期限で決める。担当や検証役が範囲の外で見つけた問題も同じにするが、先に表の下の、範囲の外の後続の決まりを当てる。段階の milestone に置くのは、その段階の完了条件を塞ぐものと、その前提になる作業だけにする。表を上から読み、最初に当たる行に置く。

| 期限                                                                                                     | 置き場                               |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 今すぐ（担当と検証役の待ち時間、事故、やり直しを減らす。検査・デプロイ・データを壊すものを含む）         | 「開発基盤」、ラベル「スループット」 |
| 今の段階の完了まで（今の段階の完了条件か、その前提を塞ぐ）                                               | 今の段階                             |
| 後の段階の完了まで（その段階の完了条件か、その前提を塞ぐ）                                               | その段階                             |
| どの段階の完了条件も塞がない開発の仕組み（CI、デプロイ、検査の道具、開発環境、進め方、テストや検査の穴） | 「開発基盤」                         |
| どの段階の完了条件も塞がない製品の作業（初回提供の範囲の外の機能や改善）                                 | 「初回提供の後」                     |
| 期限なし                                                                                                 | 「期限なし」                         |

- 段階の Issue を依存で塞ぐ Issue は、「期限なし」と「初回提供の後」に置かない。置くと、どちらも自動では選ばないので、段階が止まる。rank-ready は、そうした Issue を「置き場を直す」に出す（「次の Issue を選ぶ」）。
- 「壊す」は、実際に起きたものか、今の段階の作業で起きる経路があるものに限る。
- テストや検査の穴は、守っているコードを段階の Issue が変えるなら、その Issue の依存にする。置き場は「開発基盤」のままにする。
- 計画との食い違いは、その記述を後の段階で決め直すなら、その段階に入れる。
- 利用者にだけ当たる後退（性能や型の甘さ）は、利用者を招く段階に入れる。
- 今の段階の別の Issue と同じコードを変えるだけでは、今の段階に入れない。置き場は表で決める。

範囲の外の後続は、表を読む前に次の順に読み、最初に当たる決まりで置く。

1. 次のどれかに当たる後続は、表で決める。2と3で「期限なし」にしない。
   - 実際に起きた事故
   - 今の段階の作業で起きる経路があるもの
   - 段階の Issue が依存するもの（テストや検査の穴で守るコードを段階の Issue が変えるものを含む）
2. 次のどちらかだけを理由にする後続は、「期限なし」に置く。ほかの作業が同じ振る舞いについての文書の訂正だけなら、それも含める。文書のずれは振る舞いを変えず、穴を埋めるときに合わせて直せる。
   - 実データで起きていない端の場合。今のコードと入力に無い形でだけ起きるもの。
   - 生き残った変異だけを理由にしたテストや検査の穴。今の振る舞いは正しいもの。
3. 表で「スループット」の無い「開発基盤」になる後続が、「期限なし」の Issue に塞がれるなら、「期限なし」に置く。

「期限なし」と「初回提供の後」の Issue、およびラベル「スループット」が無く段階も塞がない「開発基盤」の Issue は、記録として開いたまま残し、自動では選ばない（「自動着手の対象」）。持ち主が名指ししたときだけ担当を立てる。

「期限なし」の Issue は、さらに次のとおりに扱う。

- 期限が無い理由を、Issue に一行書く。
- 段階の milestone を閉じるたびに見直し、期限ができたものを、この節の表のとおりに移す。見直したことを Issue にコメントで書く。期限ができなければ、閉じずに残す。

## 次の Issue を選ぶ

着手できる Issue のうち、自動着手の対象だけを、段階と「開発基盤」の組に分けて出す。段階の組は milestone の番号の順に、各組の中ではラベル「スループット」、後ろに続く依存の鎖の長さ、Issue の番号の順に並べる。鎖の長さには、「期限なし」と「初回提供の後」の Issue へ続く依存を数えない。開いた Issue に塞がれていない対象だけが、件数で切られずにすべて出る。「順番」の規則は、鎖の長さが同じで番号の大きい Issue も比べるので、出た候補を上から数件だけで決めない。

```sh
node .claude/skills/madori-coordinator/scripts/rank-ready.mjs
```

### 自動着手の対象

自動着手の対象は、次の Issue だけにする。

- 段階の milestone の Issue
- 「開発基盤」の Issue のうち、ラベル「スループット」が付いたもの、または開いた段階の Issue を依存で塞ぐもの。塞ぐとは、開いた Issue の依存をたどって、開いた段階の Issue に行き着くことをいう。間に挟まる Issue の milestone は問わない。

出力の4列目は、段階の組では「スループット」の印、「開発基盤」の組では対象である理由（「スループット」か `塞ぐ=#<番号>`）である。`塞ぐ=` の番号は、行き着く段階の Issue のうち、milestone の番号、Issue の番号の順で最も前のものである。対象でない Issue は出ず、最後の行の `parked=` に、着手できる数だけが出る。

「置き場を直す」の組は、milestone の無い Issue と、段階を塞ぐのに「期限なし」か「初回提供の後」にある Issue を、着手できるかを問わずに出す。この組からは担当を立てず、「Issue の置き場」の表のとおりに milestone を付け直してから、もう一度出す。組が空なら見出しも出ない。

出た候補から、担当のいる Issue と、次のどちらかに当たる Issue を除く。

- 資源の枠を超える。
- 動いている担当の Issue と同じファイルを触る。同じファイルの数え方は、「計画を Issue に分ける」の依存と同じにする。除いたら、動いている方を依存の先として「依存を登録する」のとおりに登録し、理由に同じファイルを書く。

### 資源の枠

同時に動かす担当は五人までのまま、その内側で次を守る。

- 「staging を占有する」Issue は、同時に一つまで。
- 残りの枠は、「staging を占有する」に入らない Issue で埋める。「staging を読むだけ」は枠に数えない。

担当の五つの枠と「staging を占有する」の枠には、担当を、マージの後の staging での確認を終えるまで数える。

「`pnpm dev`」と「Docker の `pnpm check --full`」は、指揮役が数えない。どちらも、マシン全体で共有する Docker の枠（開発用に二つ、runner 用に一つ）を `scripts/shared/docker-slots.ts` のロックで取ってから Docker を使い、枠が埋まっていれば空くまで待つ（README「開発を始める」）。ロックは、実際に Docker を使っているプロセスだけを数える。そのため、その資源を使う Issue の担当、検証役、判定の後の直しも、Docker の枠の空きを待たずに立て、頼んでよい。枠を待っている担当と検証役は止めない。

長く枠を持つ `pnpm dev` は、「見回り」で確かめる。

資源は Issue の「使う共有資源」の欄で読む。値の意味は[種類別のテンプレート](../../../.github/ISSUE_TEMPLATE/)にある。欄の無い Issue は、本文の「触ってよいパス」と「終わった証拠」から、同じ意味で判断する。「直した場合」のように条件つきで使う資源とパスも、使うものと数える。検証役の資源は、確かめる PR の Issue の欄で読む。枠を超えて動いている担当は止めず、枠が空くまで、その資源を使う Issue を選ばない。

### 枠の配分

担当の五つの枠のうち、段階の作業には五つまで、「開発基盤」には一つまで使う。「開発基盤」の組に候補があり、「開発基盤」の担当が動いていなければ、先にその一件を選び、残りの枠を段階に使う。段階に選べる Issue が無くても、「開発基盤」に二つ目の枠を使わず、自動着手の対象でない Issue でも埋めない。上限を超えて動いている「開発基盤」の担当は止めない。

### 順番

除いた残りから、次の順で選ぶ。段階の枠では次のとおりにする。

1. 開いている段階の milestone のうち、最も前の段階から選ぶ。その段階に、担当のいない着手できる Issue が無いときだけ、次の段階から選ぶ（3と4の場合を除く）。
2. 同じ段階の中では、ラベル「スループット」の Issue を最初に選ぶ。次に、実環境での確認や試作のように、危険を早く明らかにする Issue を選ぶ。次に鎖の長い Issue を、それでも決まらなければ番号の小さい Issue を選ぶ。
3. 次の段階を依存で塞いでいる Issue（2026-11-21 には #47）に担当が付いていれば、「スループット」の Issue を選んだ後の空いた枠は、次の段階からも選んでよい。
4. 次の二つがそろうときは、次の段階の、設計を決めるための確かめの Issue を先に選んでよい。
   - 最も前の段階で着手できる Issue が、どれも後ろに依存の続かない Issue である。
   - その段階で最も長い依存の鎖には、もう担当が付いている。

「開発基盤」の枠では、組に出た Issue から、ラベル「スループット」の Issue を先に選び、次に鎖の長い Issue を、それでも決まらなければ番号の小さい Issue を選ぶ。

## 担当を立てる

- Issue の「人の判断」が決まっていなければ、担当を立てずにユーザーに聞く。
- 立てる前に毎回 `df -h /` を見る。準備で使う数 GB を引いて 20 GiB が残らなければ立てず、「見回り」の手順2のとおりに片付ける。
- Issue 一つにつき、担当のスレッドを一つ立てる。`t3_thread_launch` で worktree を origin/main から作る。題は `#<番号> <Issue の題>` にする。
- `modelSelection` を `{instanceId: <instance>, model: <モデル>, options: [{id: "effort", value: <effort>}]}` にし、effort を省かない。`<instance>` は、`t3_thread_list` の `currentThreadId` のスレッド（指揮役自身）の `providerInstanceId` を写す。`claudeAgent` と決め打ちしない。モデルと effort は [pstack-models.md](../../rules/pstack-models.md) の `madori-owner` の行に従う。
- 応答の `modelSelection` に選んだ effort が返ったことを確かめ、その effort と理由を Issue にコメントする。
- 最初の指示は次の一行にする。`<threadId>` は指揮役のスレッドの ID で、担当はそこへ報告する。

  ```text
  /madori-owner #<番号> 報告先 <threadId>
  ```

  スラッシュコマンドとして読まれなければ、「madori-owner スキルで #<番号> を進める。報告先は <threadId>。」と送り直す。

- スレッドは一つの目的にだけ使う。手の空いたスレッドを、別の Issue に使い回さない。
- 担当の PR は担当のスレッドに紐付く。紐付いた PR がマージされると、そのスレッドは自動で settled になる。指揮役のスレッドには PR を紐付けない。紐付いていたら外し、`list_thread_pull_requests` で外れたことを確かめる。

## 検証役を立てる

担当から報告が来たら、PR の今の状態を `gh pr view` と `gh pr checks` で確かめてから、検証役を立てる。「資源の枠」が埋まっていれば、空くまで立てない。ディスクの空きは、「担当を立てる」と同じく毎回確かめる。

- 検証役は、差分の大部分を書いた系統と別の系統のモデルにする。モデルと effort は [pstack-models.md](../../rules/pstack-models.md) の `madori-verifier` の行に従い、`delegate_task` の `target` で明示する。
  - Opus：`{providerInstanceId: <instance>, model: <モデル>, options: {effort: <effort>}}`。`<instance>` は「担当を立てる」と同じく、指揮役自身のスレッドの `providerInstanceId` を写す。
  - Codex：`{providerInstanceId: "codex", model: <モデル>, options: {reasoningEffort: <effort>}}`。
- `delegate_task` に `isolation: "worktree"` を付けて、指揮役のスレッドの子として立てる。指示は [verifier-brief.md](verifier-brief.md) の `{…}` を埋めて渡す。
- `delegate_task` の `title` を `PR #<PR>（#<Issue>）の検証（<回>回目）` にする。`<回>` は指示の `{ATTEMPT}` と同じ数である。計測（`metrics/ingest/polled.ts` の `threadTitle`）はこの形で検証役のスレッドを見分け、Issue と PR に結ぶので、ほかの形にしない。
- 指示に足してよいのは、試す入力と確かめ方だけにする。合否の基準を足すなら、先に Issue に書く。普段の手順と食い違う禁止は書かない。足した基準に拠る不合格が出たら、その基準を見直してから、同じ検証役に判定し直させる。
- 同じ仕組みの端の場合で二回目の不合格が出たら、直しを重ねる前に、その仕組みを確かな情報源に切り替えるか、テストのあるスクリプトに移すかを決めて、担当に伝える。
- 検証役のスレッドには PR を紐付けない。
- 検証役を立てるたびに、その PR で何回目かを数え、指示の `{ATTEMPT}` に入れる。
- 判定は、検証役が `scripts/dev/verdict.ts` で、確かめた head に付ける。コマンドは、head にコミットのステータス `verify` を付け、判定の記録（`attempt`、`head`、`verdict`、`decided_at`、`failed_checks` の yaml）を先頭に置いた報告を PR のコメントに残す。ステータスの `state` は、合格なら `success`、不合格なら `failure` である。`description` は `attempt <回>: PASS` か `attempt <回>: FAIL <落ちた確認を「, 」でつないだもの>` で、`target_url` はそのコメントである。指揮役は判定を書き写さない。
- 検証役の報告を受けたら、判定を head のステータスで読む。GitHub は新しいものから返すので、`verify` の最初の行が最新の判定である。

```sh
gh api repos/wakamenori/instant-madori/commits/<head>/statuses \
  --jq '.[] | select(.context == "verify") | [.state, .description, .target_url] | @tsv'
```

- `verify` が無ければ（head が変わっていた、コマンドが失敗した、打たずに終えた）、報告で理由を確かめる。head が変わっていたなら、新しい head で検証役を立て直す。ほかの理由なら、同じ検証役に理由を直して打ち直させる。
- 判定のステータスを確かめたら、検証役のスレッドを `t3_thread_organize`（`action: "settle"`）で settled にする。見回りの片付けは、settled でないスレッドの worktree を残すため。

## ブランチを staging で試す

担当は staging へブランチを自分でデプロイしない。終わった証拠がマージの前の staging での確認を求めるときは、担当が指揮役に頼む。頼まれたら、その確認が読むだけか占有が要るかを、テンプレートの「使う共有資源」の意味で分ける。

- 読むだけなら、デプロイも占有もせずに、担当に知らせる。
- 占有が要るなら、占有を始めてから（「staging の占有」）、要れば `gh workflow run deploy-staging.yml --ref <ブランチ>` でデプロイする。終わったら担当に知らせる。
- 占有を始められなければ、担当に待つよう知らせる。空いたら、この手順で受ける。
- ブランチのマイグレーションは、この時点で staging の D1 に入る。入れてよいかを、頼まれたときに判断する。

## staging の占有

staging は一つしかなく、デプロイのたびに DO と Container が入れ替わって、観測や試験が壊れる。staging を占有する担当は、同時に一人までにする。

staging が空いているとは、占有している Issue が無く、先に始まったデプロイ（main へのマージの自動の実行と、そのやり直しを含む）がすべて終わっていることを言う。占有は、Issue に付けたラベル「staging を占有中」で表す。計測は、このラベルの付け外しの履歴から占有の区間を取る。

占有の開始と終了は、次のコマンドで行う。ラベルを手で付け外ししない。

```sh
node scripts/dev/staging.ts start <Issue の番号>
node scripts/dev/staging.ts end <Issue の番号>
```

- `start` は、ラベルの付いた Issue が閉じたものも含めて一つも無いことと、`deploy-staging.yml` の終わっていない実行が件数で切らずに数えて一つも無いことを確かめる。どちらかがあれば、占有している Issue と終わっていない実行を出して、何も書かずに0以外で終わる。空いていれば、ラベルを付け、人が読む開始のコメントを残す。
- `end` は、その Issue がラベルを持っていることを確かめてからラベルを外し、終了のコメントを残す。持っていなければ、何も書かずに0以外で終わる。
- 占有は次のどちらかで始まる。
  - 占有の要る確認を担当から頼まれて、受けたとき（「ブランチを staging で試す」）。`start` が通ってから、要ればデプロイする。
  - 「staging を占有する」Issue の PR をマージするとき（「マージを決める」）。マージの直前に `start` を打ち、通ってからマージする。そのマージが起こすデプロイは、この占有に含まれる。
- `start` が止まったら、占有を始めない。担当には待つよう知らせ、空いてから打ち直す。
- 占有は、その担当が確かめ終わるまで続く。終えたことを担当のスレッドを読んで確かめてから、`end` を打つ。
- 占有の間は、デプロイを起こすマージも、デプロイ（`gh workflow run`、`gh run rerun`）もしない。デプロイを起こさないマージ（「マージを決める」）では staging が入れ替わらないので、占有の間もマージしてよい。ただし、ほかに占有している担当がいなければ、占有している担当の確認に要るデプロイ（頼まれたブランチのデプロイ、失敗したデプロイのやり直し）は、指揮役が行う。

## マージを決める

次のすべてがそろったら、マージする。

- PR の今の head の最新の `verify` のステータスが `success` である（「検証役を立てる」）。
- self-hosted runner の `check` が、同じ head で成功した。ブランチ保護が無いので、`gh pr checks` で自分で確かめる。
- 自分で差分を読んだ。
- D1 のマイグレーションを加える PR なら、今の main のマイグレーションと番号が衝突しない。PR の `check` は分岐点と比べるので、先に main へ入った同じ番号には、マージの後のデプロイの `pnpm check --full` で初めて気づく。
- マージの門が通す（次の段落）。
- staging が占有されていない（「staging の占有」）か、門が `deploys: no` を出した。「staging を占有する」Issue の PR なら、マージの直前に占有を始める（「staging の占有」）。

出荷するコミットの全体検査は、staging へのデプロイの `pnpm check --full` が受け持つ。検査に落ちたコミットはデプロイされない。マージの門は、デプロイを起こすマージを一件ずつにし、main の最新の検査が失敗している間は止める。そのため、出荷するコミットはすべて自分の `--full` を通り、失敗した main に変更が積み重ならない。門は、マージの直前に、PR ごとに番号と head を書き込んで打つ。前のマージより前に打った結果は古い。

```sh
node .claude/skills/madori-coordinator/scripts/merge-gate.mjs check <番号> <head>
```

- 0で終わり、1行目が `merge` なら、マージしてよい。
- 3で終わり、1行目が `wait` なら、マージしない。理由は `reason:` の行にある。
  - main が `red` なら、「main が赤のとき」に従う。
  - main が `running` なら、前のデプロイの結果を待つ。「マージの後」で前倒しした見回りが戻る。
  - main が `unchecked` なら、main の最新のデプロイを起こすコミットを検査した実行が無い（取り消されたか、作られなかった）。staging が占有されていなければ `gh workflow run deploy-staging.yml --ref main` を打ち、「マージの後」のとおり結果を待つ。
- 1で終わったら、判定できていない。マージしない。表示された理由を直して打ち直す。
- `deploys: yes|no` の行は、そのマージがデプロイを起こすかを示す。PR の変更のうち、main の `deploy-staging.yml` の `paths-ignore` に入らないファイルがあれば `yes` で、一覧は毎回 main から読む。`deploys: no` の PR は、main が赤でも、デプロイが動いていても、staging の占有の間も、門が通す。

門は、main の状態を毎回 git と Actions の記録から導き、どこにも書き残さない。main の first parent を新しい順にたどり、`paths-ignore` の外のファイルを変えた最初のコミット（デプロイを起こすコミット）から先頭までのうち、取り消されていない deploy-staging の実行（push と、main での手動の実行）を持つ最も新しいコミットの、最も新しい実行で決める。成功なら `green`、動いていれば `running`、失敗なら `red` で、どの段階で落ちても `red` になる。そのような実行が無ければ `unchecked` である。

```sh
gh pr merge <番号> --merge --match-head-commit <head>
```

続けてマージするときも、PR ごとに、門とマージを、番号と head を書き込んだ別々のコマンドで打つ。デプロイを起こすマージの後は、そのデプロイが成功するまで、門が次のデプロイを起こすマージを止める。

main が進んだ後に `check` をやり直しても、GitHub は最初のマージのコミットで検査する。新しい main と合わせて検査するには、担当に main を取り込ませて head を新しくする。

## マージの後

マージで main に入った変更に `paths-ignore` に入らないファイルがあれば、staging へ自動でデプロイされる。次のデプロイを起こすマージはこの結果を待つので、デプロイを起こすマージの後は、ポーリングせずに、`schedule_task` の一回きりの予定（`schedule: {type: "once", runAt}`、`bindToCurrentThread: true`）で12分後に見回りを前倒しする。前倒しした見回りでは、次のコマンドで main の状態を読む。

```sh
node .claude/skills/madori-coordinator/scripts/merge-gate.mjs status
```

- `green` なら、デプロイは成功した。次のマージに進む。
- `running` なら、まだ終わっていない。5分後にもう一度前倒しする。
- `red` なら、「main が赤のとき」に従う。
- `unchecked` なら、staging が占有されていなければ `gh workflow run deploy-staging.yml --ref main` を打ち、12分後に前倒しする。

担当にデプロイを知らせるかは、そのマージで動いたデプロイの実行で決める。デプロイが動いたかは、次のコマンドで、マージコミットとその第一親の差分を、マージコミットの `deploy-staging.yml` の一覧で判定する。

```sh
node .claude/skills/madori-coordinator/scripts/deploy-files.mjs after <番号>
```

- ファイルが出たら、デプロイが動く。そのとき標準エラーに `merge commit <マージ SHA>` が出る。その実行は、マージ SHA で特定する（`gh run list --workflow deploy-staging.yml --branch main --event push --commit <マージ SHA>`）。手で始めた実行は、同じ SHA でも数えない。
- 0で終わって何も出なければ、デプロイは動かない。そのマージでは、デプロイの結果を待たず、担当にもデプロイを知らせない。
- 0以外で終わったら、判定できていない。表示された理由を直して打ち直す。
- 落ちる見込みだけを理由に、デプロイを取り消さない。取り消したマージと、検証役が確かめられなかった検査を残したマージは、その結果を読むまで見回りの手順6で追う。
- Issue の終わった証拠がマージの後の staging での確認を求めるなら、デプロイが終わったら、指揮役が担当のスレッドへ `t3_thread_send` で知らせる。担当のスレッドはマージで settled になり、担当の見張りは消えているため。知らせを受けた担当が確かめて、記録が要るなら記録の PR を作る。

### main が赤のとき

門が `red` を出したら、main の最新の検査が失敗している。直るまでは、デプロイを起こさない PR と、その失敗を直す PR だけをマージする。main が `red` か `unchecked` の間は、staging の占有を始めない。

1. 落ちた段階と試験を読む。落ちた試験の直近の合否を、`node scripts/check/test-history.ts --test <試験名>` で `check` と `deploy-staging` の両方について数え、手元で動かした結果も足す。
2. 落ちた実行を `gh run rerun <run> --failed` で一度だけやり直し、12分後に見回りを前倒しする。やり直しは、不安定か常に落ちるかを見分けるためだけに使う（AGENTS.md「検査と引き継ぎ」）。
3. やり直しが成功したら、門はそのまま `green` に戻る。不安定な試験なら不具合の Issue にし、環境の失敗なら、マージした PR に記録する。
4. 同じように落ちたら、原因を分けてすぐに動く。
   - コード：main の変更に従って落ちる。直すか戻す担当を立てる。デプロイを起こさないマージ（文書の中のパスなど）との組み合わせで落ちることもあるので、前に `green` だったコミットからのすべてのマージを疑う。
   - 外の変化（`pnpm audit` の新しい脆弱性など）：追従する担当を立てる。
   - main の変更に関係なく、どのコミットでも落ちる試験：AGENTS.md のとおり不具合の Issue にし、その試験を一時的に外す担当を立てる。
   - 続く環境の失敗（runner のディスク、Docker、Cloudflare）：環境を直してからやり直す。
5. 直す PR は、門が `deploys: yes` を出すなら、`merge-gate.mjs check <番号> <head> --fixes <run>` が通してからマージする。門は、`<run>` が今の `red` の実行のときだけ通す。門が `deploys: no` を出す直し（`.claude/` の試験、`metrics/`、文書など、`--full` が読むがデプロイしないファイル）は、そのままマージし、続けて `gh workflow run deploy-staging.yml --ref main` で直しを含む先頭を検査する。どちらも12分後に見回りを前倒しする。
6. 占有している担当の Issue のマージが main を赤にしたときは、その直しのマージと、main を検査し直す実行も、その占有に含めて指揮役が行う。

## 記録と、見つかった問題の行き先

- 判断と結果は、その Issue か PR にコメントで書く。誰の判定か、どの head か、何で確かめたかを書く。検証役の判定は、判定のコマンドが PR に書く。マージは指揮役が PR に書く。
- 画像は、AGENTS.md「Issue と PR の画像」のとおり `images` に置いたリンクで貼る。検証役は、画像の Markdown を判定のコマンドに渡す報告に入れる。
- 担当や検証役が範囲の外で見つけた問題は、根拠を確かめてから行き先を決める。関係する Issue があり、種類も同じなら、その Issue にコメントで書き足す。yaml を使う種類ではコメントの先頭に本文と同じ項目を置き、今回見つけた経緯を記す。続けて根拠を書く。投稿前に `node .claude/skills/madori-coordinator/scripts/records.mjs addition <コメントファイル> <元の種類のラベル>` で確かめる。種類が違うか、関係する Issue が無ければ、その種類のテンプレートで新しい Issue を作り、「Issue の置き場」で決めた milestone に入れて、「依存を登録する」のとおりに依存を登録する。
- 不安定な試験の Issue には、直すか消すかを決めて書かずに、「その試験が守る振る舞いを守り続ける」と書く。直すか消すかは、その試験だけが守る振る舞いの一覧で決める。消すなら、一覧の一行ずつについて、代わりに守る試験が今あって動くことを確かめてからにする。

## 見回り

T3 の定期タスクが、1時間ごとに `/madori-coordinator 見回り` を送る。次を順に行う。何も変わっていなければ、ユーザーへ報告せずに終える。見回りと進み具合の報告は、次の段階へ進むのに残る Issue と、今の段階で作った Issue と閉じた Issue の数から始める。

1. メインのチェックアウトを `git pull --ff-only` で main に合わせる。
2. `df -h /` で空きを確かめる。20 GiB を切っていたら、次の worktree とイメージを片付ける。続けて、空きに関係なく毎回、Rust の `target/` を片付ける。空きが戻るまで、新しいスレッドを立てない。片付けるのはこの三つだけにする。ユーザーの個人のデータやキャッシュの削除は頼まない。
   - 使い終わった worktree。残す worktree のパスを集め、一つずつ `--keep` に書いて次を実行する。残すものが一つも無ければ、`--keep` の代わりに `--keep-none` を付ける。

     ```sh
     node .claude/skills/madori-coordinator/scripts/worktrees.mjs sweep --keep <パス> --keep <パス>
     ```

     - 残すのは、settled でないスレッドの worktree、「資源の枠」でまだ数えている担当（マージの後の staging での確認を終えていない担当）の worktree、同じ検証役に判定し直させるつもりの検証役（「検証役を立てる」）の worktree である。担当のスレッドはマージで settled になるので、settled だけを理由に外さない。
     - settled でないスレッドは、`t3_thread_list` に `settled: false` を付けて最後のページまで出す。
     - 各スレッドの worktree は、`t3_thread_read` が返す `thread.worktreePath` で調べる。`creationSource` が `provider` のスレッドは読まない。Claude Code や Codex が自分で立てた subagent で、親のスレッドと同じ `worktreePath` を返す。
     - `t3_worktree_list` は使わない。検証役が PR の head を detached で取り出した worktree を返さない。
     - スクリプトが見るのは、次の二か所だけである。`.claude/worktrees/` の `agent-` 以外と、ほかの場所の worktree には触らない。
       - `~/.t3/worktrees/instant-madori/` の worktree は、`--keep` に無く、作られてから1時間を過ぎ、ロックも未コミットの変更も無く、HEAD が origin のどれかのブランチに入っているときに消す。detached なら、そこで作ったコミットが HEAD の履歴にだけ残っていないことも確かめる。settled の検証役が、まだマージされていない PR の head を取り出した worktree も、これで消える。
       - メインのチェックアウトの `.claude/worktrees/agent-*` は、Claude Code の subagent が動いている間に置くロックが無く、作られてから24時間を過ぎていれば、未コミットの変更ごと消す。担当が消し忘れた subagent の worktree である（madori-owner「subagent の worktree を消す」）。
     - 一行に一つ、消した worktree（`removed`）と、残した worktree（`kept` と理由）が出る。
     - 2で終わり、`--keep` のパスが worktree でないと出たら、そのパスのスレッドを `t3_thread_read` で読み直す。返るパスが同じで `does not exist` と出ていれば、そのスレッドの worktree はもう無いので、`--keep` から外して打ち直す。返るパスが違えば写し間違いなので、直して打ち直す。
     - 1で終わったら、`failed` の行を報告に書き、手で消さない。

   - このリポジトリの形状サービスのイメージ。メインのチェックアウトで次を実行する。`pnpm docker:prune-images` を使わないのは、`git pull` で lockfile が変わると、`pnpm` が `node_modules` の食い違いを理由に実行を断るためである。

     ```sh
     node scripts/dev/prune-images.ts
     ```

     - このコマンドは、Container が使うイメージと、動いている Wrangler（`pnpm dev`、実 Container の試験、runner の `pnpm check --full`、staging へのデプロイ）がタグを付けたイメージを残す。ほかのプロジェクトのイメージには触らない。残す規則は README にある。
     - これのほかに、Docker のイメージ、ビルドキャッシュ、Container、ボリュームを消すコマンドを打たない。`docker image prune -a` は、Container を作る前のイメージを消し、そのセッションのジョブやデプロイを失敗させる（#402）。
     - 1で終わったら、出た行を報告に書き、手で消さない。

   - Rust の `target/`。空きに関係なく毎回、メインのチェックアウトで次を実行する。worktree とイメージを片付けるときは、その後に実行する。

     ```sh
     node scripts/dev/prune-targets.ts
     ```

     - 対象は、メインのチェックアウトの `target/` と、runner ごとの `target/` だけである。16 GiB を超えたものと、空きが 20 GiB を切っている間の古いものを、丸ごと空にする。規則は README「開発を始める」にある。
     - `busy` の行は、使用中なので残した `target/` である。理由を報告に書き、手で消さない。次の見回りでまた試す。
     - 空きが戻ったかは、最後の行の `freeBytes` で判断する。`short` が `true` なら、`target/` を空にしても 20 GiB に戻っていない。その行を報告に書く。
     - 1で終わったら、出た行を報告に書き、手で消さない。
3. 担当ごとに、コミット、push、PR、`check` の動きを確かめる。報告の来た PR と、報告は無いが `check` の通った PR には、検証役を立てる。承認待ちで止まったスレッドは「承認待ちで止まったとき」のとおりに扱う。ほかの理由で止まった担当は、新しい担当に入れ替える。
4. `node scripts/shared/docker-slots.ts status` で、Docker の枠を持つプロセスを見る。`pnpm dev` が枠を持っていて、それを起動したスレッドがターンを終えて待っているなら、そのスレッドに `pnpm dev` を止めるよう頼む。
5. 終わった検証役の判定を読み、「マージを決める」に進む。
6. 前の見回りの後にしたマージと、前の見回りまでにデプロイの結果の確認か担当への知らせが済んでいないマージ、「マージの後」で追うと決めたマージについて、「マージの後」の判定でデプロイが動いたかを確かめる。動いたマージは、その実行の結果を読み、「マージの後」のとおりに扱う。実行が終わっていなければ、次の見回りでまた確かめる。動かないマージは待たない。
7. 動いている担当が五人より少なければ、「次の Issue を選ぶ」で選んで担当を立てる。

## 承認待ちで止まったとき

担当、担当が任せた Codex、検証役は、シェルのコマンドの承認の要求で止まることがある。承認は T3 の画面からしか出せず、`t3_pending_request` では答えられない。止まったスレッドは、`status` が `running` のまま進まない。避ける書き方は madori-owner「シェルで止まらない」にある。

- 見回りの手順3と、検証役の報告が遅いときに、`t3_thread_list` に `includeSubagents: true` と `statuses: ["running"]` を付けて、動いているスレッドを出す。担当が任せた Codex のスレッドは、`parentThreadId` が担当のスレッドである。
- それぞれを `t3_thread_read` で読む。`thread.pendingRequestCount` が1以上なら止まっている。`view: "activity"` の中で `type` が `approval_request` で `status` が `waiting` の項目の本文が、止めたコマンドである。Claude Code のサブエージェントの要求は、親のスレッドに出る。
- 承認せずに立て直す。検証役は `task_cancel` で止め、止めたコマンドと代わりの書き方を指示に足して、新しい検証役を立てる。担当が任せた Codex なら、担当のスレッドへ `t3_thread_send` で知らせ、その Codex を止めて、代わりの書き方を指示に書いて任せ直させる。担当自身なら、`t3_thread_interrupt` で止めてから、代わりの書き方で続けるよう送る。
- 止めたコマンドの書き方が madori-owner「シェルで止まらない」に無ければ、そのスキルを直す Issue を作る。

## milestone を閉じる

- 閉じるのは段階の milestone だけにする。「開発基盤」「期限なし」「初回提供の後」は閉じない。
- milestone は、その Issue がすべて閉じたときに閉じる。Issue が一つも無い milestone は閉じない。
- 段階の受け入れを確かめる Issue は、記録に失敗や未確認の項目が一つでも残る間は閉じない。直した後に確かめ直す。
- 閉じる前に、次の三つを行う。
  - 「期限なし」の Issue を見直す（「Issue の置き場」）。
  - `/pstack:reflect` で、その段階の進め方を振り返る。見つかった改善は Issue にするか、このスキルや madori-owner を直す担当を立てる。
  - 担当を一人立て、`/pstack:maintain-verification-skill` で verify-madori の地図を点検させる。直すところは一つの PR にまとめさせる。
