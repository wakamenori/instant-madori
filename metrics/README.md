# Software Factoryの計測

このフォルダーには、Software Factoryが機能を届ける速さと、その内訳を計測する仕組みを置く。計測は、サービス（`apps/`、`crates/`、`packages/`）から独立した開発の道具である。記録はこのマシンのSQLiteに溜め、それを読むviewerもこのフォルダーに置く。

## 計測で答える問いと指標

最上位の目的は、段階のmilestoneが全部閉じるまでの期間を短くすることである。ただし、これは全部閉じたときに一度だけ測れる考え方として置き、日常の指標にはしない。日常の目的は、利用者に見える振る舞い（機能）を、より速く届けることである。指標は、この日常の目的から逆算して、一つの北極星指標（NSM）とその分解の木で持つ。

```
NSM  対象のスループット ＝ 同時進行数 × 対象の工数比率 ÷ 対象1件あたりの工数
 ├─ 同時進行数         ← 上限の内訳：進行中、割り当て待ち、リソース制約で着手不可、着手可能なIssueなし
 ├─ 対象の工数比率     ← 種類別の工数
 └─ 対象1件あたりの工数 ← 作業・待ち・未分類
```

- 対象は、機能のIssueだけか、すべての種類のIssueかを画面で選ぶ。日常の目的に当たるのは機能だけで、すべての種類は工場全体の流れを見るときに使う。すべての種類では対象の工数比率が常に1になるので、式は同時進行数 ÷ 1件あたりの工数になる。
- 木の段は、親とのつながり方でそろえる。一段目（L1）には、掛けると親に一致する恒等式だけを置く。二段目（L2）には、互いに重ならず、足すと親に一致する内訳だけを置く。相関でしか言えない原因（一度で検証に合格した割合など）は木に入れず、L2の区分を調べるときに見る。
- L2の区分は、値が変わったときに打つ手が決まるものだけにする。打つ手の決まらない細分は、問いが出てから足す。L1の記録は残るので、後から足しても集め直さない。
- 分母は動いた時間にし、工場がどれだけの時間動けたか（稼働率）は追わない。動けた時間を左右するのはusageの残りと持ち主の判断で、持ち主の判断は測る対象にしないからである。
- 品質と開発の仕組みの改善の効果は、木の外の指標として持つ。

指標は、なるべく自動で取れる記録から決める。判定、占有、マージのような出来事は、文章から読まない（「計測に要る記録は、作業の副作用として残す」）。文章から取るのは、指示に書かれたIssueの番号と役割、Issueの決まった欄だけである。

### 共通の決まり

- 着手は、担当のスレッドが作られた時刻である。担当を止めて立て直したIssueでは、担当ごとに着手から手放すまでの区間を持ち、止めていた間は数えない。
- 担当が手放した時刻は、そのIssueを最後に閉じたマージと、担当の最後のターンの終わりの、遅いほうである。担当は報告するとターンを終えて待つので、最後のターンだけで決めると、検証とマージ待ちの時間が落ちる。マージの後にstagingで確かめるIssueでは、確かめ終わったターンまで入る。
- 完了は、PRがマージされてIssueが閉じたことである。開き直してまた閉じたIssueは、最後に閉じた時刻で数える。PRなしで閉じたIssue（不要、重複、ほかのPRで済んだもの）は数えない。担当を通さずに完了したIssueは、スループットにも1件あたりの工数にも数えず、件数を別に出す。担当を通さなかったのか、担当の記録が欠けたのかは、PRのブランチ名と作り手で見分け、記録が欠けたものは別の件数として出す。
- 動いた時間は、着手してから担当が手放すまでのIssueが1件以上ある時間である。工場を止めている時間と、指揮役だけが動いている時間は含めない。しきい値で切ることはしないが、エージェントもCIも動いていない時間が長く続いたら、計測の信頼性として知らせる。
- 工数は、各Issueの着手から担当が手放すまでの時間を、動いた時間の中で全部足したものである。2件が同時に1時間ずつ進めば、工数は2時間である。待っていた時間も、マージの後の確かめも含む。
- 期間は1時間ごとに区切る。完了の数で決まる値は、短い区間では完了が0件になりやすいので、直近の一定の動いた時間の合計で出す。その長さは直近の稼働4時間、8時間、24時間から画面で選び、初めは8時間にする。スループットの分解に使う四つの値（対象のスループット、同時進行数、対象の工数比率、対象1件あたりの工数）は、すべて同じ長さで出す。完了の数で決まる値には偶然のぶれの範囲を添え、期間の境目で開いていたIssueの件数も並べる。
- スループットとその分解、工数の内訳は、2026年11月21日12:21 UTC以降の記録で出す。それより前は、モデルとツールの呼び出しごとの記録が無いので見ない。品質と種類別の件数は、それより前に閉じたIssueも数える。

### Issueの種類

種類は、何を変えるか（製品か、開発の仕組みか）と、どういう変更か、の二つの軸で決める。

| どういう変更か ＼ 何を変えるか   | 製品（利用者が使うものと、その計画） | 開発の仕組み（作る・確かめる・届ける・動かす仕組み） |
| -------------------------------- | ------------------------------------ | ---------------------------------------------------- |
| 新しくする・良くする             | 機能                                 | 開発の仕組みの改善                                   |
| 約束どおりでなかったのを戻す     | 製品の不具合                         | 開発の仕組みの不具合                                 |
| 振る舞いを変えずに、作りを変える | 製品の作りの見直し                   | 開発の仕組みの作りの見直し                           |
| 外の変化に合わせる               | 外の変化への追従（両方に共通）       | 外の変化への追従（両方に共通）                       |
| 知る・決める                     | 確かめと判断（両方に共通）           | 確かめと判断（両方に共通）                           |

指揮役は、Issueを起こすときに、次の問いに順に答えて種類を決め、そのラベルを一つだけ付ける。

```
問1  変える理由は、外から来たか？（依存、脆弱性、外のサービスやツールの変化）
     はい → 外の変化への追従
問2  成果は、作ったものではなく、分かったことや決めたことか？
     （試作、計測、確かめ、受け入れ、計画の中身を決める）
     はい → 確かめと判断
問3  変えるのは、製品か、開発の仕組みか？
問4  変える前は、約束どおりに動いていたか？
     違っていた                               → 製品の不具合／開発の仕組みの不具合
     約束どおりで、できることを足す・良くする → 機能／開発の仕組みの改善
     約束どおりで、できることは変えない       → 製品の作りの見直し／開発の仕組みの作りの見直し
```

問いが前提にする定義は次のとおりである。

- 約束は、plan.md、Issueの終わった証拠、AGENTS.mdとREADMEの決まり、公開しているAPIの仕様、これまで動いていた振る舞いである。
- 製品は、利用者が使うもの（コード、データ、素材）と、その約束（計画）である。
- 開発の仕組みは、作る・確かめる・届ける・動かす仕組みである。担当と検証役の手順、スクリプト、検査、CI、デプロイ、運用のための仕組み（ログ、集計、照合、本番の環境）を含む。
- 約束どおりに動いていたかは、実際にどう動いていたかで答える。まだ起きていない穴は約束どおりなので、それを塞ぐ作業は改善（事故を防ぐ投資）になる。
- 改善と作りの見直しの境目は、製品も開発の仕組みも同じである。速くする、事故を防ぐ、できることを足すなら改善（製品では機能）、できることも出来の良さも変えずに作りだけを整えるなら作りの見直しである。事故を防ぐとは、検査や守りのような新しい仕組みを足すことである。今ある作りを整える作業は、型で縛る、定数をまとめるなど、動機が誤りを防ぐことでも、作りの見直しである。
- 製品では、まだ作っていない振る舞いを作るなら機能、作った振る舞いが約束と違っていたなら製品の不具合である。利用者に届いたかどうかは問わない。
- 利用者との約束（データの保持期間など）を満たす振る舞いは製品である。運用する人の道具（ログ、集計、照合、本番の環境、版の記録）は開発の仕組みである。
- 文書（plan、README、AGENTS.md、スキル）が実態と食い違っていたのを直す作業は、書いてあるとおりに従うと失敗する手順なら不具合、説明が古いだけなら作りの見直しである。
- 製品のテストだけを足す作業は、テストが確かめる手段なので、開発の仕組みの改善である。
- 実際に困ったことでも、それを禁じる約束が書かれていなければ、不具合ではなく改善である。不具合として数えたいときは、分類を曲げずに、その約束をAGENTS.mdやREADMEに書く。
- 種類は、何のための作業かで決める。スクリプトを作っても、段階の確かめ・受け入れ・計測のための手段なら確かめと判断である。

ラベルの名前は、意味が名前だけで伝わるように、次の8つにする。GitHubのラベルの名前は50文字までなので、その中に収める。

- 機能：利用者に見える振る舞いを足す・変える
- 製品の不具合：約束どおりに動かない製品を直す
- 製品の作りの見直し：振る舞いを変えずに作りを変える
- 開発の仕組みの改善：作る・確かめる・届ける・動かす仕組みを良くする
- 開発の仕組みの不具合：約束どおりに動かない仕組みを直す
- 開発の仕組みの作りの見直し：振る舞いを変えずに作りを変える
- 外の変化への追従：依存・脆弱性・外のツールの変化に合わせる
- 確かめと判断：試作・計測・受け入れ・計画づくりで知る・決める

ラベルの扱いは次のとおりである。

- 一つのIssueには、一つの変更だけを入れる。既存のIssueに書き足す問題の種類が元のIssueと違うなら、書き足さずに新しいIssueにする。
- 作業してみて違えば、付け替えてよい。計測は閉じた時点のラベルを使い、閉じた後の付け替えは使わない。付け替えの履歴は、閉じた・開き直したの履歴と一緒にGitHubから時刻の順に取り込み、件数と一覧を出す。
- まだ閉じていないIssueの工数は、今付いているラベルの種類で暫定に数え、閉じた時点のラベルで確定する。作業中のIssueの時間を種類の不明にすると、直近の機能の工数比率がいつも低く出るためである。
- ラベルのなかった過去のIssueは、同じ問いで一度だけ分類し直す。これは閉じた後の付け替えの例外とし、別の出どころとして取り込んで、後から付けたことが分かるようにする。不具合と作りの見直しの見つけた経緯も、同じ出どころで取り込む。閉じたIssueの本文とラベルは書き換えない。開いているIssueには、新しい決まりを使い始めるときに種類のラベルだけを付け、yamlは書き込まない。開いている開発の仕組みの改善の狙いは、指揮役が担当を立てる前にyamlとして書く。
- ラベル「スループット」は種類ではなく急ぎの印なので、今の役目のまま使う。
- 製品の作業か開発の仕組みの作業かは、ラベルで決める。PRが変えたファイルは、ラベルと食い違っていないかを確かめるのに使う。製品のラベルなのに `apps/`、`crates/`、`packages/` を一つも変えていない、開発の仕組みのラベルなのにそれらしか変えていない、といった食い違いは、計測の信頼性として出す。この検査では、テストのファイル（`*.test.*` と `tests/` の中）は開発の側に数える。
- 機能でない作業は、どれも必要な作業だが、終わっても利用者に届くものは変わらない。その効果は、後から機能のスループットに出る。種類ごとの完了数と工数を出し、機能でない作業が急に増えたら、機能が紛れていないかを見直す。
- 約束の誤りを直して振る舞いを変える作業は、機能に数える。そのため、元のIssueの品質の指標には出ない。件数が少ないので、記録を足さずに受け入れる。

### スループットとその分解

| 指標                | 計算                                                  | 単位 | 読み方                                                                                                                                                                   |
| ------------------- | ----------------------------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 対象のスループット  | 期間中に完了した対象のIssueの件数 ÷ 動いた時間        | 件/h | 多いほど良い                                                                                                                                                             |
| 同時進行数          | 工数 ÷ 動いた時間                                     | 件   | 良し悪しの向きは持たない。開いているIssueを増やせば上がるが、その分だけ1件あたりの工数が悪くなる。1件あたりの工数と、上限の内訳と並べて読み、上限を変えるかの判断に使う  |
| 対象の工数比率      | 対象のIssueの工数 ÷ 工数                              | %    | 多いほど良い。ただし、開発の仕組みの改善に回した分は投資である。また、対象のIssueが手戻りやマージ待ちで時間を延ばすだけでも割合は上がるので、1件あたりの工数と並べて読む |
| 対象1件あたりの工数 | 対象のIssueの工数 ÷ 期間中に完了した対象のIssueの件数 | h/件 | 少ないほど良い                                                                                                                                                           |

四つを同じ期間で出せば、同時進行数と対象の工数比率を掛け、対象1件あたりの工数で割った値は、完了が1件以上ある期間では、いつも対象のスループットに一致する。対象のスループットは直接数え、三つはどれが動いたかを説明するのに使う。1件ずつの着手から完了までの時間はこの式に入れず、時間がかかりすぎたIssueを探すときに1件ずつ見る。

このNSMは、試作や確かめを先に進める時期には下がって見える。段階の性質として受け入れ、読むときの注意とする。

### 同時進行数の上限の内訳

同時進行数が担当の上限より低い時間は、空いていた1件分の1分ごとに、次の理由のどれか一つに割り当てる。上のものを優先する。どれも自動で取れる記録から決める。上限までを、進行中と三つの理由で積む。

| 理由                   | 決め方                                                                                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 着手可能なIssueなし    | 依存がすべて閉じた、担当のいないIssueが無い                                                                                                                     |
| リソース制約で着手不可 | 着手できるIssueはあるが、stagingを占有するIssueは同時に一つまで、段階と開発基盤の枠の配分、のどちらかで選べない。Issueの「使う共有資源」の欄とmilestoneで決める |
| 割り当て待ち           | 着手できて、リソースの制約でも選べるIssueがあるのに、担当がいない                                                                                               |

担当の上限の値は、指揮役のスキルの変更の履歴から追う。

### 内訳

工数は、Issueごとに、その時間に何が起きていたかで分ける。一段目は互いに重ならず、足すと工数に一致する。

| 一段目 | その時間に起きていること                                                             |
| ------ | ------------------------------------------------------------------------------------ |
| 作業   | Issueの内側の担い手のだれかが応答を生成しているか、そのIssueのための機械が動いている |
| 待ち   | 何も動いておらず、待っている相手が分かっている                                       |
| 未分類 | 何も動いておらず、待っている相手も分からない                                         |

- Issueの内側の担い手は、担当、実装役、検証役と、それぞれのサブエージェント、指揮役がT3でそのIssueのために立てたエージェントである。指揮役そのものは、多くのIssueを扱う共有の処理者なので外側に置き、指揮役を待つ時間を待ちに数える。
- 応答生成は、モデルが推論し、コード、コマンド、文章を書いている時間である。実行は、機械が動いている時間で、ローカルのツールとhook、CI、デプロイを含む。CIは、workflowの実行1回（最初のjobの開始から最後のjobの終了まで）を一つの区間にする。
- 待つためのツールは、それ自体を実行に数えない。`sleep`、`until`、`--watch` などのコマンド、Claude Codeの `Agent`、Codexの `wait` と `write_stdin` がこれに当たる。その時間は、待っている相手で決まる。CIを見張っていればCIの実行、実行中のプロセスを待っていればその実行、サブエージェントを待っていればその子の生成と実行になる。相手が分からなければ未分類になる。
- 判断の依頼（`AskUserQuestion` など）は、ツールの時間として記録されても実行には数えず、人を待つ時間に数える。

作業時間の内訳は、応答生成、ローカルでの実行、CIとデプロイの実行の、それぞれの合計で出す。区間は重なってよいので、内訳の合計は作業時間より大きくなり、その倍率を並行度として出す。同じ担い手の中でも、Claude Codeは応答を受け取りきる前にツールを動かし始めるので、応答生成と実行は重なる。

待ち時間は、待っている相手で分ける。足すと待ち時間に一致する。

| 相手     | 内容                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| 人       | 承認と、判断の依頼への回答                                                     |
| リソース | CIのrunner、Dockerの枠、stagingの占有、デプロイの順番                          |
| 指揮役   | 報告や判定の後、次の手が打たれるまで。指揮役が別件を対応中か、停止中かで分ける |

二つの相手を同時に待っていたら、人、リソース、指揮役の順に一つに決める。この順は仮のもので、重なる頻度を測ってから決め直す。

フェーズは、この内訳と掛け合わせる別の切り口である。フェーズと一段目の表は、すべてのセルを足すと工数に一致する。実装を終えて検証を待つ時間は、検証の列の、待ちのセルに出る。

| フェーズ   | 始まりと終わり                               |
| ---------- | -------------------------------------------- |
| 実装       | 着手から、最初に検証したheadのpushまで       |
| 検証       | 検証したheadのpushから、そのheadの判定まで   |
| 手戻り     | 不合格の判定から、次に検証したheadのpushまで |
| マージ待ち | 合格の判定からマージまで                     |
| マージ後   | マージから担当が手放すまで                   |

区間の始まりと終わりは、出来事が起きた時刻で決める。記録のコメントを書いた時刻は使わない。

### 品質

品質は、作ったものが一度で正しくできているかを見る。NSMの木には入れず、対象の工数比率と1件あたりの工数の区分を調べるときに見る。誰の不備かで分け、1件ずつの性質の割合で持つ。期間ではなく、比べたい作業の集まり（たとえば工程を変える前と後に完了したIssue）で計算する。製品と開発の仕組みに分けて出す。作りの見直しと不具合は、それぞれ製品の種類と開発の仕組みの種類で数える。

| 指標                     | 計算                                                                                                              | 何の不備か                        | 関係する区分                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------- | --------------------------------- | ----------------------------------------------------------------------- |
| 一度で検証に合格した割合 | 1回目の検証の判定がPASSだったIssue ÷ 検証したIssue。落ちた確認ごとの割合も持つ                                    | 検証より前（担当、実装役）        | 対象1件あたりの工数。検証で落ちると、手戻りのフェーズの時間が延びるため |
| 作りの見直しが起きた割合 | マージの後に初めて見つかった作りの見直しの、原因になった完了済みIssue ÷ 完了したIssue。計画の変更によるものは除く | 検証より前（設計、Issueの切り方） | 対象の工数比率。新しいIssueが起きるため                                 |
| 不具合が漏れた割合       | マージの後に初めて見つかった不具合の、原因になった完了済みIssue ÷ 完了したIssue。開き直して直したものも含む       | 検証（見逃し）                    | 対象の工数比率                                                          |

- 検証の回数は、検証役が確かめたheadに付けたコミットのステータスを1回と数え、合否、落ちた確認、時刻もそこから取る。検証役のメッセージとPRのコメントは、ステータスを使い始める前の記録にだけ読む。
- 検証役は立ったが判定が無い回は、記録の抜けとして出し、分母から外す。検証役が立たないままマージしたIssueは、一度で合格しなかったものとして数え、記録の抜けとしても出す。
- 指揮役に検証の手順が入った2026年11月18日01:49:39 UTC（`faf6af125`）より前にマージしたIssueは、初回判定の分母から外す。「検証の手順が無かった時期」の件数を `pre_verification` に出す。
- 一度で合格した割合には、Issueを閉じたPRの検証だけを数える。閉じた後の記録のPRの検証は、件数を別に出す。
- 見つけた時点は、原因になった作業のマージより前か後かで決める。担当がほかのIssueで入った問題を作業中に見つけたら、マージの後になる。自分のまだマージしていない作業で見つけた問題は、PRの中で直すのでIssueにならない。
- 検証で見つけて後に回したものは、見逃しには数えず、別の件数として出す。
- マージの後の二つは、原因のIssueを最後に閉じたマージから、動いた時間で30時間以内に見つかったものを数える。30時間たつまでは暫定の値とし、観察を終えたIssueの割合を添える。30時間という長さは、データがたまったら見直す。
- 原因が「不明」や「もとからあった」ものは分子に入らないので、その件数も出す。
- 件数が少ないうちは偶然のぶれが大きい。30件で割合が25%なら、ぶれは上下15ポイントほどある。

### 開発の仕組みの改善の効果

- 計測の側に、狙いとして書ける項目の一覧を持つ。各項目は、識別子、名前、定義、単位、良くなる向きを持つ。
- 開発の仕組みの改善のIssueには、この一覧から、何を減らすつもりかを狙いとして書く。一覧に無い狙いなら、急ぎの改善でも、先に計測を足すIssueを起こし、改善のIssueをそれに依存させる。計測のIssueの終わった証拠には、記録が取り込まれ、狙いの値を読めることを入れる。改善の前の数字をためる時間は決めず、計測が改善より先に入ることだけを守る。
- 計測を足すときは、まず自動で取れる記録を探す。自動で取る手段が無い狙いだけは、数字では評価せず、Issueの成功の条件を満たしたかで見る。この場合は、計測を待たずに改善を進める。
- 効果は、改善がマージされる前と後で、同じ長さの動いた時間について狙いの数字を比べて見る。偶然のぶれの範囲を添える。改善の前の観測が無ければ、比べられないとする。同じ狙いの改善が近い時刻に入ったら、分けずにまとめて一つの変化として評価する。
- 承認待ち（`approval.wait`）は、担当と検証役が承認の要求で止まっていた時間を、工数で割って見る。承認待ちの時間は、ほかの担い手が作業していなければ、内訳の待ち（人）に入る。狙いとしては、承認だけを取り出して別に持つ。
- 事故を防ぐ改善（検査を足すなど）は、前と後でどちらも0件に近くなるので、防いだ回数で見る。足した検査が実際に何かを捕まえた回数を、CIのstepや試験の失敗から自動で数える。あわせて、同じ種類の事故がまた起きたかを、長い期間で見る。

## 生の記録と解釈を四つの層に分ける

受け取った記録を書き換えずに溜める層と、それを解釈する層を分ける。解釈の規則を変えたときに、記録を集め直さずに計算し直すためである。

| 層         | 置くもの                             | 書くもの   | 作り直し               |
| ---------- | ------------------------------------ | ---------- | ---------------------- |
| L1 raw     | 受け取ったままの記録と、その出どころ | 受け口だけ | 作り直さない。追記だけ |
| L2 staging | ソースの単位で型を付けた表           | 変換       | L1だけから作り直す     |
| L3 core    | ファクトリーの領域モデル             | 変換       | L1だけから作り直す     |
| L4 marts   | 指標と、計測の仕組み自体の健康状態   | 変換       | L1だけから作り直す     |

viewerはL4を読む。詳しく見るときはL3を読む。

層をまたいで、次の決まりを守る。

1. L1は追記だけにする。間違いは変換の側で直す。
2. L2から上は、L1だけから作り直せる。作り直しの入口を持ち、テストでも使う。
3. 発生した時刻と取り込んだ時刻を分けて持つ。遅れて届く記録と、順番が前後する記録を扱うためである。
4. 取り込みは、何度実行しても同じ結果になる。読み終えた位置は、書き込みが成功した後に進める。
5. 外から来る形は入口で検証する。検証を通らない記録も捨てずに隔離する。

## L1は出どころを問わず同じ包みで溜める

L1の行は、どの出どころでも同じ列を持つ。

- `ingest_id` は、取り込みごとの識別子である。
- `source` は出どころで、例えば `claude.otel.log`、`claude.hook`、`codex.otel.log`、`t3.run`、`github.actions.job`、`factory.cli` である。
- `kind` は出どころの種類で、出来事は `event`、状態の観測は `observation` とする。
- `prev_ingest_id` は同じ対象の直前の観測を指す。
- `source_version` は、出どころの形式の版である。
- `observed_at` は取り込んだ時刻、`occurred_at` は出どころが言う発生時刻である。`occurred_at` は無ければ空にする。
- `natural_key` は出どころの識別子、`content_hash` はpayloadの内容のハッシュである。
- `payload` は、保存前に下記のプライバシー規則を適用したJSONである。

出どころには二つの種類がある。

- 起きたことが一度だけ届くもの（OTel、hook、CLI）は、届いたまま追記する。
- 今の状態を読みに行くもの（GitHubのPRとActionsのjob、T3のスレッドとターン）は、前回の観測と内容が違うときだけ、新しい観測として追記する。T3の表のように履歴を持たない出どころでも、いつ何が変わったかがL1に残る。

一度だけ届く出どころの重複は、`source`、`natural_key`、`content_hash` の組で除く。状態を読みに行く出どころは、同じものの最新の観測と内容が同じときだけ除く。A、B、Aと変わったときの二度目のAも残すためである。どちらの決まりも、L1の表の一意の索引が守る。入口で検証するのは包みの形だけで、payloadはL2で解釈する。

## L2は出どころの癖を吸収する

L2は、出どころの単位ごとに一つのモデルを持つ。最初に持つモデルは次のとおり。

- GitHubからは、`stg_github_issue`、`stg_github_blocked_by`、`stg_github_pr`、`stg_github_comment`、`stg_github_commit_status`、`stg_github_issue_event` を作る。
- GitHub Actionsからは、`stg_actions_job` と `stg_actions_step` を作る。
- T3からは、`stg_t3_thread`、`stg_t3_run`、`stg_t3_message` を作る。`stg_t3_message` はメッセージの種類と送り手だけを持ち、本文を持たない。
- Claude Codeからは、`stg_claude_session`、`stg_claude_model_call`、`stg_claude_tool_call` を作る。
- Codexからは、`stg_codex_session` と `stg_codex_tool_call` を作る。
- 工程の判断からは、`stg_factory_event` を作る。

状態を読みに行く出どころからは、最新の状態の表と、有効期間を持つ変化の表の二つを作る。時刻はUTCにそろえる。解釈できなかったpayloadは、理由と一緒に隔離の表へ入れる。

同じ種類の記録が、時期によって違う出どころから来ることがある。例えばツールの時間は、過去の分を会話ログから、これからの分をOTelから取る。L2はどちらも同じ `stg_claude_tool_call` の形にそろえ、出どころを列に残す。

## L3は一つのIssueを一本のtraceとして表す

L3は、記録をファクトリーの言葉で表す。一つのIssueを一本のtraceとし、そこで起きた活動をspanとして持つ。OTelのtraceと同じ形なので、OTelから来る記録とそのままつながる。

- 作業項目（`work_item`）はIssueである。milestone、作成した時刻、着手できるようになった時刻、閉じた時刻を持つ。着手できるようになった時刻は、依存するIssueがすべて閉じた時刻である。
- 変更（`change`）はPRで、版（`revision`）はheadのSHAとpushの時刻である。変更は、本文の `Closes #N` で作業項目に結ぶ。
- 担い手（`actor`）は、役割、モデル、effort、T3のスレッド、セッションを持つ。役割は、指揮役、担当、検証役、実装役（Codex）、設計の相談役のどれかである。
- 対応表（`identity_link`）は、セッション、T3のスレッド、作業項目、変更、版を結ぶ。どの手がかりで結んだかも持つ。手がかりは、`T3CODE_THREAD_ID`、最初の指示、cwd、`Closes` である。
- span（`span`）は、始まりと終わりのある活動である。ターン、モデルの呼び出し、ツールの呼び出し、Codexの実装、検証、CIの順番待ちと実行、デプロイ、staging占有を含む。どのspanも、作業項目と担い手に結ぶ。
- 出来事（`event`）は、一瞬で起きることである。報告、判定、マージ、マージを止めたこと、直しの依頼を含む。判定はPASSかFAILかとFAILの理由の分類を、マージを止めたことはその理由を持つ。

## L4は指標の定義を版付きで持つ

L4は、L3から指標を計算する。指標の定義はコードとして版を付けて持つので、定義を変えてもL1を集め直さない。

- Issueの流れは、着手できた、着手した、PRを出した、マージした、stagingに反映した、の各時刻の間隔を持つ。待ちの内訳、FAILの回数、費用も持つ。
- 工数の内訳は、Issueごとに、spanの始まりと終わりとフェーズの境目で区切った区間で持つ。区間ごとに、一段目、待ちの相手、フェーズ、応答生成と実行の合計を持つ。分ごとの行は作らない。
- CIは、jobごとの順番待ちと実行の時間と、1時間ごとのrunnerの稼働率を持つ。
- マージ待ちのフェーズの時間を、待ちの相手ごとに持つ。
- 担い手は、役割とeffortごとに、モデルとツールの時間、トークン、費用を持つ。
- 流れ全体は、同時進行数、対象のスループット、作業の割合を持つ。作業の割合は、作業の時間を工数で割った値である。
- 計測の仕組みの健康状態は、出どころごとの最後の取り込み、取り込みの遅れ、隔離した件数を持つ。受け口は1分ごとに、出どころごとの件数（追記、重複、保留、期限切れ、L1に入れずに捨てた数）と最後に取り込んだ時刻を、出どころ `metrics.receiver` の記録としてL1に書く。そのため健康状態もL1だけから作り直せる。

## viewerは振り返りと診断に使う

viewerは、持ち主がときどき開いて、工場が速くなっているか、遅いならどこが原因か、次に何を直すかを決めるために使う。今止まっている担当を見つけて手を入れるのは、指揮役の見回りとT3の画面の役目なので、viewerは今の監視をしない。

### 並べ方

1画面に収める。上の帯に、集計対象（機能のみ、全種類）と集計期間（直近の稼働4時間、8時間、24時間）の切り替えを置く。初めは全種類と直近8時間を表示する。機能の完了が無い時期にも、最初の画面を空にしないためである。

1. 1段目に、数字のタイルを並べる。スループット（NSM）を左に一番大きく置き、同時進行数、機能の工数比率（機能のみのときだけ）、1件あたりの工数を続ける。各タイルには、単位、良い向き、95%区間と完了件数、推移の小さな線を添える。
2. 2段目の左に、1件あたりの工数の内訳（作業・待ち・未分類の積み上げ）を置く。右に、フェーズ別の内訳の表と、待ち時間の内訳・作業時間の内訳の横棒の一覧を置く。表のセルを押すと、3段目のIssueの一覧を、そのセルの時間が長い順に絞り込む。
3. 3段目に、同時進行数の上限の内訳（積み上げ）、種類別の完了件数（全種類のとき）か種類別の工数比率（機能のみのとき）、期間内に完了したIssueの一覧を置く。Issueの一覧は工数の多い順に上位6件を出し、残りは開いて見る。Issueを押すと、担い手ごとの経過を開く。
4. 最下行に、計測の信頼性の要点（未分類の割合、Issueに結べなかった記録、期間内の完了件数）を1行で置く。

品質、開発の仕組みの改善の効果、計測の信頼性の詳しい表は、1画面の下に続けて置く。

- 色は、作業を青、待ちを橙、未分類を灰にする。種類を色で分けず、種類別の数は横棒の一覧で出す。色の組は、dataviz の検査（色覚の多様性への配慮）を通したものを使う。
- 時間のグラフは、ポインタを当てた時刻の値を一覧で出す。1件あたりの工数の内訳には、同じ値を表で見る切り替えを付ける。

### 横軸と期間

- 横軸は動いた時間にする。止めていた時間は詰め、止めていた所に区切りの印と、再開した日時を書く。指標が動いた時間で定義されているので、1目盛りが1時間の稼働になり、期間の幅も見たままになる。
- 値は直近の一定時間の移動の値で、その長さは直近の稼働4時間、8時間、24時間から画面で選ぶ。初めは8時間にする。
- 比べる基準の線や、前の期間との差は出さない。機能の完了が少ないうちは、二つの期間の差はほとんどが偶然のぶれだからである。線にぶれの範囲を帯で付け、線の流れと帯で読む。右端には、今の値をぶれの範囲と一緒に書く。

### 注意の出し方

注意は見た目で表し、文章にするのは記録が届いていないときだけにする。

| ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 偶然のぶれの範囲                                                                                                                   | 線の周りの帯                                                    |
| 30時間たっていない品質の値                                                                                                         | 値を薄くし、観察を終えたIssueの割合を添える                     |
| 内訳の未分類                                                                                                                       | 内訳の色の一つとして並べる                                      |
| 割合の分母の件数                                                                                                                   | 値に `n=41` のように添える                                      |
| 分母から外した件数、期間の境目で開いていたIssue                                                                                    | ポインタを当てたときだけ出す                                    |
| 担当の記録の抜け、ラベルと変えたファイルの食い違い                                                                                 | 値の横には出さず、計測の信頼性の節にまとめる                    |
| 記録が届いていない（集計の時点から見て、巡回する出どころが周期を超えて成功していない。直近の期間の中で、新しく隔離した記録がある） | そのときだけ、ページの一番上に1行出す。詳しくは計測の信頼性の節 |

### 作り方

- 受け口が集計を作り直すたびに、1枚の静的なHTMLを書き出す。記録にはIssueの題名や作業の中身が入るので、このマシンの外には出さない。
- 集計のDBから画面用のデータを作る部分と、そのデータを描く部分を分ける。今は、データをHTMLに埋め込む。全部は埋め込めない詳しさ（1件のIssueの分刻みの経過など）を必要なときに取る、別の機械から見る、画面から書き込む、のどれかが要るようになったら、同じデータを返す読むだけのサーバーを足す。そのサーバーは、記録を書く受け口とは別のプロセスにする。
- どの集計期間の値も、L4の移動の値と一致させる。
- 集計期間と集計対象のすべての組み合わせを前もって計算して埋め込み、切り替えは表示を替えるだけにする。担い手ごとの経過は、最も長い集計期間の中で完了したIssueの分だけ埋め込む。

## 記録は三つの部品で取り込む

受け口は `node metrics/receiver/receiver.ts` で起動する。`127.0.0.1:4318` を確保してからDBを開き、spoolを取り込んでからHTTP要求を処理する。二つ目の受け口が同じポートを確保できなければ、DBを開く前に終了する。

- ログは `POST /v1/logs`、メトリクスは `POST /v1/metrics` にOTLP/HTTP JSONで送る。ログは1件ずつ、メトリクスはデータ点ごとに所属を判定する。保留を含む書き込みが確定したら200、保存に失敗したら503を返す。
- 検証に失敗した要求は、信号の種類、バイト数、SHA-256、検証エラーのパスだけを隔離する。JSONとして読めない要求は隔離して400を返す。
- `GET /health` はSQLiteの `health_source` ビューを返す。出どころごとに最終受信時刻、過去24時間の件数と遅れ、隔離・期限切れの件数、現在の保留件数を読める。

- 受け口は、launchdで常駐し、OTLP/HTTPとhookの記録を受ける。L1に書くのは受け口だけにして、書き手を一つにする。hookは受け口に送らず、いつも一時ファイル（spool）に書いて終わる。受け口は1秒ごとにspoolを取り込み、書き込みが成功した後にファイルを消す。受け口が止まっている間はspoolに溜まり、戻ったときに、OTLPを受け始める前に取り込む。受け口がこのマシンで一度も動いていなければ、hookは何も書かない。受け口のポートはOTLP/HTTPの既定の4318で、`pnpm dev` が使う5173と8787を避ける。
- ポーラーは、GitHub（Issue、依存、PR、コメント、コミットのステータス、Issueの出来事（ラベルの付け外し、閉じた、開き直した）、Actionsのjobとstep）を数分ごとに、T3のDBを1分ごとに読む。T3のDBは読み取り専用で開く。
- Claude Codeのhookは、リポジトリの `.claude/settings.json` に置く。SessionStartは、`session_id` とT3のスレッド（`T3CODE_THREAD_ID`）とcwdを結ぶ。UserPromptSubmitとStopは、ターンの始まりと終わりを記録する。承認の要求と回答はT3の承認ごとの記録から取る（`approval.wait` の項を参照）。PermissionRequestのhookの記録は集計に使わない。バックグラウンドで起動したBashは、PostToolUseの `backgroundTaskId` と、終わったときにUserPromptSubmitに届く通知（作業のID、`tool_use_id`、状態、終了コード）で結び、終わりの時刻は通知にある出力ファイルの更新時刻から取る。PreToolUseとStopは、決まった道具を通さない操作と、決まった形の出力が欠けたときだけ止める（「計測に要る記録は、作業の副作用として残す」）。ツールとモデルの時間はOTelが出すので、hookでは測らない。

OTelは、リポジトリではなくこのマシンの設定で有効にする。Claude Codeは、プロジェクトの `.claude/settings.json` の `env` に書いたテレメトリーの設定を使わないためである。

- Claude Codeは、`~/.claude_personal/settings.json` の `env` で有効にする。T3は、このフォルダーを `CLAUDE_CONFIG_DIR` としてClaude Codeを起動する。
- Codexは、`~/.codex/config.toml` の `[otel]` で有効にする。リポジトリの `.codex/hooks.json` は、SessionStart、UserPromptSubmit、PreToolUse、PostToolUse、PermissionRequest、Stopを登録する。worktreeのセッションも本体のチェックアウトの `.codex/hooks.json` を読み、コマンドはセッションのcwd（worktree）で動く。そのため、定義の承認と変更は本体のチェックアウトに入ってから効き、スクリプトは各worktreeの版が動く。承認は定義のハッシュに結び付くため、各イベントのコマンドは次の2行に固定し、`<Event>` にはイベント名を入れる。
  1. `node metrics/hook/codex.ts <Event> >/dev/null 2>&1 || true` は、ツールの出力を除いてspoolに書く。記録に失敗してもセッションに出力を返さず、作業を続ける。
  2. `node scripts/dev/agent-guard.ts <Event>` は、標準入力を読み終えて成功する。今後の検査が判定を返せるよう、出力と終了コードはそのままCodexに渡す。

受け口はCodexのhookからイベントやターンなどの事実、指示と最終応答から取り出したIssue番号や役割などの要約、コマンドやパスを残したツール入力だけを保存する。Codexは `apply_patch` のパッチ全体を `command` で送るので、`*** Add File:` などのファイルの見出しの行だけを残し、ファイルの中身は捨てる。cwdのgit共通ディレクトリがこのリポジトリと違えば破棄し、一致すれば会話を `t3.codex_link` で照合してから `codex.hook` としてL1に入れる。

OTelの設定はこのマシンのすべてのセッションに効く。受け口は、hookの記録でこのリポジトリと結べたセッションと、T3のDBでこのリポジトリのスレッドと結べたCodexの会話だけをL1に書き、ほかは捨てる。hookは、セッションのプロジェクトの `.git` が何を指すかを書き、受け口はそれがこのリポジトリのgitの共通ディレクトリかを確かめる。本体のチェックアウトと、Claude CodeとT3が作るworktreeは、どれも同じ共通ディレクトリを持つ。Codexの `conversation.id` は、読み取り専用の `~/.t3/userdata/statev2.sqlite` でCodexスレッドの `nativeThreadRef.nativeId` と照合する。本体のチェックアウトがプロジェクトの `workspace_root` と一致したら、根拠を `t3.codex_link` としてL1に残す。照合に失敗した回数は受け口の健康記録に含める。結べるまでの記録はプライバシー規則を適用してSQLiteに保留し、24時間のうちに結べなければL1に入れずに捨てる。

過去の分は、T3のDB、会話ログ、GitHubから一度だけ取り込む。取り込んだ記録の `source` には、これからの記録と区別できる出どころの名前を付ける。

## 保存はSQLite、変換はSQLで行う

- DBは、Nodeに組み込みの `node:sqlite` で扱うSQLiteで、WALモード、`synchronous=FULL` で開く。置き場所は `~/Library/Application Support/instant-madori/metrics.sqlite` で、リポジトリとworktreeの外である。`INSTANT_MADORI_METRICS_HOME` でDBとspoolの親ディレクトリを指定できる。
- L2〜L4は、SQLファイルで書く。小さなTypeScriptの実行役が、それを依存の順に流して作る。
- L2から上の計算が遅くなったら、L2から上をDuckDBに移す。DuckDBは書き手が一つのプロセスに限られるので、L1には使わない。

## L1に入れるものを先に決める

L1は直さない約束なので、入れた記録を後から消すのは難しい。そのため、入れるものを次のように決める。

- 指示の本文（ユーザーと指揮役が書いた文）は入れない。UserPromptSubmitの本文からは、役割、Issue、PR、ターンを起こしたものの種類だけを取り出し、本文は捨てる。Stopの `last_assistant_message` も捨てる。
- 利用者を示す属性は入れない。OTelの記録にある `user.email`、`user.id`、`user.account_uuid`、`user.account_id`、`organization.id`、`host.name` は、受け口で捨てる。
- コマンドの文字列は入れる。後で分類を変えたときに、集め直さずに済むためである。既知の形のトークンは、受け口で伏せる。
- ツールの入力（OTelの `tool_input`、`tool_parameters`、Codexの `arguments`）は、コマンドと、ツールが働いた場所（ファイルのパス、パターン、URL）だけを残し、ほかの文字列は長さだけにする。サブエージェントへの指示やほかのスレッドへのメッセージは、指揮役と担当が書いた文だからである。ツールの出力（Codexの `output`）も入れない。
- OTelのログの本文（`body`）は、イベント名でなければ捨てる。指示の文が本文に入る送り方に変わっても、L1に入れないためである。
- DBは、このマシンの外に出さない。

## 計測に要る記録は、作業の副作用として残す

指揮役、担当、検証役は、計測のための操作をしない。計測は、作業の道具が残す出来事、T3のDB、OTel、hookから組み立て、文章は読まない。計測の仕組みが止まっても壊れても、三者の作業は変わらない。

記録の取り方は、次の順に選ぶ。

1. すでに出ている事実を読む。OTel、T3のDB、GitHubの出来事（マージ、push、ラベルの付け外し、コミットのステータス、Actionsのjob）である。
2. 作業の道具が、本来の仕事の副作用として事実を残す。道具は、使ったほうが仕事が楽で安全になる形にする。
   - 検証の判定は、検証役が、確かめたheadにコミットのステータスとして付ける。合否と落ちた確認を持つ。
   - stagingの占有は、指揮役が開始と終了をそれぞれ一つのコマンドで行う。コマンドは、ほかのIssueが占有していないかを確かめ、Issueのラベルを付け外しし、人が読むコメントを残す。
   - マージは、`check` と検証のステータスをブランチ保護の必須の検査にして、GitHubに止めさせる。指揮役はマージを一つのコマンドで行い、コマンドはheadの固定と、占有中ならデプロイを起こさない変更かを確かめる。
   - 手元の検査は、`pnpm check` などのスクリプトが、始まり、終わり、終了コードを受け口に残す。Dockerの枠の待ちも同じ形である。
3. hookがツールの呼び出しを横から見る。止めるのは、決まった道具を通さない操作と、決まった形の出力が欠けたときだけにする。
   - 検証役のStopのhookは、判定のステータスを付けずに終わろうとしたら止める。
   - 指揮役が `gh pr merge` を直接実行したら、PreToolUseのhookが止めて、マージのコマンドを案内する。
4. 文章とyamlの読み取りは、2で置き換える前の記録にだけ使う。置き換えた後の記録が最も長い期間（24時間の稼働）の分たまったら、読み取りを消す。

- 人が書く記録は、指標が成り立たなくなるほど影響の大きいものだけにする。決まった形の記録は、Issueの本文の先頭とコメントに置くyamlのブロックである。yamlには、自動では取れないのに指標に要る事実だけを書く。種類はラベルだけに持ち、yamlには書かない。キーは英語、値はラベルや選択肢と同じ日本語にする。ルールで管理し、集計しやすくするためである。T3のスレッドはこのマシンにしか残らないので、どれもGitHubに残す。決まりは、指揮役のスキル、検証役への指示、Issueのテンプレートに書く。出来事の時刻は、yamlの中に、出来事が起きた時刻として書く。コメントを書いた時刻は使わない。
  - Issue（指揮役が起こすときに書く）：製品と開発の仕組みの、不具合と作りの見直しでは、見つけた時点（マージの前の検証、マージの後）、見つけた人、原因（Issue、PR、外の変化、もとからあった、不明）、計画の変更によるものか（作りの見直しのとき）。開発の仕組みの改善では、狙い。機能、外の変化への追従、確かめと判断のIssueには、yamlを書かない。
  - 既存のIssueへの書き足し：Issueと同じ、見つけた経緯。
- Issueのテンプレートは種類ごとに分け、yamlの要る種類のテンプレートにだけ、本文の先頭にyamlのブロックを置く。指揮役の下書きのフロントマターから、その種類に要る項目を本文のyamlへ写す。共通の見出しは8つのテンプレートでそろえ、依存の欄はちょうど一つにする。依存を登録するスクリプトが、それを前提にしているためである。種類を付け替えて要る項目が変わったら、yamlの項目もそろえる。検査は、ラベルを見て、その種類に要る項目がyamlにそろっているかを確かめる。
- 計測は、yamlのブロックと、Issueの「使う共有資源」の欄から、決まった項目だけを取り込む。本文全体は取り込まない。
- Dockerの枠の待ちは、`scripts/shared/docker-slots.ts` が、待ちごとの識別子、待ち始めた時刻、終わった時刻と理由（枠を取れた、取り消した）、手放した時刻を受け口に残す。担当や検証役の待ちは、どのworktreeから呼ばれたかでIssueに結び、runnerの待ちはActionsのrunと試行で結ぶ。
- ラベルを付けた・外した、Issueを閉じた・開き直した、の履歴は、GitHubから時刻の順に取り込む。最後に閉じたPRと、閉じた時点のラベルは、この履歴から決める。
- 計測は、記録の抜け（ラベルやyamlのブロックが無いもの、決まりどおりでないもの）を見つけて出す。抜けた分は、指揮役がラベルかyamlを足して埋める。計測は本文を読まない。
- 抜けに数えるのは、その時点の決まりが求めていた記録だけである。今の記録の決まりを使い始めた `43c2075b0` より前の記録と、過去の分類で埋めた種類は、抜けに数えない。開いているIssueのyamlは、開発の仕組みの改善で、狙いが無いまま担当を立てたときだけ抜けに数える。
- そのほかの工程の出来事は、すでにある記録から導く。導けない出来事は、推定できないものとしてL4に出す。
- hookは、すべての担当、検証役、指揮役のセッションで動く。そのため、受け口が無くても速く終わる。記録だけのhookは何も出力せず、終了コード0で終わる。止めるhookだけが、止める理由を出す。止めるかどうかは、受け口の有無で変わらない。
- 計測のIssueとPRには、見分けるためにラベル `metrics` を付ける。計測のIssueも、指揮役がほかのIssueと同じように担当を立てて進める。開発の仕組みの改善の狙いを測るための計測が、改善より先に入るようにするためである。
- `metrics/` だけの変更では、stagingへデプロイしない。そのため、計測のPRのマージは、staging占有に関わらず行える。
- ポーラーは、GitHub APIの上限を指揮役と分け合う。条件付きリクエストを使い、残りが一定の数を下回ったら次の周期まで待つ。
- 計測の健康状態は、viewerにだけ出す。指揮役の見回りには出さない。
- `metrics/` は、`apps/`、`crates/`、`packages/`、`scripts/` をimportしない。サービスも `metrics/` をimportしない。hookはNodeの組み込み、`metrics/home.ts` とhook内だけを読み込み、取り込みのパーサーはI/Oを行わない。L1への書き込みを開始できるのは受け口だけである。各境界を `scripts/check/boundaries.ts` の表に加えて検査する。

## 設計が頼る前提

試作で確かめた前提は次のとおり。

- T3は、起動するClaude Codeのプロセスに `T3CODE_THREAD_ID` を渡す。T3が起動したセッションで、プロジェクトの `.claude/settings.json` のhookが動き、その入力に `session_id`、`prompt_id`、cwdが入る。
- Claude CodeのOTelは、モデルの呼び出しごと（`api_request`）に時間、最初のトークンまでの時間、トークン、費用、モデル、effortを出す。ツールの呼び出しごと（`tool_result`）に、ツール名、時間、成否、コマンドを出す。OTelの `session.id` は、hookの `session_id` と同じ値である。
- プロジェクトの `.claude/settings.json` の `env` に書いたOTelの設定は、T3でもコマンドラインでも効かない。プロセスの環境変数とフラグの設定では効く。
- CodexのOTelは、`conversation.id`、トークン、最初のトークンまでの時間、effort、ツールの判定を出す。
- CodexはT3のすべてのスレッドで一つの `codex app-server` を共有するので、環境変数ではスレッドを見分けられない。
- launchdで動くプロセスから、`gh` の認証、`git` のリモートへの接続、T3のDBの読み取りが使える。

有効にした後で確かめた前提は次のとおり。

- Claude Code 2.1.330では、`bypassPermissions` のモードでも、PreToolUseのhookがBashの入力を書き換え、実行を止められる。バックグラウンドで起動したBashは、起動した時点でPostToolUseが出て、`tool_response` に `backgroundTaskId` が入る。終わると、作業のID、`tool_use_id`、状態、終了コードを含む通知がUserPromptSubmitのhookに届く。
- Claude Code 2.1.330では、同じツール呼び出しのPreToolUseがPermissionRequestより先に動く。PermissionRequestの入力には `tool_use_id` がない。回答する人がいないために拒否された要求では、PermissionDeniedは動かなかった。T3は人に示した承認ごとに `runtime_requests` に1行作る。Claude Codeでは `nativeRequestRef.nativeId` が呼び出しの `tool_use_id` に一致する。`resolved_at` には回答の時刻か、ターンの中断で要求を取り下げた時刻が入る。Claude Codeがその場で拒否した要求には行がない。
- Codex 0.169.0のプロジェクトのhookは、本体のチェックアウトで承認すれば、そのworktreeでも、承認を飛ばす指定なしに動く。コマンドはセッションの作業ディレクトリで動くので、相対パスで書けばworktreeのスクリプトが動く。PreToolUseはコマンドを書き換え、止められる。Stopのhookの入力には `last_assistant_message` が入る。承認のハッシュは定義だけから計算され、手元の承認済みのhookでも、定義から計算した値が記録された値と一致した。

- `~/.codex/config.toml` の `[otel]` は、T3の `codex app-server` で効く。T3が立てたCodexのスレッドの記録が、`t3.codex_link` で結ばれてL1に入った。
- `~/.claude_personal/settings.json` の `env` に書いたOTelの設定は、`CLAUDE_CONFIG_DIR` を同じフォルダーにして起動したClaude Codeで効く。 T3が起動したClaude Codeでも効き、2026年11月21日12:21 UTC以降のモデルとツールの呼び出しがL1に入っている。このリポジトリのhookと組み合わせると、記録がこのリポジトリのものとしてL1に入った。

まだ確かめていない前提は次のとおり。

- Claude Codeの検証役のStopのhookが、判定のステータスが無いまま終わろうとするのを止められる。
- 検証役が付けたコミットのステータスを、ブランチ保護の必須の検査にできる。
- 受け口が止まっているとき、OTelの送信の失敗が、担当、検証役、指揮役のセッションに何も表示しない。

## 集計を作り直す

`node metrics/build/build.ts` は、計測ディレクトリの `metrics.sqlite` を読み取り専用で開き、`metrics-derived.sqlite` の全表を一つのトランザクションで作り直す。受け口は追記後にこのコマンドを子プロセスで起動する。起動間隔は最短1分である。

T3はプロジェクトの最初のスレッドから、GitHubは2026年11月1日から収集する。以後は取り込みが確定した位置から再開する。GitHub APIの残量が1500件を下回ると、その周期を見送る。失敗と見送りの回数は `mart_health` で確認できる。

今の実装は、区間で持つ形（L4）に移すまで、待ち時間を担当スレッドが作成された瞬間から1分刻みで分類する。マージ直前の端数も1分に数えるため、状態別の合計とタイムスタンプから求めた経過時間には、Issueごとに1分未満の差が出る。

集計結果の `owner_interval` は担当スレッドごとの区間、`mart_minute` は Issue・UTC 分ごとの旧来の区分である。同じ Issue の立て直しが同じ分に入ったときは、その分を一度数える。`mart_turn_detail` は時間が分かるツールやモデル、承認、Docker 枠の記録を持つ。これらには重なりがあるので工数には足さない。

`mart_kpi` と `mart_kind_period` の `hour` は UTC の正時を表す Unix 秒である。`window='rolling'` の行は、その時間の終わりから、動いた時間を `span` 時間（4、8、24）さかのぼる。2026年11月21日12:21 UTC 以降の記録を使い、蓄積が短ければ実際の分数を出す。`mart_kpi.target` は「機能」か「全種類」で、「全種類」には種類不明の Issue も含む。工数がある期間は「全種類」の工数比率が1になる。

`window='hour'` の行は、その正時からの1時間を開始日の制限なく集計し、`span` は NULL とする。現行のビューアーが使う `mart_kpi` の時間別集計は「機能」を対象に各時間1行を出す。`mart_kind_period` はどちらの期間でも種類・区分別の工数と完了数を持つ。`INSTANT_MADORI_METRICS_WINDOW_MINUTES`（既定480分）は改善効果を比べる期間だけを指定する。

スループットは件／稼働時間、1件あたりは工数／件である。区間は完了数の両側95%ポアソン信頼区間から求め、分母が0の値は NULL とする。「外の変化への追従」と「確かめと判断」は両方に共通なので、種類ごとに数え、製品・開発の区分は `unknown` に入れる。種類不明の工数も同時進行数の分子に入る。過去分の分類は `[{"issue":123,"kind":"機能"}]` の形の JSON ファイルを `node metrics/import/classifications.ts <file>` に渡す。不具合と作りの見直しの行には Issue と同じ `found_at`、`found_by`、`cause` を入れ、作りの見直しには `plan_change` も入れる。受け口は spool から L1 の `classification.backfill` に保存する。`issue_classification.kind_source` に `backfill` が残る。

`owner_limit` の各行には、指揮役の上限が変わったコミットとその時刻を記録する。上限が変わったら行を加える。`mart_slot_candidate` は選べる候補を段階・開発基盤の空きに優先して割り当て、余った枠を融通する。`mart_empty_slot.slots` は理由ごとの枠・分である。Issue の記録が初めて届くまでの共有資源と依存には、最初の観測値を使う。

`deployment_delivery` は成功したデプロイのコミットをマージに結ぶ。後のコミットで反映されたかを確かめるときは、GitHub ポーラーが L1 に保存した `github.commit` の最初の親をたどる。親の記録が途切れた先の反映は推定しない。`mart_record_gap_count` は記録の抜けなどの件数、`mart_inactive_stretch` は担当区間の中でエージェントと CI がともに30分以上動かなかった期間を示す。

閉じた時点のラベルと PR の変更ファイルが食い違った Issue は、`mart_record_gap` の `label_file_mismatch` で確認できる。ファイル一覧が完全な PR を対象に、移動前と移動後の両方のパスを調べる。

`mart_quality_issue` は、マージで閉じた Issue ごとに初回判定、観察完了、見直し、漏れを持つ。`mart_quality` はそれを製品と開発に分ける。観察完了前の Issue を含む率は暫定値である。番号付き判定もスレッドも無い過去分は、マージの5分後までに作成された PR コメントに残った判定の印がすべて一致すれば使う。旧形式の印には対象の head が残らないため、マージ直後の報告もこの時間内で拾う。印が混在すれば初回は不明とする。どちらも判定時刻は補わず、件数を `legacy_comments` に出す。発見日時の専用欄がないため、Issue 本文の発見はその Issue の作成時、追記はコメント作成時に置き、検証で発見したという `found_at` を優先する。`mart_failed_check` の分母は初回の結果が判定できた Issue 数で、確認名が残っていない失敗があると各率は下限になる。その件数は `unknown_checks` に出す。`mart_discovery_count` では原因不明、もとからあった問題、検証で見つけて後に回した問題などを別々に数える。

狙いは `improvement_target` の `id` を使う。一覧にない識別子（英数字、ピリオド、ハイフン、アンダースコア）は `unknown_target` として記録の抜けに出す。日本語の成功条件など、その文字種に収まらない自由文は `manual` として比較から外す。これは自由文と識別子を同じ YAML の欄に書く現行形式での判別方法である。

`approval.wait` の値は、UTC の分ごとに、`mart_minute` の時刻 `at` に承認を待っていた Issue の数である。CodexとClaude Codeの承認は、どちらもT3から同じ形式で取る。要求から回答または取り下げまでが1行に収まるので、要求と回答を突き合わせる必要はない。対象はコマンド、ファイルの読み書き、権限、MCPの確認である。Codexの質問とClaude CodeのAskUserQuestionは除く。Claude Codeがその場で拒否した要求は人に表示されず、T3の記録にも残らない。担当か検証役のスレッドの承認の要求（`mart_turn_detail` の `approval`）が `at` に答えを待っていれば、その Issue・分を数える。同じ分に要求が重なっても、担当と検証役が同時に待っていても、一度だけ数える。Claude Code のサブエージェントの要求は親のスレッドの記録になるので、担当のターンが終わった後の要求も担当の分に入る。答えの記録が無い要求は、そのスレッドの次のターンの区切りまで待っていたとする。区切りは、要求を出したターンの終わりで、ターンの外の要求なら次のターンの始まりである。要求は、スレッドが作られた時点の担当区間に属する。担当なら自身の区間、検証役ならその時点でIssueを担当していたスレッドの区間である。その区間内に始まった要求だけを、区間の終わりまで数える。止まったスレッドの要求は、次の担当の分に入らない。T3が別のスレッドとして立てた実装役と相談役の要求は数えない。`at` は要求と関係なく決まるので、二つの時刻の間に始まって終わる1分より短い要求は数えないが、多くの分を足した割合は、承認を待っていた時間の割合に偏らない。分ごとの狙いの分母は、`slot.*` が全枠・分で、品質を除くほかの狙いが工数である。

`mart_improvement_effect` は同じ狙いの連続したマージの間隔が集計期間（既定480稼働分）未満ならまとめる。最初のマージ前と最後のマージ後で、両側に取れる同じ分数を使う。狙いの観測分母がない側とその差は NULL になる。品質の見直しと漏れは観察完了済みの Issue で比べる。割合の差の参考範囲は両側の Wilson 95% 区間の端点の差で、同一 Issue 内の分同士の相関は補正していない。

事故防止の狙いは `prevention_signal` で workflow と専用 step 名に結ぶ。`mart_prevention_catch` はマージ以降に開始した run でその step の結論が failure になったとき、同じ run と head の再試行を1件にまとめる。`mart_prevention` はこの件数を改善別に出す。step の失敗は検出の代理指標で、外部サービスの失敗も含み得る。汎用の試験実行 step は個別の検査と結べないので登録しない。

事故防止は比較期間を設けず、次に同じ狙いの改善が入るまで追う。`checked_runs` が0件なら検出数は NULL になる。`main_runs` と `main_failures` で、main で同じ検査を実行した回数と失敗数を確認できる。main でその検査を走らせていない期間の再発は判定できない。
